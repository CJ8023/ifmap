## 1. 背景与问题

ifmap 是 JSON ↔ JSON 的模板/规则引擎，同一个模板配不同的 `JsonOps` 实现（Jackson / fastjson）必须产出**同样的报文**。`docs/05-SpringBoot集成.md` 明确承诺：

> 上面 6 条之外若出现不一致，属于实现 bug，两边测试都会红。

这个承诺**当前是假的**。同一份模板 + 同一份源报文，两个实现产出的报文**字节不同**，而 24 条 TCK 用例与 438 个测试全绿 —— 因为 TCK 的数字断言只做**数值相等**（如 `assertEquals(12.34d, ((Number) m.get("amount")).doubleValue(), 1e-9)`，见 `JsonOpsConformanceTestBase.java:174`），从不校验**字符串形态**。

### 1.1 实测证据（本轮探针，`D:\cj\tmp\probe\`）

源报文（两个实现共用）：

```json
{"amount":10.00,"bigAmt":12345678.90,"tiny":0.000001,"exp":1.0E10,"half":0.100,
 "neg":-0.00,"items":[1.50,2.25],"nested":{"c":1.0E10},"longId":12345678901234567890,"flag":true}
```

模板 `{"v":"$.<字段>"}` 的渲染结果：

| 源字段 | Jackson（starter 默认） | fastjson | 一致？ |
|---|---|---|---|
| `amount`: `10.00` | `"10.0"` | `"10.00"` | ❌ |
| `bigAmt`: `12345678.90` | `"1.23456789E7"` | `"12345678.90"` | ❌ |
| `tiny`: `0.000001` | `"1.0E-6"` | `"0.000001"` | ❌ |
| `exp`: `1.0E10` | `"1.0E10"` | `"1.0E+10"` | ❌（两边都不对） |
| `half`: `0.100` | `"0.1"` | `"0.100"` | ❌ |
| `neg`: `-0.00` | `"-0.0"` | `"0.00"` | ❌ |
| `items`: `[1.50,2.25]` | `[1.5,2.25]`（JSON number） | `[1.50,2.25]` | ❌ |
| `longId` | `"12345678901234567890"` | 同 | ✅ |
| `flag`: `true` | `"true"` | 同 | ✅ |

规则族（`numRound`/`numSum`/`numOffset`/`numFormat`）全部走 `BigDecimal.toPlainString()`，**是安全的** —— 泄漏只在 `$.path` 直接取值与 `@sum@` 两条路径上。

### 1.2 根因（分层）

1. **JsonOps 层丢字面量**：`JacksonJsonOps.defaultMapper()` 未开 `USE_BIG_DECIMAL_FOR_FLOATS`，Jackson 在 JsonPath 层就把 `10.00` 变成 `Double 10.0` —— **尾零在引擎拿到值之前就没了**，下游任何转换都救不回来。
2. **TemplateEngine 层出科学计数法**：`TemplateEngine.normalizePathValue()` 用 `String.valueOf(value)`。`Double.toString` 对 |v| ≥ 1e7 或 < 1e-3 出科学计数法（`1.23456789E7`）；`BigDecimal.toString()` 对负 scale 也出科学计数法（`1.0E+10`）。
3. **归一化不递归**：`normalizePathValue` 是叶子专用，数组/对象内的数字原样透传 → 科学计数法进了数组，且两个实现形态不同。
4. **同逻辑散落 5 处**：`TemplateEngine.normalizePathValue`、`TemplateEngine.toDecimal`、`Text.join`、`StringRules.concat`、`Coercions.coerce` 各自写了一遍 `String.valueOf`。

### 1.3 数组语义的静默脏数据

`StringRules.concat(Object... parts)` 内部 `sb.append(part)`，而 `RuleRegistry` 的「实参是 List 就逐元素映射」只在**无候选可匹配**时才触发（`RuleRegistry.tryMapOverList`）—— `Object...` 永远匹配成功，于是数组被整体 `append`，走 `List.toString()`：

| 模板 | 实测输出 | 问题 |
|---|---|---|
| `@FUN(concat,$.a,$.b)`（两个数组） | `"[01, 02][100, 200]"` | Java `List.toString()` 直接进报文 |
| `@FUN(concat,$.rates)`（单数组） | `"[1.5, 2.5]"` | 同上；`docs/02` §3.1 承诺的「逐元素」不生效 |
| `{"row@array":{"a":"@FUN(concat,$.a,-,$.b)"}}` | `[{"a":"[01, 02]-[100, 200]"}]` | 模板结构看着完全正确，输出是垃圾 |

这类输出**不会抛异常**、看起来像正常文本 —— 属于最危险的一类缺陷。

### 1.4 `@sum@` 的静默失败与校验漏网

| 模板 | Jackson | fastjson |
|---|---|---|
| `$.amount@sum@$.flag`（布尔参与求和） | `10.0`（**静默把 flag 当 0**） | `10.00` |
| `@sum@$.amount,$.amount`（逗号误用） | `0`（**静默**） | 抛 `IfmapConfigException` |

- `TemplateEngine.toDecimal` 捕获 `NumberFormatException` 后 `log.warn` + 返回 `BigDecimal.ZERO`，与同项目的 `Text.toDecimal`（抛 `RuleArgumentException`）语义相反。
- `ConfigValidator.JSON_PATH`（`admin/ConfigValidator.java:57`）正则是 `\$\.[A-Za-z0-9_\[\]\.\*\?']*`，会在 `$.amount,$.amount` 里**匹配出合法片段** `$.amount`，整串没被校验 → 误用漏网。根因是**校验器与引擎用了两套不同的表达式切分/识别逻辑**。

## 2. 目标与非目标

### 目标

1. 同一模板 + 同一源报文，两个 `JsonOps` 实现渲染出的报文**逐字节相等**，并由测试钉住。
2. `$.path` 取到的小数**保留源文字的小数位**（`10.00` → `"10.00"`），绝不出现科学计数法。
3. 数组/对象内的数字**保持 JSON number 类型**，但同样不出科学计数法。
4. `@sum@` 与 `numSum` 的类型语义对齐。
5. 1.3 / 1.4 三类静默失败改为**可观测 + 可拒绝**（两阶段）。

### 非目标（本批不做，见 §8）

- 缺的能力：`trim`/大小写/全角半角/`strPad`、时间戳↔日期/时区、显式输出 `null`、bool→`Y/N` 专用规则。
- 缺的整合能力：真正的条件分支（if-then-else / switch）、两个并行数组按位合并成字符串。
- 非 JSON 报文（XML / 定长 / 分隔符 / GBK）。
- 5 条 biz 规则外移、`@and@` 规则改名。

## 3. 决策记录

| # | 决策 | 依据 |
|---|---|---|
| D1 | **保真做两层**：JsonOps 层保证「小数到 JDK 层不丢字面量」+ TemplateEngine 层保证「到报文层统一 plain」 | 单做任一层都不够：只做引擎层救不回已被 Double 化的尾零；只做 JsonOps 层仍会输出 `1.0E+10` |
| D2 | **归一化递归，但只 plain 化不改类型**（数组/对象内保持 JSON number） | 不推翻 `docs/02` §2.1 已声明的契约、不改坏存量配置的报文结构；要字符串时用 `numRound`/`numFormat` 显式声明 |
| D3 | **`@sum@` 返回 String**，与 `numSum` 一致 | 项目已定「金额类规则统一返回字符串」（`NumberRules` 类注释），`@sum@` 是唯一例外，配置侧最易踩 |
| D4 | **静默失败两阶段**：`ifmap.strict-types=warn`（默认）→ 下个版本 `fail` | 存量配置里可能存在 `@FUN(concat,$.arr)` 这类写法，直接拒绝会打断线上；且数组类型无法静态扫描，只能靠 warn 阶段线上观测 |
| D5 | **`@sum@` 位数口径 = 保留各操作数最大小数位** | `BigDecimal.add` 的 scale 天然等于 `max(scale…)`，即**数值本身完全不变、只改返回类型**，改动面最小；金额要定位数有 `numSum(v,scale,rounding)` 显式表达 |

### 4.1 U1 · JsonOps 契约升级：小数保真

**职责**：保证 `JsonOps` 的 JDK 边界上，小数是 `BigDecimal` 且序列化时不出现科学计数法。这是唯一能修「尾零丢失」的层。

**改动**

| 文件 | 改动 |
|---|---|
| `ifmap-json-jackson/.../JacksonJsonOps.java` | 同一个 mapper 既负责读也负责写（`defaultMapper()`，`JacksonJsonOps:69-110`）→ 同时配两向：读增 `DeserializationFeature.USE_BIG_DECIMAL_FOR_FLOATS=true`，写增 `SerializationFeature.WRITE_BIGDECIMAL_AS_PLAIN=true` |
| `ifmap-json-fastjson/.../FastjsonJsonOps.java` | 解析侧本就出 `BigDecimal`（`FastjsonValues.parseDocument` 用 `Feature.OrderedField`），不改；`toJson` 增 `SerializerFeature.WriteBigDecimalAsPlain` |
| `ifmap-core/.../json/JsonOps.java` | javadoc 增「小数契约」小节 |

**`JsonOps` 小数契约（新增到接口 javadoc）**

1. `parse` / `readContext().read(...)` 遇到 JSON 小数必须返回 `java.math.BigDecimal`，且 **scale 等于源文字的小数位数**（`10.00` → scale 2）。
2. 整数按 `Integer` / `Long` / `BigInteger` 选型（超出 `long` 用 `BigInteger`），不得退化为浮点。
3. `toJson` 不得输出科学计数法（`1.0E+10` 必须写成 `10000000000`）。
4. 返回值必须全部是 JDK 原生类型（既有契约，`JdkNativeValues` 已覆盖；`BigDecimal` 是 `Number`，兼容）。

**API 名已核对**（`javap` 实测存在）：`DeserializationFeature.USE_BIG_DECIMAL_FOR_FLOATS`、`SerializationFeature.WRITE_BIGDECIMAL_AS_PLAIN`、`JsonGenerator.Feature.WRITE_BIGDECIMAL_AS_PLAIN`、`SerializerFeature.WriteBigDecimalAsPlain`。

**兼容性**

- 属 **SPI 契约变更**：宿主自定义 `JsonOps` 不受影响（契约要求它自己也遵守）；直接调 `parse()` 并依赖返回 `Double` 的宿主代码受影响 → 进 CHANGELOG 的「破坏性变更」。
- 现有 TCK **不会红**：全库无 `Double.class`/`(Double)` 断言（已 grep 确认），数字断言均为 `((Number) v).doubleValue()`。
- `JacksonJsonOps(ObjectMapper)` 构造器已存在 → 宿主可自行决定 mapper 配置。

**性能**（实测，`Probe8`：40 个小数字段、20 万次解析/轮、4 轮）

| 配置 | 平均 |
|---|---|
| `Double`（默认） | 2.80 – 3.10 μs/op |
| `BigDecimal`（开 flag） | 2.29 – 2.53 μs/op |

未观察到回退。真实压测留到上线前，见 §8。

### 4.2 U2 · 新增 `cn.cj.ifmap.core.util.Values`：唯一的「值 → 报文形态」出口

**职责**：把 JDK 值规整成报文安全形态。它**不认识业务**，只做类型规整；所有把值转成文本的地方都必须走它，杜绝散落的 `String.valueOf`。

| 方法 | 语义 | 边界 |
|---|---|---|
| `static String stringify(Object v)` | 标量 → 文本。`BigDecimal`/`Double`/`Float` 走 `toPlainString()`；`Boolean` → `"true"/"false"`；`null` → `""`；其它 → `String.valueOf` | **遇到 `List`/`Map` 抛 `IllegalArgumentException`**（见下） |
| `static Object plainify(Object v)` | 递归规整：`BigDecimal` → 形态 plain 但 **scale 不变**的 `BigDecimal`；`List`/`Map` 递归；`null`/其它原样 | 不改类型 |
| `static BigDecimal toPlainDecimal(Number n)` | `BigDecimal` 原样返回；`Double`/`Float` 走 `BigDecimal.valueOf(double)`（**禁止** `new BigDecimal(double)`）；整型走 `new BigDecimal(long)` | 输入为 `null` 抛 `IllegalArgumentException` |

**为什么 `stringify` 对容器抛异常**：这正是 1.3 类脏数据的类型层封堵。调用方必须先想清「这个值要不要展开」，不允许静默 `List.toString()`。

**调用点收敛（本批只有 3 处）**

| 调用点 | 为什么安全 |
|---|---|
| `TemplateEngine.normalizePathValue` 叶子分支 | 已先判过「不是容器」 |
| `Coercions.coerce(src, String.class)` | `canCoerce` 已挡住容器（见 U4-A），进不来 |
| `StringRules.concat` | 调用前先做容器检查并按 `StrictTypes` 处理 |

**明确不做（避免范围失控）**：`Text.join`（`@concat@` / `@append@` / `listJoin` 的拼接出口）本批**不**改。理由：这两个中缀运算符声明的是「多值拼接」，`joinResolved` 明确对数组 `addAll` **展平**，展平是它声明的语义；而规则 `concat` 声明的是「多值拼接（null 按空串）」，**从未声明数组语义** —— 所以只有规则 `concat` 的容器泄漏构成缺陷。`Text.join` 对「元素是 Map」仍走 `String.valueOf` 的残留风险记入 §8 R7。

**依赖**：仅 JDK（`BigDecimal`、`Collection`）。**Java 8 兼容**（不用 `List.of` 等 9+ API）。

### 4.3 U3 · TemplateEngine：归一化与表达式切分

**改动点**

| 位置 | 现状 | 改后 |
|---|---|---|
| `normalizePathValue(Object)`（L458） | `Number \|\| Boolean` → `String.valueOf` | 叶子：`Values.stringify`；容器：`Values.plainify`（递归、类型不变） |
| `resolve()` 的 `@sum@` 分支（`return sum;` 在 L362） | `return sum`（`BigDecimal` → JSON number） | `return Values.stringify(sum)`（String，scale 不变 → D5） |
| `toDecimal(Object)`（L465） | `new BigDecimal(value.toString())`；失败 `warn` + `ZERO` | `Values.toPlainDecimal(number)`；失败按 `StrictTypes`（U4） |
| `Text.join`（L128） | `String.valueOf(item)` | `Values.stringify(item)` |
| `Coercions.coerce(src, String.class)` | `String.valueOf(src)` | `Values.stringify(src)` |
| `StringRules.concat`（L32） | `sb.append(part)` | `Values.stringify(part)` + 容器检测（U4） |

**切分逻辑抽出（结构性修复）**

现状 `TemplateEngine` 里 `split(valueKey, separator)`（私有）与 `splitTopLevel(inner)`（包私有 `static`）定义「一个表达式由哪些操作数组成」，而 `ConfigValidator` 用另一套正则识别路径 —— 两套逻辑就是 1.4 的根因。

新增 `cn.cj.ifmap.core.template.DslExpressions`（`final`、静态工具），把表达式语法集中到一处，**引擎与校验器共用**：

| 方法 | 语义 |
|---|---|
| `static boolean isFun(String)` / `static String funName(String)` | `@FUN(name,...)` 识别与取名 |
| `static List<String> funArgs(String)` | 顶层逗号切分（沿用现有 `splitTopLevel` 实现，含括号深度处理） |
| `static List<String> infixOperands(String, String token)` | 按 `@sum@`/`@and@`/`@or@`/`@concat@`/`@append@` 切分（沿用现有 `split` 实现，去 trim） |
| `static boolean hasInfix(String, String)` | 含中缀运算符 |
| `static boolean isLiteral(String)` | 非 `$.` 开头、非 `@FUN(`、非 `@seqNo`、不含中缀 → 字面量 |

`TemplateEngine` 的私有 `split`/`splitTopLevel` 改为委托 `DslExpressions`（行为不变，避免重复实现）。**本单元不改变任何既有渲染行为**，是纯抽取 —— 用回归测试保证。

**U3 渲染口径变化**（模板 `{"v":"..."}`）

| 源 | 改前（Jackson） | 改后（两实现一致） |
|---|---|---|
| `10.00` | `"10.0"` | `"10.00"` |
| `12345678.90` | `"1.23456789E7"` | `"12345678.90"` |
| `1.0E10` | `"1.0E10"` | `"10000000000"` |
| `0.100` | `"0.1"` | `"0.100"` |
| `-0.00` | `"-0.0"` | `"0.00"` |
| `[1.50,2.25]` | `[1.5,2.25]` | `[1.50,2.25]`（仍 number） |
| `$.amount@sum@$.m`（`10.00`,`5`） | `15.0`（number） | `"15.00"`（string） |

### 4.4 U4 · `StrictTypes`：静默失败改为可观测 + 可拒绝

**新增枚举 `cn.cj.ifmap.core.rule.StrictTypes`**

```java
public enum StrictTypes {
    WARN,   // 默认：保持既有行为，打 ERROR 日志（带字段路径），可观测
    FAIL    // 直接抛异常，附字段路径与替代写法
    ;
    public boolean failFast() { return this == FAIL; }
}
```

**注入方式（不做全局静态状态）**

| 入口 | 设计 |
|---|---|
| `IfmapEngine.Builder.strictTypes(StrictTypes)` | 默认 `WARN`；`IfmapEngine.createDefault()` = `WARN` |
| `TemplateEngine(JsonOps, RuleRegistry, NullPolicy, StrictTypes)` | 新增 4 参构造；**保留 3 参构造**（委托 `WARN`），宿主源码兼容 |
| `BuiltinRules.registerTo(RuleRegistry, StrictTypes)` | 新增 2 参重载；**保留 1 参重载**（委托 `WARN`） |
| `StringRules` 构造 | 新增 `StringRules(StrictTypes)`；**保留无参构造**（委托 `WARN`），其它 `*Rules` 不变 |
| Spring | `IfmapProperties.strictTypes`（字段，默认 `WARN`，relaxed binding 支持 `ifmap.strict-types=warn\|fail`），`IfmapAutoConfiguration` 透传给 Builder |

**三个失败点**

**U4-A · `concat` 收到容器实参**

- 触发：实参中存在 `List` 或 `Map`。
- `WARN`：保持旧行为（`List.toString()`），打 `ERROR` 日志 —— `模板字段 [x]：规则 [concat] 收到数组/对象实参，已按 List.toString() 拼接，输出将不是预期报文；数组请用 listJoin/dictValArray 或 @array 列转行`。
- `FAIL`：抛 `RuleArgumentException`，消息含规则名、参数下标、替代写法。

**修复范围精确等于一个规则。** 这一点已用代码确认，与初版设想不同：

`Coercions.canCoerce`（`Coercions.java:69-81`）**已经**挡住了「容器 → `String` 形参」，且注释就写着「只接受标量 -> String，避免把 List/Map 悄悄串化」：

```java
if (t == String.class) {
    return src instanceof CharSequence || src instanceof Number
            || src instanceof Boolean || src instanceof Character;
}
```

因此 `dictVal(List, ...)`、`numRound(List, ...)` 这类标量形参的规则**本来就**会因匹配失败而落到 `RuleRegistry.tryMapOverList` 逐元素映射（实测 `@FUN(numRound,$.a,2)` → `["1.00","2.00"]`）——`docs/02` §3.1 的承诺对它们成立。

漏网的只有 `concat`，原因是它的形参是 **`Object...`**，而 `canCoerce` 对 `Object` 一律返回 `true`（`Coercions.java:74`）：

```java
if (t == Object.class || t.isInstance(src)) {
    return true;
}
```

所以本单元**不需要改 `Coercions`**，只改 `StringRules.concat` 内部。

**已评估并否决的替代方案**：把 `concat` 形参收紧为 `CharSequence...`，让 `Coercions` 的既有防线生效。否决理由：`canCoerce(Number, CharSequence)` 为 false，而 `listOp` 返回 `Object`、`dictValArray` 返回 `List`，于是 `@FUN(concat,@FUN(listOp,$.a,max),$.x)` 这类写法会从「能用」变成「无匹配方法」——用一处行为破坏换一处静默泄漏，不划算。

**U4-B · `@sum@` 操作数非数值**

先划清边界：`toDecimal` 现在有**两条**返回 0 的路径，语义完全不同，不能混为一谈。

| 输入 | 现状 | 本批处置 |
|---|---|---|
| `null` / 空串（字段缺失、`$.missing`） | 静默 0（**连日志都没有**） | **保持 0，两种模式都不报**。理由：「缺失即 0」是求和表达式的常规用法，`$.a@sum@$.b` 里 b 偶发缺失是正常业务，`FAIL` 下报错会打断正常流程 |
| 非数值文本（`"abc"`）/ 容器 | `log.warn` + 0 | `WARN`：保持 0，日志升为 `ERROR`（含字段路径与原文）；`FAIL`：抛 `IfmapConfigException`（含字段路径与原始值） |

即：**只升级现在已经在告警的那一类**，不把「缺失」从静默改成报错。

**U4-C · 表达式操作数静态校验（部署前 / 保存前）**

- 位置：`TemplateScanner` 新增 `static List<String> expressionProblems(String templateJson)`，用 `DslExpressions` 走一遍模板里每个字符串值（含 `@array@$.path` 形态的 key），对每个多值表达式：
  - 每个操作数要么是 **`DslExpressions.isLiteral` 成立的字面量**，要么是**完整合法路径**（`jsonOps.isValidPath`）或是 `@FUN(`/`@seqNo`；
  - 操作数**不得再含中缀分隔符或逗号**（即 `@sum@$.a,$.b` 里 `$.a,$.b` 不是合法操作数）→ 报错。
- 挂载：`IfmapEngine.validateTemplate` 聚合 `registry.assertRulesExist(...)` 与 `expressionProblems(...)`。
- `StartupValidationException` 增加 `List<String> problems`（新增 3 参构造，保留 2 参构造）。`ContractValidator` 对每个 problem 产出一条 `ContractReport.Violation`（kind 沿用 request/response），于是**启动自检**与**管理端保存前校验**同时生效。
- 该开关**不受 `strict-types` 控制**：错语法永远拒绝（与历史上 `farmatDate` 拼写错误的处置口径一致 —— 错的东西不该能存进去）。

**U4 效果对照**

| 模板 | 改前 | 改后（FAIL） | 改后（WARN） |
|---|---|---|---|
| `@FUN(concat,$.a,$.b)` 两数组 | `"[01, 02][100, 200]"` | 抛 `RuleArgumentException` | 旧输出 + ERROR 日志 |
| `$.amount@sum@$.flag` | 静默 `10.0` | 抛 `IfmapConfigException` | 旧输出 + ERROR 日志 |
| `@sum@$.amount,$.amount` | Jackson `0` / fastjson 抛 | 保存/启动即被拒（两层都拒） | 同左 |

## 5. 兼容性与迁移

### 5.1 破坏性变更清单

| # | 变更 | 影响面 | 处置 |
|---|---|---|---|
| B-1 | `JsonOps.parse` 小数返回 `BigDecimal`（原 `Double`） | 直接依赖 `parse()` 返回类型的宿主代码 | CHANGELOG + `docs/05` 声明；引擎层已保证形态改善 |
| B-2 | `$.path` 小数形态变化（保 scale、去科学计数法） | **所有**报文内容；需银行/资方侧回归 | 逐接口回归 + 提供 §1.1 形式的形态对照清单 |
| B-3 | 数组/对象内数字由「原始形态」变为「plain 形态」 | 数组型报文 | 同上（类型不变，仅去科学计数法） |
| B-4 | `@sum@` 返回 String（原 JSON number） | 用了 `@sum@` 的模板 | `docs/02` 表达式总表更新；若目标侧要求 number，见 §8 开放问题 |
| B-5 | `concat` 遇容器：`warn` 保持旧行为 → 未来版本 `fail` 抛异常 | 存量 `@FUN(concat,$.arr)` 写法 | 两阶段灰度；warn 阶段靠 ERROR 日志盘点存量 |
| B-6 | `@sum@` 非数值操作数：`warn` 保持 0 → 未来 `fail` | 存量脏数据模板 | 同上 |
| B-7 | 表达式错语法（如 `@sum@$.a,$.b`）保存/启动即拒 | 存量脏配置 | **立即生效**（不灰度）；上线前必须先跑一次配置巡检 |
| B-8 | **影子（shadow）比对会因数字形态变化报出 diff** | 用了 shadow 模式的接口，在基线刷新前每条都会 diff | 属预期：先刷新影子基线，再上 `fail`；否则会被误读成逻辑回归 |

### 5.2 上线顺序

1. 先跑配置巡检（逐条走 `ConfigValidator`，或直接在预发环境跑一次启动自检）→ 收集 B-7 违规清单并修数据。
2. 部署 `strict-types=warn`，观察 B-5 / B-6 的 ERROR 日志，逐条确认是「存量本来就有问题」还是「本次改动引入」。
3. 报文形态变化（B-2 / B-3 / B-4）逐接口与对方核对。
4. 观察期结束 → `strict-types=fail`。

### 5.3 回滚

- 单开关回滚：`ifmap.strict-types=warn`（立即退回 B-5/B-6 的旧行为）。
- B-1/B-2/B-3 无开关：回滚需退版本（镜像回滚）；`JacksonJsonOps(ObjectMapper)` 可供宿主临时传一个不配 `USE_BIG_DECIMAL_FOR_FLOATS` 的 mapper 缓解。

## 6. 测试计划

沿用 TDD：先写红用例，再改实现。

### 6.1 TCK（`JsonOpsConformanceTestBase`，24 → 30 条，两实现各跑一遍）

| # | 用例 | 断言 |
|---|---|---|
| T1 | `parse` 小数保真 | `parse("{\"d\":10.00}")` 的 `d` 是 `BigDecimal` 且 `scale()==2` |
| T2 | `toJson` 保留 scale | `toJson(parse("{\"d\":10.00}"))` 的文本**逐字节**等于 `{"d":10.00}` |
| T3 | 科学计数法源文字 | `toJson(parse("{\"e\":1.0E10}"))` 不含 `E`，等于 `10000000000` |
| T4 | `BigDecimal("1E+10")` | `toJson` → `10000000000` |
| T5 | 大整数 / 前导零 | `BigInteger` 保真；`"0012345"` 仍是字符串形态 |
| T6 | 数组/嵌套内小数 | 保持 JSON number 且 plain：`{"items":[1.50,2.25]}` |

### 6.2 端到端（引擎层，两个实现共用同一张期望值表）

**“两实现逐字节相等”怎么落成可执行断言**：本仓没有任何模块同时依赖 jackson 与 fastjson（也不应为此引入：fastjson 1.2.84 会被依赖扫描器报 CVE，不能进别人的传播路径）。因此不写“单次跨实现对比”，而是把期望值写成**共享的硬字面量**，让同一张表在两个模块各跑一遍：

- 新增 `ifmap-json-tck/.../TemplateFidelityTestBase.java`（抽象基类，`protected abstract JsonOps jsonOps()`，与既有 `JsonOpsConformanceTestBase` 同一形态）。`ifmap-json-tck` 已依赖 `ifmap-core`（compile）与 JUnit（compile），**pom 无需改动**。
- 两个实现模块各加一个 5 行子类（照抄 `JacksonJsonOpsConformanceTest` 的形状）。
- 期望值写**具体字符串**（`"10.00"`），而不是 `doubleValue()` 比较。任一侧偏离即红。

断言内容：

- §4 的 U3 口径表 7 条逐条断言（期望值全是硬字面量）。
- `@sum@`：`$.amount@sum@$.m` → `"15.00"`；`1.5@sum@2.5` → `"4.0"`。
- 规则族回归：`@FUN(numRound,$.bigAmt,2)` → `"12345678.90"`、`@FUN(numSum,$.items)` → `"3.75"`、`@FUN(numFormat,...)` 与 `@FUN(strMask,...)` 输出不变。
- 数组/嵌套：`[1.50,2.25]` 仍是数组且元素是 number，文本形态 plain（不含 `E`）。

### 6.3 StrictTypes

| 用例 | WARN | FAIL |
|---|---|---|
| `concat` 两数组 | 输出旧值（`"[01, 02][100, 200]"`） | 抛 `RuleArgumentException`，消息含规则名与参数下标 |
| `concat` 单数组 | 输出旧值 | 同上 |
| `@sum@` 非数值文本（`"abc"`） | 按 0 求和 | 抛 `IfmapConfigException`，消息含字段路径与原始值 |
| `@sum@` 字段缺失 / 空串 / null | **两模式都按 0**（回归护栏：不得把「缺失」改成报错） | 同左 |
| 标量规则 + 数组实参 | 回归护栏：必须仍是逐元素映射（`@FUN(numRound,$.a,2)` → `["1.00","2.00"]`），修 `concat` 不得破坏它 | 同左 |
| `@sum@$.a,$.b` | 保存/启动即拒（不受开关影响） | 同左 |

**断言日志文本不在本批范围**：本仓刻意不引入任何日志实现（只有 `slf4j-api`，测试期连 provider 都没有 —— 跑测试会看到 `No SLF4J providers were found`）。为断言一句日志而引入 `logback-classic`（test 作用域）不划算，且断言日志文本本身脆弱。因此：

- `WARN` 态只断言**行为**（旧输出保持不变），可观测性靠生产环境日志交付；
- `FAIL` 态断言**异常类型 + 消息内容**（含字段路径/参数下标）—— 消息是给排障人看的，值得钉住。

**负例必须存在**：错语法（`@sum@$.a,$.b`）与「容器实参」两类都要有「必须被拦下」的断言 —— 历史上静默忽略的教训是「没有负例就等于没有校验」。

### 6.4 回归护栏

- `DslExpressions` 抽取是纯重构 → 抽取前后跑全量测试，行为零变化（先用现有测试作为安全网，再补 `DslExpressions` 自身的单测）。
- 双 JDK 构建：JDK 17 `clean verify` 全绿 + JDK 8 `clean verify` 全绿（Java 8 兼容是本批硬约束）。
- SpotBugs 0 缺陷（`effort=Max` / `threshold=Medium`，注意报告在 `<module>/target/spotbugsXml.xml`，口径 = `grep -c '<BugInstance '`）。
