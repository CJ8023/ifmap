## 1. 背景与问题

### 1.1 分支判定是「两条通道拼起来」的，且三处口径互不一致

`IfmapOrchestrator.matches`（`IfmapOrchestrator.java:567`）同时干两件事：

```java
if (logicBranches.matches(flag, context)) {                 // :569  通道①：@LogicBranch 策略命中
    return true;
}
if (value == null || judgement.getActualValue() == null) {   // :573
    return false;
}
for (String candidate : value.split("[;,]")) {               // :578
    if (candidate.trim().equalsIgnoreCase(judgement.getActualValue().trim())) {
        return true;                                         // 通道②：拿 value 比「判定值」
    }
}
```

**关键事实（它决定了本设计的形状）**：通道② 比的是 `result_judge` 抽出来的 `actualValue`，**不是** `logic_branch_flag` 指向的路径。也就是说 `logic_branch_flag` 在代码里**根本不是 JsonPath**，它只是通道① 的策略键。

但 DDL 与文档都把它写成了路径：

| 位置 | 现在的说法 |
| --- | --- |
| `002-create-logic-branch.sql:23` | `logic_branch_flag` … `COMMENT '逻辑分支标志（JsonPath 表达式，支持 $.a.b 与裸字段名）；空=兜底分支'` |
| `002-create-logic-branch.sql:24` | `logic_branch_value` … `COMMENT '逻辑分支判断值，多值以 \| 分隔'` |
| `docs/04-接入与建表.md:372` | 同上（「JsonPath」「多值以 `\|` 分隔」「空 = 兜底分支」） |
| `docs/10-迁移指南.md:218` | 「`logic_branch_flag` 空 = 兜底；`method_flag` 空 = 不执行动作」 |
| `docs/07-管理端REST.md:87,176` | 「`logic_branch_flag` 为空才是兜底分支」「默认兜底分支（flag/value 都空）最多 1 条」 |

三处不一致：

1. **`flag` 的语义**：文档说路径；代码当策略键（`LogicBranchStrategyRegistry.matches(String key, StrategyContext)`，`core/strategy/LogicBranchStrategyRegistry.java:66` → `LogicBranchStrategy.match(StrategyContext)`，`:30`）。
2. **多值分隔符**：DDL/文档说 `|`；代码按 `[;,]` 切（`:578`）—— 真值里有 `|` 时今天的行为是「与字面量 `a|b` 相等才命中」。
3. **比较口径**：代码是 `trim()` + `equalsIgnoreCase`；而 `result_judge` 的 `ignoreCase` **默认 false（严格）**（`docs/10:309`）。

存量配置正好落在「文档口径」上：`docs/12-被调接口配置指南.md` §4 的标准例子里 `flag=PAY_SUCCESS` / `value=SUCCESS` —— `PAY_SUCCESS` 显然不是 JsonPath，它只能靠通道② 命中。**任何「把 flag 当路径迁移」的方案都会静默改变行为**（`$.PAY_SUCCESS` 永远取不到值 → 常规分支全不命中 → 落到兜底 → 变成 `docs/12:213-217` 描述的「接到了但什么都没做」）。

### 1.2 判定已经是规格，分支是最后一处例外

`result_judge` 已按同一次改造收敛成一列 JSON 规格（`ResultJudgeSpec`，算子 `eq/ne/in/notIn/exists/notBlank/regex/always`，`MAX_DEPTH=3`，闭合算子集，fail-closed）。分支判定仍停在「两列 + 隐藏的两条通道」，于是同一个能力有两套写法、两套校验文案、两套文档口径 —— 这是本次要消灭的「同一件事两套做法」。

### 1.3 两个必须保住的既有语义

`LogicBranchConfig` 的 javadoc 把兜底定义在两个不同维度上，迁移时不能合并：

| 维度 | 语义 | 现有实现 |
| --- | --- | --- |
| `logic_branch_flag` **为空** | **兜底分支**：不参与常规匹配，只在所有常规分支都未命中时生效；排第一条也不抢命中；每接口最多 1 条 | `applyBranch` 两趟：先挑出兜底，常规遍历完再试兜底（`:522-556`） |
| `method_flag` **为空** | **该分支不执行任何动作**（只做匹配，不改状态） | `executeBranch`（`:558`） |

`docs/10:220-221` 专门警告过「别把 `method_flag` 空也当成兜底」。两者在新设计里必须分别在规格（`{"op":"always"}`）与 `method_flag` 空上表达，不能混。

### 1.4 为什么求值根必须是「对方原文」，不能是「已渲染产物」

唯一一处"看起来更自然"的替代方案是拿**已渲染产物** `responseData` 当根（"分支判断的是我们要回的东西"）。它被三份证据否掉：

1. `docs/12` §4 的标准 INBOUND 例子：`result_judge` 用 `{"any":[{"path":"$.noticeStatus","op":"eq","value":"SUCCESS"}, …]}`，而 `response_param_template` 是 `{"code":"0000","message":"success","applyNo":"$.applyNo","ackNo":"$.seqNo"}` —— **ACK 骨架里根本没有 `noticeStatus`**。产物根下 `$.noticeStatus` 取不到 ⇒ 常规分支永不命中 ⇒ 每次都走兜底。
2. 要救只能往给对方的 ACK 里塞判定字段（`"noticeStatus":"$.noticeStatus"`）—— **语义错误**：ACK 是回给对方的应答，不是内部判定结果的容器。
3. `response_param_template` 为空时 `renderResponse` 返回空 Map（大量存量接口如此）⇒ 产物根本没有任何字段。而此时判定走原文、分支走产物，等于**同一个接口两套求值根**。

所以：**分支规格与 `result_judge` 共用同一个根、同一个 `JsonReadContext`**。OUTBOUND 时是对方响应原文；INBOUND 时是对方请求报文原文（与 `result_judge` 完全同源）—— 这才是"改成和 `result_judge` 一样"。

## 2. 目标与非目标

**目标**

1. `ifmap_logic_branch_config` 只留一列 `branch_judge`，语法、算子、深度、失败语义与 `result_judge` **同一份实现**（不是"类似"）。
2. 存量 `(flag, value)` 数据能**机械 1:1 迁移**，并给出等价性论证与可执行的回填 SQL。
3. 兜底（`always`）与「不执行动作」（`method_flag` 空）两个维度都保住。
4. 非法规格在保存期被拒（422），在运行期 fail-closed（不静默落到兜底）。

**非目标**

1. 不动 INBOUND/OUTBOUND 的方向分叉（`executeInbound`）、不合并两条执行路径。
2. 不做 `branch_judge_name`（分支判定器可插拔）—— 需要自定义逻辑就写 `@LogicBranch` 策略，用 `strategy` 算子挂上。
3. 不做每分支独立的应答模板、分支级重试/告警。
4. 不新增数值比较算子（`>`/`<`）—— 同样走 `@LogicBranch`。**一次只解决"两套口径"这一件事。**

## 4. 设计

### 4.1 数据模型

```sql
-- 008-logic-branch-judge.sql（Liquibase + starter 自动 DDL 共用）
ALTER TABLE `${tablePrefix}logic_branch_config`
    ADD COLUMN `branch_judge` text NOT NULL
    COMMENT '分支判定规格（JSON；必填，无默认值 ⇒ 未配置即失败）';

-- 010-logic-branch-drop-legacy.sql（可裁剪：共存期跳过本文件即可）
ALTER TABLE `${tablePrefix}logic_branch_config` DROP COLUMN `logic_branch_flag`;
ALTER TABLE `${tablePrefix}logic_branch_config` DROP COLUMN `logic_branch_value`;
```

列数 **17 → 16**（−2 +1）。唯一键 `uk_…_logic_branch (tenant_id, interface_no, method_flag, logic_branch_name, deleted_seq)` **不含 flag/value**，删列不影响索引（已核对 `002-create-logic-branch.sql`）。

`008` 与 005 同一条风险：**非空表 + `text NOT NULL` 无默认值**在严格模式下可能报 1364/1138。处置顺序（同 005 注释）：

1. 先按可空列加：`ALTER TABLE … ADD COLUMN branch_judge text;`
2. 跑 `009` 回填（见 §4.5）；
3. 收紧：`ALTER TABLE … MODIFY COLUMN branch_judge text NOT NULL;`
4. **把 `008` 标记为已执行**（`liquibase changelog-sync`），否则下次启动会重复 `ADD COLUMN` 报 1060。

保留列（不删，属于本设计之外）：

| 列 | 保留理由 |
| --- | --- |
| `logic_branch_order` | 常规分支的求值顺序，语义不变 |
| `logic_branch_name` | 唯一键成员 + 新的 `matchedBranch` 取值 |
| `method_flag` | 动作 key，语义收窄为「空 = 不执行动作」 |

### 4.2 规格语法

顶层与 `result_judge` **逐字相同**：

| 写法 | 含义 |
| --- | --- |
| `{"op":"always"}` | 无条件命中（= 兜底分支）。每接口最多 1 条 |
| `{"all":[<c1>,<c2>,…]}` | 全部满足（非空） |
| `{"any":[<c1>,<c2>,…]}` | 任一满足（非空） |

叶子条件：

| 算子 | 形状 | 语义 |
| --- | --- | --- |
| `eq` / `ne` | `{"path":"$.a","op":"eq","value":"x","ignoreCase":true}` | 与 `result_judge` 完全一致（`ne`/`notIn` 在取不到值时视为成立，`exists` 只看有无） |
| `in` / `notIn` | `{"path":"$.a","op":"in","value":["x","y"]}` | 同上 |
| `exists` / `notBlank` / `regex` | `{"path":"$.a","op":"exists"}` | 同上 |
| **`strategy`** | `{"op":"strategy","value":"PAY_SUCCESS"}` | 交给 `LogicBranchStrategyRegistry.matches("PAY_SUCCESS", ctx)`；**无 path** |
| **`judged`** | `{"op":"judged","value":["SUCCESS","FAILED"],"ignoreCase":true}` | 与 `result_judge` 的 `actualValue` 比较；**无 path** |

`strategy` / `judged` 是**分支专用**：`result_judge` 里出现它们要报错「strategy/judged 是分支专用算子」，否则会出现「结果判定里引用了自己的判定结果」这类循环语义。

`judged` 的取值口径必须写进文档：**`result_judge` 里第一条命中条件取到的值**（`docs/12` §6 已说明 `actualValue` 只记第一条命中）。多路径 `any` 时它是有序的，这点沿用现状。

例子（`docs/12` §4 改写前后）：

| 分支 | 旧（两列） | 新（一列） |
| --- | --- | --- |
| 支付成功 | `flag=PAY_SUCCESS` `value=SUCCESS` | `{"any":[{"op":"strategy","value":"PAY_SUCCESS"},{"op":"judged","value":["SUCCESS"],"ignoreCase":true}]}` |
| 支付失败 | `flag=PAY_FAILED` `value=FAILED` | `{"any":[{"op":"strategy","value":"PAY_FAILED"},{"op":"judged","value":["FAILED"],"ignoreCase":true}]}` |
| 兜底 | `flag=''` `value=''` | `{"op":"always"}` |
| 按原文路径分流（**新能力**） | 做不到（只能比判定值） | `{"all":[{"path":"$.noticeStatus","op":"eq","value":"SUCCESS"}]}` |

### 4.3 解析器改造（`core`）

```
judgement/JudgeOp.java
  + STRATEGY, JUDGED
  + requiresPath()            // STRATEGY/JUDGED 返回 false
  + fromName(...)             // 同步认 "strategy"/"judged"
judgement/JudgeCondition.java
  ~ path 允许为 null（仅当 !op.requiresPath()）
judgement/ResultJudgeSpec.java
  + compile(spec, jsonOps, EnumSet<JudgeOp> allowed)  // 一次解析：返回 {errors, tree}
  ~ validate(...) / parse(...) 变成 compile 的薄封装（行为不变）
  ~ 叶子解析：!requiresPath() 时不再要求 path，也不再做 isValidPath
orchestrator/branch/BranchJudgeSpec.java（新）
  ~ 是对 ResultJudgeSpec 的**薄门面**：allowedOps = 7 + {STRATEGY, JUDGED}
  + compile(raw, jsonOps) / isAlways(raw) / evaluate(ctx, judgeInfo)
orchestrator/branch/BranchJudge.java（新）
  ~ 持有 JsonOps + LogicBranchStrategyRegistry + 有界 LRU（键 = 规格原文，容量 1024，满则清）
  + matches(LogicBranchConfig, JsonReadContext, Judgement, StrategyContext): boolean
  ~ 求值分派：STRATEGY → registry.matches(key, sc)；JUDGED → judgement.getActualValue()；其余 → ctx
```

三个实现要点：

1. **`compile` 一次解析**。现状 `validate()` + `parse()` 会把同一份文本解析两遍；分支是热路径，合并成一个 `compile` 后 `validate`/`parse` 只是它的投影。公开 API 与报错文案保持不变（`ResultJudgeSpec` 现有 12 个用例必须全绿）。
2. **绝不抛异常**。`RuleSpecJudge` 的契约是"规格非法 → 返回失败 Judgement，不抛"；分支沿用：解析失败只产生 errors，由调用方决定怎么失败。
3. **`strategy` 的执行异常照旧上抛**。`LogicBranchStrategy` 内部抛 `IfmapStrategyException` 是宿主自己的错误，不能被规格解析吞掉（与现有 `matches` 行为一致）。

### 4.4 运行期

#### 4.4.1 求值根

`executeOne` 里每次调用**只建一个** `JsonReadContext`（`jsonOps.readContext(response)`），判定与分支共用。INBOUND 分支用对方请求报文原文，与 `executeInbound` 里的判定完全同源。

**响应不是 JSON 时**（`result_judge` 为 `always` 的接口可能出现）：`readContext` 失败 → ctx 为 `null` → 含 `path` 的叶子一律按"取不到值"求值（`eq/in/exists/notBlank/regex` 不命中，`ne/notIn` 命中）+ 一条 WARN；`strategy`/`judged` 叶子不受影响。**不因为分支配置把一次成功的调用判成失败**（与今天 `getActualValue()==null` 时返回 false 同口径）。

#### 4.4.2 两趟匹配（顺序无关的兜底）

保持 `applyBranch` 现有结构（`:522-556`）：第一趟跳过 `{"op":"always"}` 的行按 `logic_branch_order` 升序求值，第一趟全不命中再取**顺序最靠前的那条 `always`**。多写了几条 `always`（绕过 admin 直改库）时取第一条 + WARN，不抛。

#### 4.4.3 fail-closed 的落点

现状：`errorMessage` 只由判定决定（`executeOne:268-272` 附近 `judgement.isSuccess() ? null : failureMessage(judgement)`），分支失败没有出口。改法：

```
Judgement.Stage + BRANCH
JudgeFailType.SPEC_INVALID（复用，不新造）
Judgement#asBranchFailure(String reason)   // 复制并改写 success/stage/failType，保留 httpStatus/trackId/message/actualValue
BranchOutcome applyBranch(...)             // { matchedName, Judgement failure } 二者互斥
```

`executeOne` 的日志与返回值统一走一个 `effective` Judgement：

| 场景 | `execution_result` | `fail_type` | `error_msg` | `matchedBranch` |
| --- | --- | --- | --- | --- |
| 判定成功 + 分支正常 | SUCCESS | — | null | 命中的 `logic_branch_name` 或 null |
| 判定成功 + 某条规格非法 | **FAIL** | **SPEC_INVALID** | 「分支规格非法：<分支名>：<首条错误>」 | null |
| 判定失败 | FAIL | 判定自己的 | 判定原因 | null（与今天一致：判定失败不评分支） |

规格非法时**一条分支都不试**（不是"跳过这条试下一条"）—— 前者是配置错误、必须暴露；后者会让错误配置"看起来能用"。

#### 4.4.4 动作与 `matchedBranch`

| 项 | 新口径 |
| --- | --- |
| 动作 key | 只用 `method_flag`；空 = 不执行动作（D12） |
| `method_flag` 非空但未注册 | 沿用 `ActionRegistry.failOnMissingAction` |
| `IfmapResult.matchedBranch` / 日志「命中分支」 | `logic_branch_name`（D13） |

`IfmapResult.matchedBranch` 的 javadoc、`LogicBranchConfig`、`LogicBranch`/`LogicBranchStrategy` 的注释要同步（现在写的是"分支标识"= flag）。

### 4.5 迁移映射与等价性

#### 4.5.1 映射表

| 旧数据 | 新规格 | 等价性 |
| --- | --- | --- |
| `flag=''`，`value` 任意 | `{"op":"always"}` | 今天 `applyBranch` 只按 `flag` 判兜底，`value` 不参与 ⇒ 兜底语义一致（这类行现在 admin 会报「配了 value 却没 flag」，属于脏数据，迁移时顺带暴露） |
| `flag` 有值，`value=''` | `{"any":[{"op":"strategy","value":"<flag>"}]}` | 今天只走通道① |
| `flag` 有值，`value` 有值 | `{"any":[{"op":"strategy","value":"<flag>"},{"op":"judged","value":[…],"ignoreCase":true}]}` | 今天 `matches` = 通道① `OR` 通道②，`any` 正好是 `OR` |

`ignoreCase:true` 不能省：旧比较是 `equalsIgnoreCase`（`:578`）。**已声明的偏差**：旧实现会对两边 `trim()`，新实现不 trim —— 只有"判定值带首尾空白"时才不同，可在巡检里查（`actualValue` 由 `RuleSpecJudge` 产出，通常已 trim）。

#### 4.5.2 回填 SQL（`009`，Liquibase 执行；kit 版见 §4.9）

```sql
-- group_concat 默认 1024 字节，12 个 512 字符的值会截断，必须先放宽
SET SESSION group_concat_max_len = 8192;

-- ① flag 空（含 flag/value 皆空）= 兜底
UPDATE `${tablePrefix}logic_branch_config`
   SET `branch_judge` = '{"op":"always"}'
 WHERE COALESCE(`branch_judge`, '') = ''
   AND TRIM(COALESCE(`logic_branch_flag`, '')) = '';

-- ② 只有策略键
UPDATE `${tablePrefix}logic_branch_config`
   SET `branch_judge` = CONCAT('{"any":[{"op":"strategy","value":', JSON_QUOTE(TRIM(`logic_branch_flag`)), '}]}')
 WHERE COALESCE(`branch_judge`, '') = ''
   AND TRIM(COALESCE(`logic_branch_flag`, '')) <> ''
   AND TRIM(COALESCE(`logic_branch_value`, '')) = '';

-- ③ 策略键 + 判定值（value 按 [;,] 切分，与引擎 split 口径一致；按序号展开成 JSON 数组）
UPDATE `${tablePrefix}logic_branch_config` b
  JOIN (
        SELECT src.`key_id`,
               GROUP_CONCAT(JSON_QUOTE(TRIM(src.`part`)) ORDER BY src.`n` SEPARATOR ',') AS `vals`
          FROM (
                SELECT c.`key_id`, n.n,
                       SUBSTRING_INDEX(SUBSTRING_INDEX(REPLACE(c.`logic_branch_value`, ',', ';'),
                                                       ';', n.n), ';', -1) AS `part`
                  FROM `${tablePrefix}logic_branch_config` c
                  JOIN (SELECT 1 AS n UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
                        UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8
                        UNION ALL SELECT 9 UNION ALL SELECT 10 UNION ALL SELECT 11 UNION ALL SELECT 12) n
                    ON n.n <= 1 + CHAR_LENGTH(REPLACE(c.`logic_branch_value`, ',', ';'))
                                - CHAR_LENGTH(REPLACE(REPLACE(c.`logic_branch_value`, ',', ';'), ';', ''))
                 WHERE COALESCE(c.`branch_judge`, '') = ''
                   AND TRIM(COALESCE(c.`logic_branch_flag`, '')) <> ''
                   AND TRIM(COALESCE(c.`logic_branch_value`, '')) <> ''
               ) src
         WHERE TRIM(src.`part`) <> ''
         GROUP BY src.`key_id`
       ) v ON v.`key_id` = b.`key_id`
   SET b.`branch_judge` = CONCAT('{"any":[{"op":"strategy","value":', JSON_QUOTE(TRIM(b.`logic_branch_flag`)),
                                 '},{"op":"judged","value":[', v.`vals`, '],"ignoreCase":true}]}');
```

三条语句都用 `WHERE COALESCE(branch_judge,'') = ''` 保证**可重跑**（半途失败可续跑）。

硬约束：`value` 的**值个数 ≤ 12**（`n` 的展开上限）。超过的会在回填时被**静默截断**，所以 `00-precheck` 必须加一条前置断言把这类行查出来（§4.9），人工拆开后再跑。

#### 4.5.3 等价性怎么证

不是"读一遍 SQL 觉得对"，而是**双跑对照**：

- 新增 `LegacyBranchEquivalenceTest`（`core` 测试）：把旧 `matches()` 的语义原样复制成一个测试内 `LegacyMatcher`（禁止直接调用生产代码），再用一张参数表跑两个实现：
  `(flag, value) × (strategy 命中/不命中) × (actualValue: null / 'SUCCESS' / 'success' / ' SUCCESS ' / 'FAILED' / 'a|b')`，
  断言**两边结果逐格相同**；唯一允许不同的格子是 `actualValue=' SUCCESS '`（trim 偏差），显式列在"已声明偏差"集合里。
- 回填 SQL 的正确性由 `05-verify.sql` 反向核对（§4.9），并在一套真实存量数据副本上演练（`docs/10 §4` 的演练纪律）。

### 4.10 与 INBOUND 的关系

- 分支规格的根 = 判定用的那份原文（OUTBOUND = 对方响应；INBOUND = 对方请求报文），因此**本设计对两个方向同时生效且不需要额外分支**。
- INBOUND 标准场景（`docs/12` §4）在改造后**表达能力变强**：可以直接写 `{"all":[{"path":"$.noticeStatus","op":"eq","value":"SUCCESS"}]}`，不必再让 `result_judge` 与分支共享"判定值"这一条间接路径。
- 已落地的 INBOUND 执行路径（`14810b8 feat(core): 引擎支持被调方向执行路径`）与本设计**无冲突**：本设计只替换 `applyBranch` 内部的匹配函数，与"原文从哪来"无关。

## 7. 风险与回滚

| 风险 | 级别 | 处置 |
| --- | --- | --- |
| 回填 SQL 截断 >12 个值 | 中 | `00-precheck` 前置断言；`05-verify` 反向核对值个数 |
| 存量脏数据（`flag` 空但 `value` 非空）被迁成 `always` | 低 | 语义与今天一致；巡检会报"规格与旧配置矛盾"，由人清理 |
| trim 偏差（判定值带首尾空白） | 低 | 已声明；巡检可查 |
| 自动 DDL 用户拿到空 `branch_judge` | **高** | fail-closed + 日志/WARN 指向 `docs/10 §7` + 巡检 error。**这是有意选择**：静默当兜底会让所有流量走错分支 |
| `008` 手工三步骤后 Liquibase 重复执行（1060） | 中 | 文档写明 `changelog-sync`；`docs/10` 步骤里给出命令 |
| 宿主自定义 `LogicBranchStrategy` 依赖 `flag` 是路径 | 中 | `strategy` 算子原样传 key；`CHANGELOG` 标 **BREAKING** 并给迁移对照表 |

**回滚**：`010` 不执行即保留两旧列（共存期标准动作）；代码回滚到上一版本时旧列仍在，`branch_judge` 只是多出来的一列（旧代码不读它）—— 但**回填过的 `branch_judge` 不会丢**，重新升级仍是幂等的。

## 9. 评审检查点（自查清单）

1. **等价性**：`LegacyBranchEquivalenceTest` 的"已声明偏差"集合是否**只有** trim 一条？
