# 08 · 日志与合规

> 前情：[`06-执行编排与策略扩展.md`](06-执行编排与策略扩展.md)（编排器与执行日志的写入时机）。
> 本文对应设计 §6.4（保留期清理）与 §7.5（脱敏）—— 把"接口报文落库"这件事做合规：**该脱的脱、该截的截、该删的删、写日志失败不许拖垮业务**。

## 1. 落什么、不落什么

`ifmap_execution_log`（17 列）每次调用落一行：接口编号、业务 ID、请求/响应报文、耗时、结果、失败原因。

| 合规项 | 做法 | 由谁负责 |
|---|---|---|
| 报文脱敏 | 值形态 + 字段名两套规则（§2） | 引擎（`ifmap.log.mask-fields` / `exclude-fields`） |
| 超长截断 | 超过阈值截断并标 `...truncated`（§3） | 引擎（`ifmap.log.truncate-threshold`） |
| 无限增长 | 保留期 + 分批删除（§5） | `JdbcExecutionLogCleaner` + 定时任务 |
| 加密（国密 / SM） | **不做** —— 属业务语义，宿主机应自定义 `LogMasker` 或 `ExecutionLogSink` | 宿主 |
| 敏感字段不落库 | 字段名整列替换为 `***`（连长度都不留） | 引擎（`ifmap.log.exclude-fields`） |
| 日志与配置分库 | 两个 SPI 相互独立（`ConfigRepository` / `ExecutionLogSink`），同库异库都行；接法见 [`docs/05`](05-SpringBoot集成.md) §3.5 | 宿主 |
| 日志写回远端服务 | 用 `ifmap-provider-remote` 的远端仓储（`POST /insert_log`），见 [`docs/11`](11-远端配置源.md) §5 | 宿主 |

> 三个开关的语义边界：`ifmap.log.enabled=false` → **完全不写**执行日志（合规要求不落库时用这个）；`exclude-fields` → 写，但某些字段只留 `***`（`request_param` 本身是结构化 JSON，值被脱敏后仍可排查问题）；`clean-enabled=false` → 写，但**不自动删**（自己安排归档）。

## 2. 脱敏（`LogMasker` SPI）

```java
public interface LogMasker {
    String mask(String json);   // 入参/返回都是 JSON 文本；非 JSON 文本也必须安全处理
}
```

默认实现 `DefaultLogMasker`，两套规则同时生效：

| 形态 | 规则 | 例 |
|---|---|---|
| **值形态**（不依赖字段名，兜底） | 手机号 `1[3-9]\d{9}` → 保留前 3 后 4 | `13812348888` → `138****8888` |
| | 身份证 `\d{17}[0-9Xx]` → 保留前 6 后 4 | `110101199001011234` → `110101********1234` |
| | 银行卡 `\d{13,19}` → 保留前 6 后 4 | `6222021234567890` → `622202******7890` |
| **字段名**（`ifmap.log.mask-fields`） | 姓名类字段按其字段名脱敏：保留首字符其余打 `*` | `"acctName":"张三"` → `"acctName":"张*"` |

默认字段集（**只有姓名类 8 个**）：`acctName`、`accountName`、`certName`、`userName`、`realName`、`legalName`、`legalPerson`、`contactName`。

> 为什么手机/证件/卡号**不**放默认字段集：它们已经有值形态正则兜底，放进字段集反而会用"姓名规则"把它们整体打成 `1**********`（既没信息量又不满足"保留前后几位"的合规惯例）。要用字段名规则，配 `ifmap.log.mask-fields`。

要点：

- **幂等**：`mask(mask(x)) == mask(x)`（重复脱敏不会二次打星）。
- **非 JSON 安全**：报文不是合法 JSON 时按文本做值形态脱敏，不抛异常、不丢内容。
- **排除字段**：`ifmap.log.exclude-fields` 里的字段**整体**替换为 `***`（连长度都不落库），优先于脱敏规则。
- **大小写不敏感**：字段名比较统一转小写（配 `acctname` 与 `acctName` 等价）。
- 留空 `mask-fields` 会用**默认集**而不是"关闭脱敏"；要完全关闭请自定义 `LogMasker` bean（声明同类型 bean 即接管，starter 自动退让）。

## 3. 截断

| 配置 | 默认 | 说明 |
|---|---|---|
| `ifmap.log.truncate-threshold` | `65536`（64 KB） | 单个字段上限（**字符数**）；超过则截断并追加 `...truncated`；`<= 0` 表示不截断 |

截断发生在**脱敏之后**（先脱敏再截断），因此不会出现"脱敏只做了一半"的中间态。超长报文改由 `response_param`（`mediumtext`，上限 16 MB）承载；宿主机若必须留全量报文，请自定义 `ExecutionLogSink` 走对象存储。

## 4. 写日志失败要降级，不能拖垮业务

| 场景 | 行为 |
|---|---|
| 写日志抛异常（表不存在、连接池满、字段超长……） | 编排器 `WARN` 记录后**继续返回业务结果**（设计 §7.6 的行为修正） |
| 想异步 / 写别的库 / 写 MQ | 自定义 `ExecutionLogSink` bean（默认 `RepositoryExecutionLogSink` 委托 `ConfigRepository#saveExecutionLog`）；日志库与配置库分离的完整示例见 [`docs/05`](05-SpringBoot集成.md) §3.5 |
| 日志库连不上，业务会失败吗 | 不会：只 `WARN`。注意日志库与配置库分离时**不要**为此回落到配置库（[`docs/05`](05-SpringBoot集成.md) §3.5 的测试用例专门钉了这一点） |
| 日志内容要额外加解密 | 在自定义 `LogMasker` 或 `ExecutionLogSink` 里做 |

## 5. 保留期清理（设计 §6.4 方案 A）

用 starter 时**默认开启**：每天 03:30 按保留期分批删除过期日志。

**不依赖 `@EnableScheduling`**：starter 用自带**守护线程**的单线程调度器（`IfmapLogCleanScheduler`）驱动，
不会打开宿主的全局调度设施，也不会让"跑完就该退出"的非 Web / 批处理应用卡住不退出（`main()` 返回后
JVM 正常退出 —— 本仓库 `ifmap-demo-spring-boot3` 的 `java -jar` 实测 exit=0）。

| 配置 | 默认 | 说明 |
|---|---|---|
| `ifmap.log.clean-enabled` | `true` | 是否开启**定时**清理（关掉后清理器 bean 仍在，可手工调用） |
| `ifmap.log.retention-days` | `90` | 保留天数，**必须 &ge; 1**（配 0 会退化成"删全表"，直接拒绝执行） |
| `ifmap.log.clean-batch-size` | `1000` | 每批删除行数（一条 DELETE 即一个事务，批太大 → 大事务 + 主从延迟） |
| `ifmap.log.clean-max-batches` | `1000` | 单次任务最多批数（护栏；没删完的留给下个周期） |
| `ifmap.log.clean-batch-sleep-millis` | `50` | 批间停顿（给从库追 binlog 留时间） |
| `ifmap.log.clean-cron` | `0 30 3 * * ?` | 调度表达式（**6 段** Spring cron：秒 分 时 日 月 周，不含年）；**非法表达式启动期就失败**，不会静默忽略 |

> 要把清理交给宿主自己的调度体系（xxl-job / ShedLock / 分布式选举，保证集群里只有一个节点删）：
> 设 `ifmap.log.clean-enabled=false`，用你自己的任务调 `IfmapLogCleanTask#cleanNow()`。

手工触发（运维窗口/补跑）：

```java
@Autowired IfmapLogCleanTask task;
long deleted = task.cleanNow();   // 返回删除行数；失败返回 -1（已 WARN，不抛异常）
```

纯 Java（无 Spring）也能用：

```java
JdbcExecutionLogCleaner cleaner = new JdbcExecutionLogCleaner(dataSource);   // 或 (dataSource, "bankint_")
long deleted = cleaner.clean(90, 1000, 1000, 50L);
```

实现细节（决定了它为什么安全）：

- **先查 `key_id` 再按 id 删**，不用 `DELETE ... LIMIT`：后者是 MySQL 方言（H2 不认），而 `DELETE ... WHERE key_id IN (SELECT ... LIMIT)` 在 MySQL 上会报 1093（不能在子查询里读同一张被删的表）。两步走两个库都合法，单测因此能用 H2 跑真实生产 DDL。
- **单线程、按批、批间 sleep**：避免一次性产生巨大 binlog 事件把从库拖住。
- **中断安全**：线程被中断时停止本轮（保留中断标记），下个周期继续。
- **表名前缀生效**：复用存量表（`ifmap.table-prefix: bankint_`）时清理的也是 `bankint_execution_log`。
- **调度用守护线程 + 上下文关闭即停**：不阻塞 JVM 退出；避免短暂停机时任务与关库竞争。

### 5.1 三种保留策略怎么选

| 方案 | 代价 | 状态 |
|---|---|---|
| A. 保留期分批删除 | 后台任务 + 需要预留删除时间窗；DELETE 产生 undo/binlog，空间不立即回收 | ✅ 默认（ADR-10） |
| B. 按月分区 + `DROP PARTITION` | 分区列必须进主键（主键要改成 `(key_id, add_time)`）+ 重建表（全表 COPY）+ 每月补分区 | ✅ 提供完整运维手册，**默认不启用**（见 5.2） |
| C. 冷热分离（归档冷表） | 多一张表 + 多一个归档任务；跨表搬迁不是事务性的（用可重入设计代替） | ✅ 提供 `JdbcExecutionLogArchiver` + 建表脚本，**默认不启用**（见 5.3） |

理由：开源产品应"装完就能用"，不该强制用户先做一套分区运维改造；日志量不到千万级时方案 A 足够
（把 `clean-batch-size` 调到 500~1000、批间 sleep 50ms 是安全默认值）。
确实需要"按月秒级回收"或"留 5 年但业务只查近 3 个月"时再切 B / C —— **`DROP PARTITION` 比 `DELETE`
快几个数量级**，且不产生删除 binlog，主从延迟几乎为零。

### 5.2 方案 B：按月分区（可选手册）

完整可执行手册（6 步，含体检/改造/每月加分区/校验/归档/回收，以及变更单模板）在
`ifmap-provider-jdbc/src/main/resources/db/optional/execution-log-partition/`（随 jar 发布，看该目录的 `README.md`）：

| 步骤 | 文件 | 作用 |
|---|---|---|
| 0 | `00-precheck.sql` | 只读体检：表体量、月度分布、主键/索引、外键/触发器、是否已是分区表 |
| 1 | `01-partition-hot.sql` | 热表改造成按月 `RANGE(TO_DAYS(add_time))` 分区（**重建表**，唯一"重"的一步） |
| 2 | `02-add-monthly-partition.sql` | 每月加下月分区（用 `REORGANIZE` 拆 `pmax`） |
| 3 | `03-verify.sql` | 校验分区清单、`pmax` 为空、主键、分区裁剪、对账 |
| 4 | `04-create-archive-table.sql` | 建归档冷表 `ifmap_execution_log_archive` |
| 5 | `05-archive-and-drop.sql` | 归档 + 回收（Java 归档器 / 裸 SQL / `DROP PARTITION`） |

三个最容易踩的点（手册里有详细处置）：

1. **必须保留 `pmax VALUES LESS THAN MAXVALUE` 兜底分区**：没有它，插入超出边界的时间会报
   `1526 Table has no partition for value`，日志写入直接失败。
2. **有 `pmax` 时不能用 `ADD PARTITION`**（报 `VALUES LESS THAN value must be strictly increasing`），
   必须 `REORGANIZE PARTITION pmax INTO (...)`；且要在月初之前加好（数据落进 `pmax` 后拆它就要 COPY 数据）。
3. **改分区 = 重建表**：MySQL（5.7/8.0）不支持在线改分区/主键，停写窗口走手工流程，
   不能停写就用 `pt-online-schema-change`（必须显式写
   `DROP PRIMARY KEY, ADD PRIMARY KEY (key_id, add_time)` 与分区子句，否则报 1503）。

### 5.3 方案 C：冷热分离（归档冷表）

适用："留 5 年但业务只查近 3 个月"。把过期日志搬到冷表 `ifmap_execution_log_archive`
（结构与热表逐列一致，多一列 `archive_time`；`add_time` 保留**原业务时间**，不改成归档时间）。

```java
// 纯 Java（无 Spring 也能用）；表前缀复用存量表时传 "bankint_"
JdbcExecutionLogArchiver archiver = new JdbcExecutionLogArchiver(dataSource, "ifmap_");
LogArchiveResult result = archiver.archive(180, 1000, 1000, 50L);
// 180 天以前的数据算冷数据、每批 1000 行、单次最多 1000 批、批间停顿 50ms
long archived = result.getArchived();   // 写入冷表行数
long removed  = result.getRemoved();    // 从热表删除行数（= 真正搬到冷表的行数）
int  batches  = result.getBatches();
```

**不自动调度**（与方案 B 的分区 DDL 同口径：归档改变数据留存形态，属于运维决策）。放进宿主自己的调度体系：

```java
// 每天 04:10 归档一次；多实例部署务必加分布式锁/ShedLock —— 同一时刻只能有一个实例在跑
@Scheduled(cron = "0 10 4 * * ?")
public void archiveJob() {
    archiver.archive(180, 1000, 1000, 50L);
}
```

三条有意为之的设计（都有单测守着，见「本模块测试表」）：

- **可重入**：先 `INSERT` 后 `DELETE`（两条语句各自提交）。若在中间进程被杀，数据会同时留在两张表；
  下次重跑时"冷表已有"的行被跳过、热表照删 —— 结果仍然正确。因此**不**用跨表事务，
  避免把大批量搬迁变成大事务（binlog 暴涨 + 主从延迟 + 长锁）。
- **列清单写死并自检**：归档显式列出 17 个列（不用 `SELECT *`，列序漂移会静默错位）；
  执行前核对热表实际列与内置清单**完全一致** —— 将来给执行日志表加列却忘了同步归档器会**直接失败**，
  而不是悄悄少归档一列。
- **失败信息可执行**：冷表不存在 → 提示"请先执行 `04-create-archive-table.sql`"；冷表缺列 → 列出缺哪些列。

并发约束：**同一时刻只能有一个归档任务在跑**；并发跑会在冷表主键上冲突报错（有意的失败，不是静默写重）。

> `JdbcExecutionLogCleaner` 固定操作**热表**，别拿它清冷表。冷表自己的留存到期（如"冷数据也只留 5 年"）：
> 未分区就分批 DELETE；按 `add_time` 分区就用 `DROP PARTITION`（`04-create-archive-table.sql` 里给了分区变体）。

## 6. 异常体系

| 异常 | 场景 | 修复方式 | 可重试 |
|---|---|---|---|
| `IfmapConfigException` | 配置缺失 / 非法 / 成环 / 契约违规 / 保留期配 0 | 改配置或改代码 | ❌ |
| `RuleNotFoundException` / `RuleArgumentException` / `RuleInvocationException` | `@FUN` 规则不存在 / 参数不匹配 / 执行期异常 | 修模板或规则实现 | ❌ |
| `IfmapStrategyException` | 策略、动作、回调未注册 | 补 bean | ❌ |
| `IfmapRemoteException` | 资方接口外呼失败 | 依赖下游恢复 | ✅ |
| `IfmapValidationException`（admin 模块） | 管理端保存前校验未通过 | 按 `errors` 明细改配置 | ❌ |

全部继承 `IfmapException extends RuntimeException`（不强制调用方 catch；配置类问题应在**启动期**暴露）。管理端把这些异常映射成 HTTP 状态码，见 [`07-管理端REST.md`](07-管理端REST.md) §4。

## 7. 合规自查清单

上线前逐条打勾（对应设计 §7.5 / §6.4）：

| # | 项 | 怎么看 |
|---|---|---|
| 1 | 执行日志里的手机号/证件/卡号已打码 | 跑一次真实调用，查 `ifmap_execution_log.request_param` / `response_param` |
| 2 | 姓名类字段按业务要求脱敏 | 配 `ifmap.log.mask-fields`（默认集可能不够，比如 `payeeName`） |
| 3 | 不该落库的字段确实没落 | 配 `ifmap.log.exclude-fields`，查库确认是 `***` |
| 4 | 超长报文已截断 | 造一条超大应答，确认以 `...truncated` 结尾 |
| 5 | 保留期符合内部规范 | `ifmap.log.retention-days` 与《日志留存制度》一致 |
| 6 | 清理任务真的在跑 | 看日志 `ifmap 执行日志清理完成：共删除 N 行`；或手工 `task.cleanNow()` |
| 7 | 写日志失败不影响业务 | 停掉日志表（或断开连接池）后调用，业务结果仍正常返回 |
| 8 | 敏感数据不出现在应用日志里 | 检查 `mask-fields`/`exclude-fields` 是否覆盖了 DEBUG 打印路径 |
| 9 | 清理权限最小化 | 清理任务用的账号只需 `SELECT` + `DELETE` 该表 |
| 10 | 大表清理不引起主从延迟 | 监控 `Seconds_Behind_Master`，必要时调小 `clean-batch-size`、调大 `clean-batch-sleep-millis` |
| 11 | 若启用冷热分离：冷表与热表都符合留存口径 | 热表 90 天、冷表 5 年这类双口径要写进制度；归档任务日志里有"冷表新增 N 行" |

## 8. 排错

| 现象 | 原因 / 处理 |
|---|---|
| 日志里姓名没打码 | 字段名不在默认集（如 `payeeName`）→ 加进 `ifmap.log.mask-fields` |
| 手机号被打成 `1**********` | 把手机号字段名也配进了 `mask-fields` → 去掉它（值形态正则会正确处理） |
| 配 `mask-fields` 为空但姓名仍被打码 | 空集合回退默认集（设计如此）→ 要彻底关闭请自定义 `LogMasker` bean |
| 执行日志不写 | `ifmap.log.enabled=false`；或没装配 `ExecutionLogSink`（无 `ConfigRepository` / `DataSource`） |
| 清理任务没跑 | `ifmap.log.clean-enabled=false`；或 `ifmap.log.enabled=false`（不写日志就不清理）；看启动日志有无 `ifmap 执行日志定时清理已启动` |
| 应用（非 Web）跑完不退出 | 不是本模块引起的话先查其它非守护线程；本模块的调度线程名叫 `ifmap-log-clean-*` 且**是守护线程**，可用 `jstack` 核对 |
| 清理报「保留天数必须大于 0」 | `ifmap.log.retention-days` 配了 0/负数；要停清理请关 `clean-enabled` |
| 启动报 cron 解析失败 | `ifmap.log.clean-cron` 非法（Spring 是 **6 段**表达式，含秒，不带年） |
| 每次清理只删了一小部分 | 达到 `clean-max-batches × clean-batch-size` 上限（日志有 WARN）→ 调大上限或缩短调度周期 |
| 清理后主从延迟飙升 | 调小 `clean-batch-size`、调大 `clean-batch-sleep-millis`，并避开业务高峰 |
| 写日志报 `1526 Table has no partition for value` | 分区表缺 `pmax` 兜底分区或新月份分区没加 → 立刻 `REORGANIZE PARTITION pmax INTO (...)` 补上（见 5.2） |
| 建分区表报 `1503 A PRIMARY KEY must include all columns ...` | 分区的唯一键没包含分区列 → 主键改成 `(key_id, add_time)` |
| 归档报"冷表不存在 / 缺列" | 没执行 `04-create-archive-table.sql`，或冷表结构漂移 → 按报错提示建表/补列（归档器不会自动建表） |
| 归档报冷表主键冲突 | 有两个归档任务在并发跑 → 加分布式锁，确认只有单实例在跑 |

## 9. 配置项总表

| 配置 | 默认 | 归属 |
|---|---|---|
| `ifmap.log.enabled` | `true` | 是否写执行日志 |
| `ifmap.log.truncate-threshold` | `65536` | 截断阈值（字符） |
| `ifmap.log.mask-fields` | 空（用默认 8 个姓名类字段） | 按字段名脱敏 |

| `ifmap.log.clean-batch-size` | `1000` | 每批删除行数 |
| `ifmap.log.clean-max-batches` | `1000` | 单次最多批数 |
| `ifmap.log.clean-batch-sleep-millis` | `50` | 批间停顿 |
| `ifmap.log.clean-cron` | `0 30 3 * * ?` | 调度表达式 |
