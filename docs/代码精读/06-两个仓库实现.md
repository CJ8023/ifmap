# 06 · 两个仓库实现（JDBC / Remote）

`ConfigRepository` 是引擎唯一的数据入口（`IfmapOrchestrator.loadPlan:163` 调它）。
本仓库给了两个实现，**语义必须一致**，差别只在数据存在哪：

| 模块 | 文件数 / 行数 | 数据源 | 何时用 |
|---|---|---|---|
| `ifmap-provider-jdbc` | 35 / 5,097 | MySQL（`JdbcTemplate`） | 默认；配置落库 + 执行日志 + 审计历史 + 归档/清理 |
| `ifmap-provider-remote` | 6 / 1,557 | HTTP（ECC 现网服务） | 迁移期/双写期，配置还在对方系统里 |

## 4. 两个实现的等价性要求（改任一边都要看）

| 契约 | JDBC 怎么保证 | Remote 怎么保证 |
|---|---|---|
| 只返 `del_status=0 && status=1` | `queryConfigsByBusiNode` 的 WHERE 硬编码 | 拿到列表后 `isActive` 本地筛 |
| 按 `interface_order` 升序、`key_id` 兜底 | `ORDER BY interface_order ASC, key_id ASC` | `CONFIG_ORDER` 比较器 |
| 分支按 `logicBranchOrder`、`keyId` 兜底 | `ORDER BY` | `BRANCH_ORDER` |
| `busiNode` 空 → 空列表 | `:195` 提前返回 | `putIfPresent` 不传空参数（远端可能返回全量或空，由本地筛） |
| 租户 String，null/空 → `-1` | `tenant(...)` | `parseTenantId` / `tenantOf` |
| 日志落库失败不能影响主流程 | 由 `RepositoryExecutionLogSink` + `writeLog` 的 try/catch 兜 | 同 |

## 5. 看起来多余但别删的点

| 点 | 位置 | 为什么保留 |
|---|---|---|
| `TableNameResolver` 单独成类 | — | 存量环境表名前缀是 `bankint_`，且前缀要拼进 SQL；把「校验 + 缓存 + 5 个表名」集中在一处，比到处字符串拼接安全 |
| `IfmapRowMappers` 的列清单常量 | `:41/50/55` | 29 列的 SELECT 只能有一份真相；散落各处会出现"某条查询少一列 → 字段静默 null" |
| `JdbcValues` 4 个小方法 | — | `NOT NULL DEFAULT ''` 列数量很多，逐个写 `== null ? "" : v` 会漏 |
| `JdbcExecutionLogCleaner` + `Archiver` 都保留 | — | 两者的风险等级不同：清理 = 删了就没；归档 = 先搬走。大表用归档、小表用清理 |
