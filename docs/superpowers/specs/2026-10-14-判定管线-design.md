## 1. 背景与问题

### 1.1 现状

判定只有一层，就是拿响应报文里的一个字段跟期望值逐个比：

```java
// ResponseJudge.evaluate（ifmap-core/.../orchestrator/ResponseJudge.java）
flag = result_flag;  expected = success_value;
flag == null            → 成功（"没有约定字段就认为受理了"）
响应为空 / 非 JSON      → 失败（不抛异常）
expected == null        → 取到的值非空且非 false/0 即成功（隐式 falsy 魔法）
否则                    → 按 , 或 ; 切分后逐个 equalsIgnoreCase
```

判定结论 `Judgement{success, actualValue, expectedValue, reason}` 在 `IfmapOrchestrator:231-236` 只被用于三处：是否走分支、`errorMessage`、`log.setExecutionResult(success ? "SUCCESS" : "FAIL")`（`:401`）。

传输层（HTTP 状态码 / 超时 / IO）在引擎里**不可见**：`PartnerServiceGateway.exchange` 的契约就是"宿主把 IO/超时/非 2xx 包成 `IfmapRemoteException`"，而 `IfmapRemoteException` 只有 `serialVersionUID`，既无状态码也无可重试标记。

### 1.2 四个问题

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| P1 | 判定只有业务层，传输层不可见 | `PartnerServiceGateway` javadoc；`IfmapRemoteException` 空体 | 分不清"对方 500""超时""对方业务拒绝"，重试/降级只能靠猜 |
| P2 | 失败原因不落地 | `ExecutionLog` 只有 `executionResult` + `errorMsg`（DDL `003:16-38`，17 列）；`errorMsg` 只是 `judgement.reason` 文本 | 排障要人工翻 `response_param`，看板上无法统计失败分布 |
| P3 | 判定表达力只有"等于任一值" | `ResponseJudge.split` 只按分隔符切分后 `equalsIgnoreCase` | 不支持取反/不等/组合；`docs/10` §6 第 12 条把存量 `!a` 变成"人工改配置" |
| P4 | "没配判定字段 = 成功"是隐式语义 | `docs/06` §7 表格首行；`IfmapOrchestratorTest` 里 10 处 `setResultFlag(null)` | 审计无法回答"到底放行了多少个不判定的接口" |

### 1.3 参照对象的成熟形态（base-svc-ai）

1. **传输层是硬门槛**：非 2xx 直接判失败且**不进入配置模式**，4xx→`error_client`、5xx→`error_server`（`ApiStepRunner.handleResponse:414`）
2. **业务层可配置**：`ApiResponseConfig{successCondition:"code=0", messagePath, trackIdPath}`；未命中时**保留实际错误码**而不是写死 `"1"`
3. **默认兜底**：没配 `successCondition` 时按 `errcode`/`code` 判业务错（`AbstractHttpStepRunner:240,298`）
4. **错误消息抽取**：`message > error > detail > errorMessage`，截断 200 字符（`:320`）
5. **静默降级**：响应非 JSON / 规格格式不合法 → WARN + 退回默认判断，**不抛异常**
6. **结果结构化**：`status + errorCode + message + resultType + resultContent` 落到执行记录，再接误差记录与恢复链路

## 2. 目标与非目标

**目标**

- 判定收敛为**单一入口**（`result_judge`），引擎 / 管理端 / 远端配置源 / 契约自检 / 试跑口径一致
- 判定分四段：传输 → 业务 → 抽取 → 分类；失败可归因、可落库、可统计
- 判定表达力覆盖：等于 / 不等 / 成员 / 正则 / 存在 / 非空 / 组合（`all`/`any`）
- 判定规格**必填**，缺失或非法一律显式失败（fail-closed），不再有"隐式成功"

**非目标（本次明确不做）**

- 不做重试 / 熔断 / 告警**驱动** —— 只记录（§3.5）
- 不做存量数据迁移、不做降级回写、不保留回滚窗口（用户口径：**新项目新配置**）
- 不在存量表（`bankint_*`）上做任何 DDL
- 不引入完整布尔表达式语言（无 SpEL、无任意嵌套）
- 不扩展 `execution_result` 的既有值域（`SUCCESS/FAIL/SKIP/TIMEOUT` 已被下游消费）
- 不加 `fail_type` 索引、不出失败分布看板接口（等真的要有消费方时再加）

## 3. 设计

### 3.1 总览

```
出网（宿主） ──可选──> PartnerOutcome{statusCode, timedOut, errorType}
                          │
                  ┌───────▼─────────────────────────────────────┐
                  │ JudgementPipeline（ifmap-core，零 JSON 依赖）│
                  │ ① TransportStage  非 2xx/超时 → 立即失败，不求值规格 │
                  │ ② BusinessStage   ResultJudge SPI  ← result_judge 规格 │
                  │ ③ ExtractStage    固定候选路径抽 message / trackId（不新增配置列） │
                  │ ④ ClassifyStage   fail_type 枚举                      │
                  └───────┬─────────────────────────────────────┘
                          ▼
              Judgement{success, stage, failType, actual, expected,
                        errorCode, httpStatus, trackId, reason}
                          │
        ┌─────────────────┼──────────────────┐
        ▼                 ▼                  ▼
   分支/动作        IfmapResult.failType   ifmap_execution_log（4 个新列）
```

职责边界不变：**引擎不出网、不做加解密**；传输层信息由宿主**可选**上报，引擎不主动获取。

### 3.2 `result_judge` 规格语法

顶层只有三种形态，**互不退化**（用户决策）：

| 形态 | 语法 | 校验 | 运行期 | `fail_type` | 审计 |
|---|---|---|---|---|---|
| ① 恒真（不判定） | `{"op":"always"}`，单对象，**不允许出现 `path`/`value`** | 合法 | 恒成功；**短路，不解析响应** | 永不产生 | `reason="always：该接口不做结果判定"` |
| ② 空组合 | `""` / `{}` / 缺列 / `{"all":[]}` / `{"any":[]}` | **非法**（不解释成恒真） | fail-closed：判失败 + WARN | `SPEC_INVALID` | 与业务失败在看板上可区分 |
| ③ 条件判定 | `{"all\|any":[{path,op,value?,ignoreCase?}]}`，**至少 1 条** | 合法（op / path / 嵌套校验） | 正常求值 | `NOT_JSON` / `FIELD_MISSING` / `VALUE_MISMATCH` | 完整 `actual` / `expected` |

`op` 取值（7 个，闭合集合，不接受未知值）：

| op | 语义 | 备注 |
|---|---|---|
| `eq` | 实际值 = `value` | |
| `ne` | 实际值 ≠ `value` | 存量 `!a` 的正式表达 |
| `in` | 实际值 ∈ `value`（数组，**不可为空**） | 替代旧 `success_value` 多值 |
| `notIn` | 实际值 ∉ `value` | |
| `exists` | JsonPath 能取到（值可为 null） | 区分"字段缺失"与"字段值为空" |
| `notBlank` | 取到的值非 null 且 trim 后非空 | 替代旧"`success_value` 为空 = 非空即成功" |
| `regex` | 实际值匹配 `value`（Java 正则） | |

其他规则：

- `path` 走 JsonPath（沿用 `JsonReadContext.read`，与模板 DSL 同一实现）
- 单条条件里的 `value` 按**字符串比较**；`ignoreCase` **默认 `false`（严格相等）**，需要忽略大小写必须显式写 `"ignoreCase":true`
  - 理由：判定是资金链路的仲裁点，宽松默认会吃掉 `SUCCESS` 与 `success` 的差异；显式写出来才可审计（D6）
  - 注意：这与旧 `success_value`"忽略大小写"相反，属**已声明的行为变更**
- `notBlank` **不再有 falsy 魔法**：`0` / `false` 视为**非空**（旧实现把它们当失败）。要判 `0` 请写 `{"op":"eq","value":"0"}`（D7）
- 组合嵌套上限 **3 层**（对齐模板 DSL 既有口径）；`all`/`any` 不允许自嵌套成同层重复
- 存储形态：`text` 列，**不用 `json` 列** —— `json` 列会拒绝非法内容（MySQL 3140 静默丢行）且会规范化数字形态，`docs/04` §8.3 已就同类问题定过口径（D8）

### 3.3 判定管线与值对象

包位置：`cn.cj.ifmap.core.orchestrator.judgement`（`ResponseJudge` 迁入并拆为四段；`Judgement` 保留在 `orchestrator` 包以少改 import）。

```java
public interface ResultJudge {
    String name();                                  // 注册名，默认实现名为 ruleSpec
    Judgement judge(ResultJudgeContext context);     // context: config + responseJson + jsonOps
}
```

判定器解析顺序（沿用现有 `pre_strategy_name` / `post_strategy_name` 的注册表 + bean 名自动注册惯例，见 `IfmapStrategyRegistrar`）：

1. 配置列 `judge_name` 非空 → 按名取注册表（大小写不敏感，不一致时 WARN 并仍按匹配到的那个执行）
2. 配置列 `judge_name` 为空 → 注册表的默认判定器 `ruleSpec`
3. 按名取不到 → {@code fail_type=SPEC_INVALID} fail-closed（**不**回落默认判定器）

> 第 3 条与初稿不同：初稿写的是「按既有 `failOnMissingStrategy` 口径处置」。落地时判定为
> **不允许回落**：回落等于"以为按资方规则判、其实按默认规则判"，比直接失败更难查。
> 另初稿提到的全局属性 `ifmap.judge.default-name` **没有实现**（默认名是注册表里硬编码的
> `ruleSpec`，可由宿主代码 `setDefaultName` 改），文档只写"空 = `ruleSpec`"。

`Judgement` 扩展（保留 `isSuccess()` / `getActualValue()` / `getExpectedValue()` / `getReason()` 四个既有访问器）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `success` | `boolean` | |
| `stage` | `Stage` 枚举 | `TRANSPORT` / `BUSINESS` / `EXTRACT` / `NONE` |
| `failType` | `String`（枚举值） | 成功时为 `""` |
| `actual` / `expected` | `String` | `expected` 为规格的字符串化摘要 |
| `errorCode` | `String` | 失败时取到的实际码（**不写死 `"1"`**，对齐 base-svc-ai） |
| `httpStatus` | `Integer` | 无宿主上报时为 `null` |
| `trackId` | `String` | ③ 段按固定候选路径抽取（不新增配置列），未取到为 `null` |
| `reason` | `String` | 人读的说明 |

**未加 `retryable`**：既然只记录不驱动，它没有消费方（`fail_type` 里的 `TIMEOUT`/`HTTP_5XX` 已能表达可重试性，将来要驱动重试从枚举映射即可）—— 见 §8 被否决方案 (iii)。

`fail_type` 枚举（9 值闭合，成功为 `""`）：

`TRANSPORT`（连接/IO 异常）、`TIMEOUT`、`HTTP_4XX`、`HTTP_5XX`、`SPEC_INVALID`（规格空/非法）、`NOT_JSON`（响应非合法 JSON）、`FIELD_MISSING`（路径取不到）、`VALUE_MISMATCH`（取到值但未命中）、`EXTRACT_FAILED`（③ 段抽取路径写错，仅 WARN，不改判定结论）。

### 3.4 `result_judge` 必填的三层落地（用户决策）

| 层 | 做法 | 证据/口径 |
|---|---|---|
| DDL | `result_judge text NOT NULL`，**不带 `DEFAULT`** | ifmap 的必填口径 = "DDL 里 `NOT NULL` 且**没有** `DEFAULT`"（`docs/11`:160，配置侧 5 个必填列：`interface_no / interface_code / interface_name / busi_node / partner_code`，`key_id` 由引擎生成故不在内）；声明成这样，**远端配置源的必填校验自动生效**，必填清单 5 → 6 列 |
| 保存期 | 管理端表单必填 + `POST /configs/validate` 同一套判定 → **422 + errors/warnings** | `IfmapAdminExceptionHandler:42-49`（既有契约） |
| 运行期 | 空白/非法规格 → fail-closed：判失败 + WARN + `SPEC_INVALID`，**不抛异常** | 与 `ResponseJudge` 今天的降级姿态一致 |

> DDL 只能保证"列非 NULL"，**表达不了"非空白字符串"**（MySQL 5.7 不认 `CHECK`；`JdbcValues.orEmpty` 会把 null 归一化成 `''`）。所以"非空白"必须靠保存期与运行期两层拦 —— 这就是三层都要的原因。

### 3.5 传输层：通道预留、行为最小

```java
public interface PartnerServiceGateway {
    String exchange(PartnerCall call);                   // 既有契约，不动
    default PartnerOutcome exchangeForOutcome(PartnerCall call) {   // 新增，可选实现
        return PartnerOutcome.ofBody(exchange(call));     // 默认实现：无状态码信息
    }
}
```

- 老实现**零改动**（默认实现回落 `exchange`）；实现了的方法才有 `http_status` / `HTTP_4XX` / `TIMEOUT` 这些信息
- 非 2xx 在宿主侧**可以**改成"不抛异常、由 outcome 上报"（对齐 base-svc-ai 的硬门槛语义）；`IfmapRemoteException` 契约保留不变（宿主抛了，引擎按 `TRANSPORT` 归类）
- **只记录不驱动**（用户决策）：`fail_type` 只落库、只展示；不做重试、不做熔断、不加索引、不出看板接口

### 3.6 执行日志与可观测

`ifmap_execution_log` 增量加 4 列（DDL 现 17 列 → 21 列）：

| 列 | 类型 | 说明 |
|---|---|---|
| `http_status` | `smallint DEFAULT NULL` | 宿主上报时才有 |
| `fail_type` | `varchar(32) NOT NULL DEFAULT ''` | 枚举值；成功为空串 |
| `error_code` | `varchar(64) NOT NULL DEFAULT ''` | 失败时取到的实际码 |
| `track_id` | `varchar(128) NOT NULL DEFAULT ''` | ③ 段按固定候选路径抽取（`$.trackId` → `$.track_id` → `$.requestId` → `$.serialNo`）；未取到即空串；**必须过截断**，脱敏按 `docs/08` 既有口径 |

- **③ 段用固定候选路径列表，不新增配置列**（`message_path` / `track_id_path` 这次不加）：消息抽取按 base-svc-ai 同序 `$.message` → `$.msg` → `$.error` → `$.detail` → `$.errorMessage`，截断 200；`error_msg` 变为「`judgement.reason` + 抽到的 message」（reason 在前，保持既有排障习惯）。抽不到就是空，**不影响判定结论**（仅 `EXTRACT_FAILED` 告警，且只在内置路径全部失败且响应是合法 JSON 时才发生）。理由：两列会让管理端多两个手填 JsonPath 的差错面，收益只是“可自定义”，而固定列表已覆盖绝大多数报文；真要按资方定制时再加列（§9.5）。

- `ExecutionLog` 值对象加 4 个字段；写入路径 `JdbcConfigRepository.saveExecutionLog:111-122`、`IfmapRowMappers`、远端 `insert_log` 映射同步
- **不动 `execution_result`**：它的值域 `SUCCESS/FAIL/SKIP/TIMEOUT` 已被宿主与下游消费，扩值域是破坏性变更（D10）
- `IfmapResult` 增 `failType`（宿主/管理端能拿到结论，不需要去解析 `errorMessage`）
- 不加索引：无查询接口、无看板（§8 被否决方案 iv）

### 3.7 校验与工具链（单一实现，禁止两套）

- **规格解析/校验只在 core**（基于 `JsonOps`，满足"core 零 JSON 库依赖"）：`ResultJudgeSpec.parse(...)` 同时提供 `validate(...)` 返回违规清单
- 两处校验入口都复用 core 的实现，**不自己写第二套**：
  - `ifmap-core/.../validate/ContractValidator`（部署前契约自检，`docs/06` §8）新增检查项：规格合法性（op 白名单 / `in` 空数组 / 嵌套深度 / `always` 不允许带 `path` / `judge_name` 已在注册表）+ **判定形态统计**（③ 条件判定 / ① 恒真 各多少条）—— 这正是 P4 要解决的审计盲区
  - `ifmap-admin` 的 `ConfigValidator`（`admin/ConfigValidator.java:52`）**调用同一个 core 实现**，不自己写一套正则/JSON 校验（admin → core 依赖方向成立）
- dry-run（`docs/07` §5）返回 judgement 明细：哪一段失败、取到什么、期望什么

### 3.8 管理端

- `ConfigSnapshotMapper` 读写新列；历史快照（`ifmap_config_history.snapshot` 是 `json`）里**旧字段要能读出来不报错**，新快照只写新字段
- 表单：判定形态三选一（恒真 / 条件），选恒真时隐藏字段输入；条件行编辑器按 op 决定 `value` 是否必填
- `docs/07` 字段表同步

## 5. 建表脚本与部署口径（新装口径）

`005-config-result-judge.sql`（示意，实测前需在真库演练）：

```sql
--changeset caijun:005-config-result-judge
ALTER TABLE `${tablePrefix}config`
  ADD COLUMN `result_judge` text        NOT NULL                COMMENT '结果判定规格（JSON；必填，空/非法即判失败）',
  ADD COLUMN `judge_name`   varchar(64) NOT NULL DEFAULT ''     COMMENT '判定器名（空=用全局默认 ruleSpec）',
  DROP COLUMN `result_flag`,
  DROP COLUMN `success_value`;
```

三条部署口径必须写进脚本 README：

1. **两条 DROP 是刻意的**：这意味着 `005` **不适用于"复用存量表且存量模块仍在跑"的场景**（`ifmap.table-prefix=bankint_` 的共存期路径 A）。那种场景必须裁掉这两句 DROP —— 脚本里用注释显式标出可裁剪段（沿用迁移 kit 的 README 风格）。
2. **不自动回填**：表非空时，历史行给不出正确规格，而**任何占位值都会变成静默放行**（`always` 会让历史配置全部判成功）。口径 = 由宿主显式处置（管理端逐条补规格，或先停用）；脚本不做 `UPDATE ... SET '{"op":"always"}'` 这种"好心"的兜底。
3. **非空表上的 `ADD COLUMN text NOT NULL` 需先演练**：MySQL 严格模式下对非空表加无默认值的非空列可能报错。真库演练若命中，改用两步法（先 `NULL` 加列 → 逐条补规格 → 再 `MODIFY ... NOT NULL`），两步法同样**不自动补占位值**。

`006` 只做 4 列 `ADD COLUMN`（全为可空或 `NOT NULL DEFAULT ''`），风险低。

## 6. 测试策略

| 层 | 用例 | 为什么是它 |
|---|---|---|
| 规格解析 | 7 个 op × `all`/`any` × 边界（取不到值 / null / 空串 / 数字 / 大小写 / `ignoreCase` 开关 / 嵌套 3 层与 4 层） | 规格引擎是唯一判定入口，边界就是事故面 |
| 非法规格 | 空串 / `{}` / `{"all":[]}` / `always` 带 `path` / `in` 空数组 / 未知 op / 4 层嵌套 → 校验层报错 + 运行期 `SPEC_INVALID` 且**不抛异常** | 三种形态"互不退化"这条设计必须被测试钉住 |
| `always` 短路 | 响应是 HTML / 空串 / `null` 时仍判成功 | 否则 `always` 会被 `NOT_JSON` 判失败，形态①名不副实 |
| JSON 实现一致性 | 同一批 fixture 在 `ifmap-json-jackson` 与 `ifmap-json-fastjson` 下**逐条同结论**，作为 `ifmap-json-tck` 的新契约 | 判定走 `JsonOps`，换实现不能改判定结论（沿用 CHANGELOG 里"换 JSON 实现不改模板语义"的既有口径） |
| 编排链路 | 判定失败不走分支（现状保持）；`stopOnFailure` 交互；`failOnFailure` 日志仍落库 | `IfmapOrchestratorTest` 里 10 处 `setResultFlag(null)` 用例全部改造成新规格 |
| 管理端 | `ConfigValidator` 规格违规 → 422 消息指明 op/位置；表单必填；快照旧字段可读 | `IfmapAdminWebEndpointTest` 既有 422 用例扩展 |
| 真库档（`itt_*`） | 建出的表**逐列比对** `COLUMN_TYPE` / `IS_NULLABLE='NO'` / `COLUMN_DEFAULT IS NULL`（`result_judge`）、日志 4 新列写入与读回、`result_flag`/`success_value` 已不存在；跑完 `itt_*` 残表 = 0 | 层口径只在真库上才看得出（H2 不等于 MySQL），且列级断言比"列数对不对"可靠 |

**TDD 口径**（`CONTRIBUTING.md` §2）：每条行为先写红测试；改 `ResponseJudge` 前先把新规格的失败用例写出来，避免"改了实现再补测试"的安慰剂。

## 8. 风险、权衡与被否决的方案

| 被否决 | 理由 |
|---|---|
| (i) 在存量表 `bankint_config` 上 `DROP` 旧列 | 用户已明确不关注存量；但**引擎侧**只认新规格这一步做到了，"物理删存量列"单列为后续项（§9） |
| (ii) 完整布尔 DSL / SpEL | 表达力边际收益低，校验与文档成本高；`all`/`any` + 7 op 已覆盖判定场景 |
| (iii) `Judgement.retryable` | 只记录不驱动 → 无消费方（`docs/ifmap-过度设计诊断_v1.md` 的教训：没有调用方/装配入口/文档承诺三者之一就不加） |
| (iv) `fail_type` 加索引 + 失败分布看板 | 同上：无消费方，等真要 B/C 场景再加 |
| (v) 空规格 = 成功（保留旧语义） | 被 D3 否决：会让"漏配判定"继续静默放行 |
| (vi) `{"all":[]}` 解释为恒真 | 被 D4 否决：与 `always` 同义会让"三形态"退化成两形态，审计统计失效 |
| (vii) 复用/扩展 `execution_result` 值域 | 破坏下游已消费的取值 |
| (viii) core 与 admin 各写一份规格校验 | 必然漂移，且 admin 侧无法发现运行期语义差异 |

**主要风险**：`005` 的 `DROP COLUMN` 对"复用存量表 + 存量模块在跑"的宿主是破坏性的 → 用脚本内注释 + README 显式标注可裁剪（§5.1）；该口径与用户"新项目新配置"的决策一致，属**已声明的取舍**而非疏漏。
