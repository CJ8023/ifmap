# 编排定序、跨步骤共享池与前后序策略 —— 设计

- 状态：**已批准**（用户已逐条决策：删 `front_interface_no` 单一定序 / 策略拆前后序且后序在回参产物之后 / 池键根 `pool` / 池引用校验只在 admin / 预置池走 `payload.pool`）

## 1. 背景与问题

### 1.1 定序机制有两套，且表达同一件事

`ifmap_config` 同时有 `front_interface_no`（前置接口编号）与 `interface_order`（执行顺序）：

- `InterfaceOrdering.plan` = `topological(sort(enabled(configs)))` —— 先按 `interfaceOrder` 升序（同值 `keyId` 兜底），再按 `front_interface_no` 做 DFS 拓扑排序 + 环检测。
- `IfmapOrchestrator.loadPlan` 用 BFS 顺着 `front_interface_no` 递归收集前置链（`MAX_FRONT_DEPTH = 64`）。
- `ConfigValidator.checkFrontChain`（`:279-309`）重复一遍前置链校验：自指 / 成环 / 过深 / 不存在。

两者表达的是同一件事：**同一 `busi_node` 下多个编排步骤的先后次序**。`front_interface_no` 是相对指针（步 N 指向 N-1），`interface_order` 是绝对序号。因为真实数据模型是 **`interface_no` 一配置一行**（`interface_no` 全局唯一），`interface_order` 不承载「同一接口的多个槽位」语义，所以两者确实冗余。

> 此前一度判断二者「正交（排序 vs 依赖）」，该判断是**从唯一键反推槽位语义**得出的，前提错误，已撤回。唯一键 `uk_config_biz (tenant_id, interface_no, busi_node, interface_order, deleted_seq)` 会让人以为「同一 interface_no 可多行」，实际不会。

### 1.2 跨步骤数据传递完全缺失

`runPlan`（`IfmapOrchestrator:181-206`）每步只做：

```java
StepOutcome outcome = executeOne(request, tenantId, config, mockResponse);
result.executedInterface(config.getInterfaceNo());
data.putAll(outcome.data);        // 只流向最终结果 IfmapResult.data
```

- `executeOne`（`:209`）每步**新建** `StrategyContext`，`params` 是 `request.getPayload()` 的一份拷贝 → 每步的入参起点相同，前序产物看不见。
- 模板 `$.` 的根就是 `render(template, source, ctx)` 传入的 `source`（`TemplateEngine:121`）：请求模板的根 = `params`，响应模板的根 = **原始回参**。因此「让后续请求模板用到前序回参」**必须**让数据出现在 `params` 里。
- 已有能力：`ResponseJudge` 每步都从 `result_flag`（JsonPath）取出了值（`Judgement.actual`），但**用完即弃**，没进任何池。

### 1.3 策略只有一个位置、且无法加工回参

- `applySpecialDeal`（`:225`）在**渲染后、出网前**执行，返回 `Map` 合并进 `params` 并**重渲染**请求模板 —— 它的语义**恰好就是「前序策略」**。
- 没有任何「回参之后」的钩子。而 `StrategyContext` 早已预留 `get/setResponseData()`、`get/setResponseJson()`、`get/setMatchedBranch()`，其中 **`get/setResponseData` 在主代码里一次都没被调用过** —— 是个预留但未接线的载体。
- 宿主实现策略已是现状：`IfmapStrategyRegistrar`（`BeanPostProcessor`）按 **bean 名**自动注册宿主的 `SpecialDealStrategy`（`:78-79`），主代码零内置实现。

### 1.4 顺带发现的两个缺陷

- **`interface_no` 全局唯一未被强制**：DDL 注释写「接口编号（业务唯一键）」，但唯一键含 `busi_node` → 同一 `interface_no` 可合法插到两个 `busi_node` 下。而 `queryLogicBranches(tenantId, interfaceNo)` 签名里**没有 `busi_node`**（`ConfigRepository:50`）→ 逻辑分支会跨节点串。`ConfigValidator` 也不查这条。
- **`InterfaceOrdering.topological` 的 `visit` 有 `if (prerequisite != config)` 判断** → 「单条配置自指」静默 no-op，两条才报环，行为不一致（`InterfaceOrderingTest` 两种行为都有用例）。

## 2. 目标与非目标

目标：

1. **定序单一机制**：删除 `front_interface_no`，`interface_order` 在 `busi_node` 内唯一定序。
2. **跨步骤共享池**：每步产物进入 `$.pool.{interface_no}`，后续步骤的请求模板直接可取；池可**往返**（宿主预置 + 结果带回）。
3. **策略拆前后序**：`strategy_name` → `pre_strategy_name` + `post_strategy_name`，共用既有的 `SpecialDealStrategy` SPI 与同一个 registry；后序可加工回参产物。
4. **断点续跑**：`interfaceNo` 语义从「执行哪条」变为「从哪条开始」；池键集合即「已成功步骤集合」。
5. **静态护栏**：`$.pool.` 引用在保存时校验（拼错 / 顺序写反 / 自引用）。

非目标（明确不做，附理由）：

| 不做 | 理由 |
| --- | --- |
| `dependsOn` / DAG / 并行批次 | 参照项目 `base-svc-ai` 的数组序一旦有任意步骤声明 `dependsOn` 就被 `DagAnalyzer` 整体作废并改走 Kahn 拓扑 + `HashMap` 序遍历（无数组序兜底），且缺失依赖只 `log.warn` 不报错。ifmap 是单一顺序流水线，引入即等于放弃"顺序=数组序"这一唯一确定性 |
| 整份 execution context 落库 + 压缩 | 参照项目用 `ai_task.execution_context` 存整份 `CapabilityExecutionContext`（741 行 `Serializable`），代价是 64KB 预算 + `ContextCompactionService` 五层渐进压缩（L4 还要调 LLM）。ifmap 只存「被声明的产物」，天然有界 |
| `outputs_json` 声明式产物池 | 与既有 `response_param_template`（已能把回参投影成字段，且支持 `@concat@`/`@FUN` 加工）构成「同一件事两套做法」；只取其「可静态校验」的能力，见 §4.6 |
| 策略链 `strategies_json`（多策略 / 显式 phase 数组） | 场景是「一个前序 + 一个后序」；数组形态会让配置面 > 使用面，且内嵌零框架 UI（980 行 `app.js`）要新写一个链编辑器 |
| 引擎侧断点进度表 | 宿主可从 `IfmapResult.data.pool` 的键集合推出「已成功步骤」，无需建表、无需触碰脱敏/保留期 |
| **存量数据搬运** | 用户明确「当作新项目」：不写老库→新库的数据迁移/回填逻辑。注意**列名同步仍在本范围内**（见 D16）：迁移 kit（`db/migration/ecc-to-ifmap/*`）与 `docs/10-迁移指南.md` 必须以新列为准改写，否则形成「文档承诺 vs 实际 DDL」不一致 |

## 3. 决策记录

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 删除 `front_interface_no` 与 `idx_config_front`，只留 `interface_order` | 两者表达同一件事；机制数 2→1；连带删掉拓扑排序/环检测/深度护栏/4 类校验（约 130 行生产代码 + 3~4 个用例） |
| D2 | `interface_order` 在 `busi_node` 内唯一（新唯一键 `(tenant_id, busi_node, interface_order, deleted_seq)`） | 现状同 `busi_node` 下两条配置可同 order，靠 `keyId` **静默兜底** —— 定序机制只靠它就等于放弃确定性 |
| D3 | `interface_no` 全局唯一（新唯一键 `(tenant_id, interface_no, deleted_seq)`） | DDL 注释已宣称是业务唯一键，但约束没强制；`queryLogicBranches` 无 `busi_node` 也要求全局唯一 |
| D4 | 引擎取计划改走 `queryConfigsByBusiNode(tenantId, busiNode)` | `loadPlan` 的替代；否则计划里永远只有 1 步 |
| D5 | 池键 = `$.pool.{interface_no}`，保留根为 `pool`，**键里不加 `busi_node`** | `interface_no` 全局唯一（D3）→ 键本身无歧义；加节点前缀是冗余组件 |
| D6 | **只展平** `response_param_template` 产出的 `data` 顶层键；**整份原始回参只进池、绝不展平** | `code`/`message`/`data` 这类通用键跨步必然互相覆盖，而默认 `NullPolicy=SKIP_FIELD` 是静默的 |
| D7 | `post_strategy_name` 在 `renderResponse` **之后**执行，可加工 `data`（`StrategyContext.setResponseData` / 返回 `Map` 合并） | 既让「入池的回参 = 加工后的结果」，又不让策略越过判定边界（判定仍读原始回参） |
| D8 | 前后序**共用** `SpecialDealStrategy` SPI 与同一个 `SpecialDealStrategyRegistry` | 前序位置本来就对，零 API 变更；后序复用只是多一个调用点。`IfmapStrategyRegistrar` 的注册逻辑不动 |
| D9 | `StrategyContext` 增加 `phase`（`PRE`/`POST`） | 一个策略类同时挂前后序两列时能自辨；否则只能靠"`responseJson == null`"这种隐式判据 |
| D10 | 池**只在步骤判定成功时**入池 | 池键集合 = 已成功步骤集合 ⇒ **顺带解决断点续跑需要的"进度"**，不必新增字段/表；且不给下游留半成品 |
| D11 | `execute(request, interfaceNo, busiNode)` 中 `interfaceNo` = **起点**（空 = 全跑）；起点不在计划内则抛 `IfmapConfigException` | 不加新签名即承载断点续跑；传错起点从"静默重跑"变"立刻报错" |
| D12 | 预置池入口 = `payload.pool`（读作初始池，**不写回** payload） | 零 API 新概念；回程由 `IfmapResult.data.pool` 承载 → 池可往返 |
| D13 | 池引用校验（T2）统一 **error**，含「引用后续步骤」与「自引用」 | 唯一正当的预置场景（断点续跑回放）只涉及**更早 order** 的步骤 |
| D14 | 校验只在 admin 模块（`ConfigValidator`） | 用户决策；core 侧启动自检不做 |
| D15 | 复用 `DslExpressions.extractPathTokens` 做路径抽取，拆开请求/响应模板的路径集合 | 抽取层早已存在（`ConfigValidator:224-268`），只需换判据，不新造解析器 |
| D16 | 迁移 kit（`db/migration/ecc-to-ifmap/*`）与 `docs/10-迁移指南.md` 的**列名同步本次一并做**（只做列名/结构同步，不写数据搬运） | 评审决策；迁移 kit 是「随 jar 发布」的交付物（`docs/08:132`、`README.md:44` 均有承诺），留过时列名会让文档承诺与实际 DDL 冲突 |

## 4. 设计

### 4.1 数据模型

`ifmap_config` 变更：

| 动作 | 列 | 说明 |
| --- | --- | --- |
| 删除 | `front_interface_no` | 连同 `idx_config_front` |
| 删除 | `strategy_name` | 由 `pre_strategy_name` 取代（前序位置不变，语义一致） |
| 新增 | `pre_strategy_name varchar(128) NOT NULL DEFAULT ''` | 注释：前序策略标识（=Spring bean 名），出网前执行 |
| 新增 | `post_strategy_name varchar(128) NOT NULL DEFAULT ''` | 注释：后序策略标识（=Spring bean 名），回参产物之后执行 |
| 改唯一键 | `uk_config_biz` → `(tenant_id, interface_no, deleted_seq)` | D3 |
| 新唯一键 | `uk_config_order (tenant_id, busi_node, interface_order, deleted_seq)` | D2 |

`deleted_seq` 语义沿用现状（未删除 = 0，删除时 = `key_id`），所以软删后可以重建同 `interface_no` / 同 order。

### 4.2 执行计划

```java
// 旧：BFS 收前置链 + topological（含环检测/深度护栏）
loadPlan(tenantId, interfaceNo, busiNode)

// 新：
List<IfmapConfig> all = repository.queryConfigsByBusiNode(tenantId, busiNode);  // 契约：必须按 interfaceOrder 升序
List<IfmapConfig> plan = InterfaceOrdering.sort(InterfaceOrdering.enabled(all));
if (interfaceNo 非空) {
    int from = plan.indexOf(按 interfaceNo 定位);      // 找不到 -> IfmapConfigException
    plan = plan.subList(from, plan.size());
}
```

`InterfaceOrdering` 收缩为「过滤停用 + 按 `interfaceOrder` 升序（同值 `keyId`）」，删除 `plan` / `topological` / `visit` / `cycle` / `byInterface`。`MAX_FRONT_DEPTH` 一并删除。

`ConfigRepository` 契约调整：

- **新增** `List<IfmapConfig> queryConfigsByBusiNode(String tenantId, String busiNode)`，javadoc 写明「**必须**按 `interfaceOrder` 升序返回，同值按 `keyId` 兜底」。
- **保留** 现有 `queryConfigs(tenantId, interfaceNo, busiNode)`：它仍被 demo / 测试 / 单条查询使用。注意它签名的 `busiNode` 在 D3 之后成为冗余参数（保留以减少改动面，见 §7 R2）。
- `queryLogicBranches(tenantId, interfaceNo)` **不变** —— D3 让 `interface_no` 全局唯一后，无 `busi_node` 的签名是自洽的。

> 这是 **SPI 的破坏性变更**：`ConfigRepository` 是无默认实现的公开 SPI（docs/06 §11），宿主实现必须补这个方法。

### 4.3 步骤执行序列

```
[前序已成功步骤的产物已在池里]
 1. 构建 params（每步一份）：payload 拷贝 + FullParamStrategy + 展平(池) + pool
 2. 渲染 request_param_template（$. 根 = params）
 3. pre_strategy_name  → strategy.apply(context) → 返回值合并进 params → 重渲染   [现有位置，不变]
 4. 出网 gateway.exchange(...)
 5. context.setResponseJson(response)
 6. renderResponse(response_param_template) → data                                  [不变]
 7. post_strategy_name → strategy.apply(context) → 可 setResponseData 替换 / 返回值合并进 data
 8. 判定：judge.evaluate(config, response) —— **读原始回参**，后序策略无法影响        [不变]
 9. 成功才入池：pool.put(config.getInterfaceNo(), data)
10. applyBranch / writeLog / 返回 StepOutcome                                      [不变]
```

关键点：

- **第 1 步的池注入是新增的**。`executeOne` 目前 `StrategyContext.params` = `request.getPayload()` 拷贝，每步重建 ⇒ 池必须由 `runPlan` 持有并逐步注入。
- **第 7 步是新增的钩子**，落在 `renderResponse` 与判定之间。判定读 `response`（原始回参），所以 D7 的「不让策略越过判定边界」在实现上天然成立。
- **第 9 步的 `data` 是第 7 步加工后的 `data`** ⇒ 入池的就是加工后的产物。
- 池的 `pool` 子对象与 `params` 顶层键空间**物理隔离**（池在 `pool` 键下）⇒ 前序策略改 `params` 顶层键不会污染后续步骤（每步 params 本就重建）。

失败处理沿用现状：`stopOnFailure`（默认 true）在中途失败时 `break`；策略抛异常同现状向上抛（**不**新增 try/catch）。

### 4.4 共享池

**结构**：

```
params = {
  ...payload 顶层键,                 // 宿主入参
  ...FullParamStrategy 产出的键,
  ...展平(池) 顶层键,                // D6：按计划顺序 reduce，后写覆盖 = "最近值生效"
  "pool": {                          // D5/D12：保留根
    "IF_A": { ...A 的 data ... },    // A 的 response_param_template 产出的 Map（经后序策略加工）
    "IF_B": { ... }
  }
}
```

**写入**：`runPlan` 持有 `Map<String,Object> pool`；每步成功时 `pool.put(interfaceNo, data)`。

**读取（两种形态，各有用途）**：

| 形态 | 用途 | 冲突风险 |
| --- | --- | --- |
| `$.pool.IF_A.applyNo` | 跨步骤取指定步骤的字段（**推荐**，受 D13 静态校验保护） | 无 |
| `$.applyNo` | 取"最近一次产出的 `applyNo`"（便利） | 有：不同步骤同名键会互相覆盖，按**池的插入顺序**后者胜（预置项在前、本次成功步骤按计划顺序在后） |

**往返（断点续跑）**：

1. 宿主存下上次的 `IfmapResult.data`（其中含 `pool` 结构，因为 `data` 由 `pool` 展平而来，见 §4.5）。
2. 宿主把 `data.pool` 原样放进 `payload.pool` 发起重入，并传 `interfaceNo = 下一个未成功步骤`。
3. 引擎把 `payload.pool` **拷贝**为初始池（**不**持有也不写回 `payload` 的对象），逐步入池。
4. `pool` 的键集合 = 已成功步骤集合（D10）⇒ 宿主无需额外维护进度。

**`pool` 是保留键**：业务 payload 顶层不应有 `pool`。引擎在合并时 `pool`（池）**覆盖** payload 同名的顶层键。

### 4.5 `IfmapResult.data` 的形状

`runPlan` 现在 `data.putAll(outcome.data)`（扁平）。新形态：

```java
data.putAll(展平(池));      // 保持既有扁平语义（调用方读 result.getData().get("applyNo") 不受影响）
data.put("pool", 池);       // 新增：可往返结构
```

向后兼容：既有调用方读扁平键的代码不受影响，只是多了一个 `pool` 键。`IfmapResult.executedInterfaces` 语义**保持不变**（实际发起过调用的接口，含失败者）；「已成功的步骤」由 `data.pool` 的键集合表达。

### 4.6 池引用静态校验（T2）

**位置**：`ConfigValidator`，保存前门禁（`ValidationResult.errors` 非空即不允许保存）。

**前提改动**：`checkJsonPaths` 现在把两个模板的路径收进**同一个** `Set`（`:198-199`），必须拆成请求/响应两份 —— 两者根不同（请求根 = `params`，响应根 = 原始回参），判据不能混用。

**判据**（只处理以 `$.pool.` 开头的路径，其余一律不检查）：

| 情况 | 级别 | 消息要点 |
| --- | --- | --- |
| `X` 是本 `busi_node` 接口号，且 `interface_order` < 自己 | 通过 | — |
| `X` 是本 `busi_node` 接口号，但 `order ≥ 自己`（含**自引用**） | **error** | 引用了同序或后续步骤的产物，本轮不可能产出；打桩数据请走 `payload` |
| `X` 不是本 `busi_node` 的接口号（拼错 / 从别的节点复制而来忘了改） | **error** | 提示本节点的接口号集合 |

**为什么能统一 error**：唯一正当的预置场景是断点续跑回放，而续跑只跳过「起点之前」的步骤 ⇒ 合法池键**永远属于更早 order 的同节点步骤**。其余情况（引用后续步骤 / 跨节点）在本轮执行中**不可能产出**：

- 「跨节点引用」的实际成因是**复制配置后忘了改 `interface_no`** —— 而复用 `interface_code` 时 `interface_no` 必须不同，这恰恰是最典型的错法。
- 「跳过某后续步骤以复用其历史产物」在 D11 下**不可实现**：起点之后的步骤一定会执行并覆盖预置值。

**为什么不需要「是否允许宿主预置」的开关**：该问题被上述条件吸收，少一个配置面。

**自引用的继承**：被删除的 `checkFrontChain` 有「前置接口不能指向自己」（`:286`），池引用的 `order == self` 判定正好接管这条护栏。

**不做正向检查的原因（诚实边界）**：请求模板的 `$.` 根 = `params` = `FullParamStrategy 产出` + `payload` + 池。前两者的键**运行时才知**，与池键在模板文本里无法区分 ⇒ 「`$.x` 必须在池里」这种正向检查会大面积误报，warning 泛滥后连带 T2 一起被无视。所以只做**形态封闭**的 `$.pool.` 前缀校验。

**展平键层（默认不做）**：理论上可静态枚举前序各步骤 `response_param_template` 的**顶层键名**（该模板「键名静态、值动态」，`{"applyNo":"$.data.applyNo"}` 的键名固定），但遇到 `@array@` / 值为整对象 / 空模板时枚举会不完整，**一次不完整的枚举就是一次误报**。故不默认开启。

**运行时护栏（已有开关，不改代码）**：`ifmap.template.null-policy` 支持 `skip-field`（默认，静默丢字段 + 一条 `log.warn`）/ `empty-string` / **`fail`**（`TemplateEngine:304-305` 抛 `IfmapConfigException("模板字段 [...] 取值为空（表达式：…）")`，已实现）。它是唯一能覆盖「展平键取不到」的护栏，但是**全局**开关（同进程所有模板受影响，合法的可选字段也会抛）⇒ 只作为「多步池编排场景的推荐配置」写进文档，不默认打开。

### 4.7 前后序策略

**SPI 复用**：`SpecialDealStrategy.apply(StrategyContext) -> Map<String,Object>`（`null`/空 = 不改动）。

| | 前序（`pre_strategy_name`） | 后序（`post_strategy_name`） |
| --- | --- | --- |
| 执行位置 | 渲染后、出网前（**现状不变**） | `renderResponse` 后、判定前（**新增**） |
| 入参可见 | `params`、`requestJson`、`config`、`request` | 前 + `responseJson`、`responseData` |
| 返回值去向 | 合并进 `params` → **重渲染**请求模板 | 合并进 `data`（该步产物） |
| 可做的额外动作 | 改 `params` | `setResponseData(...)` 整体替换 `data` |
| 能否影响成功判定 | 间接（改请求 ⇒ 影响回参） | **不能**（判定读原始回参） |
| 缺失时 | `failOnMissingStrategy`（默认 true）抛 `IfmapStrategyException`；false 则 WARN + 跳过 | 同左 |

**`phase`**：`StrategyContext` 新增 `phase`（`PRE`/`POST`），使一个策略类挂两列时能自辨。

**注册与发现零改动**：`IfmapStrategyRegistrar` 按 bean 名注册 `SpecialDealStrategy`，前后序共用同一注册表；admin 的 meta 清单（「已注册策略」）语义不变，只是被两列共用。

**后序策略错误的处理**：与现状前序一致 —— 异常向上抛（`applySpecialDeal` 也没有 try/catch），不新增吞异常路径。

| R1 | `ConfigRepository` 加方法是**破坏性 SPI 变更**（无默认实现，宿主必须补） | CHANGELOG + docs/06 §11 + docs/11 明确标注；`CachingConfigRepository` 委托实现给出参考 |

## 8. 参照项目对照（取舍依据）

| 参照项目（`base-svc-ai`） | 本设计 | 取舍 |
| --- | --- | --- |
