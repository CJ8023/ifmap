# 参与贡献

欢迎提 Issue / PR。本页写清本仓库的**硬性约定**：不按约定来的 PR 会被直接退回，
不是因为格式洁癖，而是下面每一条都对应过真实事故（见各条结尾的"为什么"）。

## 1. 开发环境

| 需求 | 说明 |
| --- | --- |
| JDK | **至少两个**：JDK 8（core/仓储的字节码目标）与 JDK 17（Spring Boot 3 模块）。JDK 11/21 也应能构建 |
| Maven | 3.9.x（`mvn` 必须能联网；本地仓库不完整时离线构建不可行） |
| 数据库 | 单测用 **H2 内存库**（`MODE=MySQL`），无需 Docker/MySQL；真库只做人工验证 |

```bash
# JDK 17：全量（含 SB3 模块 + 静态分析）
JAVA_HOME=/path/to/jdk17 mvn -B -ntp clean verify

# JDK 8：去掉 SB3 模块（由父 POM 的 <jdk>[17,)</jdk> 剖面自动装卸），也不跑 SpotBugs
JAVA_HOME=/path/to/jdk8  mvn -B -ntp clean verify
```

> Spring Boot 3 相关模块（starter / admin-starter / demo-sb3）在 JDK 8/11 上**不参与构建**，
> 这是父 POM 的 `<profile><activation><jdk>[17,)</jdk>` 干的，所以 `mvn test` 在 JDK 8 上不会
> 因为 `release=17` 报错，也不需要你在 CI 里写分支。

## 2. 开发流程（TDD）

1. **先写测试并看它红**：新功能/修 bug 都必须先有一条失败的测试。修 bug 时，
   把"能复现该 bug 的断言"写进去 —— 且**验证过**它在旧代码上是红的（否则你只是写了个安慰剂）。
2. **再写实现**：让测试变绿，只写刚好够的代码。
3. **最后跑全量**：`clean verify`（JDK 17）+ `clean test/verify`（JDK 8）都绿，才算完工。
4. 用 **`clean`**：`maven-compiler-plugin` 的增量编译会误判 "Nothing to compile"，
   本仓库多次因此出现"改了代码测试却还是旧结果"。带 `-Dtest=某类` 时加
   `-Dsurefire.failIfNoSpecifiedTests=false`，否则其它模块会因"没有匹配测试"失败。

## 3. 代码约定

| 约定 | 为什么 |
| --- | --- |
| `ifmap-core` 只允许依赖 `slf4j-api`（零 JSON 库、零 Spring） | core 要在任意宿主里跑；JSON 通过 `JsonOps` SPI 注入 |
| `ifmap-core` 的 `maven.compiler.release=8`；SB3 模块 `17` | 两套 JDK 都要能编；改动 core 时别用 Java 9+ API |
| 面向宿主的**新 API 一律 `String`**，不要 `Object` | 配置里全是字符串；`Object` 会把类型判断推给调用方 |
| 模板/规则求值的异常语义：只有"路径不存在"算正常空值，其他异常一律抛 `IfmapConfigException` | 静默吞异常会让配置错误在线上变成"字段莫名变空" |
| 类里的"包装类型 `==`"零容忍 | 真踩过：`Integer` 顺序号用 `==` 比较，顺序号 ≥128 时唯一键校验静默失效（在 `-128..127` 缓存范围内才碰巧对）。用 `equals`/`Objects.equals` |
| 构造器只做"马上会炸的校验"，不做 IO | 启动期快速失败是对的，但把慢操作放构造器里会让装配阶段难以排障 |

## 4. 测试约定

- **不往生产类加 test-only 方法**：测试要用生产路径（例如 `IfmapSchemaInitializer.afterPropertiesSet()`
  建表），不要为了好测而在生产类里开洞。
- **H2 不等于 MySQL**：`json` 列在 H2 1.4.200 上没有 MySQL 的语义，测试建表要把 `json` 降级为 `text`
  （`TestSchema`/`IfmapSchemaInitializer` 里已有断言式实现，别绕过）。
- **不要用 `sleep` 等异步结果**：轮询 + 超时（例如日志清理的 cron 用例），否则 CI 上必抖。
- **示例值必须有测试兜住**：文档里写的 `@FUN` 入参/出参、脱敏前后结果，都要有 `assertEquals`
  钉住；只靠手算一定会写错（真踩过）。
- **测试类里反射要用的规则承载类**，必须放在 `public class` 里（否则反射拿不到）。

## 6. 质量门禁

`mvn verify` 会跑 **SpotBugs**（`effort=Max`、`threshold=Medium`，绑定 `verify` 阶段；
**JDK 11+ 才启用**，因为 SpotBugs 4.8.x 运行时要求 Java 11；临时跳过用 `-Dspotbugs.skip=true`）。
跑不动/跑不过不算完事，见下面两条：

1. **能改就改**，不要往排除清单里塞。W7 就是这么处理掉 5 处真问题的（`Integer` 引用比较、
   `Date` 未做副本、比较器不可序列化、两处集合直接外泄）。
2. 确实要排除时，只放**规则族级**的排除，并在 `spotbugs-exclude.xml` 里写清"为什么这一族在本项目
   天然误报"。目前放行了三族：`EI_EXPOSE_REP*`（SPI 契约就是共享可变协作者，逐次深拷贝会破坏语义）、
   `CT_CONSTRUCTOR_THROW`（启动期快速失败是刻意设计）、`MS_SHOULD_BE_FINAL`（刻意暴露的可调开关）。

   ⚠️ 放行规则族意味着**将来真写出这类缺陷 SpotBugs 不会再拦**，所以人工 review 必须补：

   - [ ] 新增的**对外 DTO / 查询结果 / 快照**是否"拷贝 + 不可变视图"（参照 `IfmapResult`、`PageResult`、
         `IfmapConfigHistory`）？别把内部集合直接 `return`。
   - [ ] 新增/修改的 `Integer`/`Long`/`Boolean` 比较是否都走了 `equals`？
   - [ ] 新增的公开静态可变字段是否真有必要（优先改成常量或构造器注入）？

## 7. 文档约定

- 新仓文档用 **LF + UTF-8 无 BOM**（`git` 侧已由 `.gitattributes` 固定为 `eol=lf`）。
- **Markdown 表格单元格内不能插段落**（含 `>` 引用），会直接把表格拆掉。
- 数值口径必须写清"怎么数的"并给复现命令（例如"28 列 = DDL 里声明的列数，不含索引"，复现：
  ``grep -cE '^  `[a-z_]+` +[a-z]' 001-create-ifmap-config.sql``）。
- 代码块里的命令若含反引号，用**双反引号定界**（CommonMark 的代码跨度里反斜杠转义无效）。
- 改了行为就同步三处：对应 `docs/0X-*.md`、`CHANGELOG.md` 的 `Unreleased`、受影响模块的 README 断言。

## 8. 文档站

```bash
py -m pip install mkdocs-material      # 或 python3 -m pip
py -m mkdocs serve                     # 本地预览 http://127.0.0.1:8000
py -m mkdocs build --strict            # 与 CI 相同的严格构建（警告即失败）
```

`mkdocs.yml` 里 `exclude_docs` 排除了内部文档：它们在开发机上存在但不进公开仓，
不排除的话本地 `--strict` 会因为"文件不在 nav 里"直接失败。

## 9. 提交与 PR 检查表

- [ ] commit message 用 `feat|fix|docs|test|chore(范围): 摘要`，正文说清"为什么"（不是"改了什么"）。
- [ ] 分支：功能分支 → PR 到 `main`；不要直接推 `main`（维护者自己发版除外）。
- [ ] JDK 17 `clean verify` 与 JDK 8 `clean verify` 都绿（贴日志或 CI 链接）。
- [ ] 新增/修改的行为有测试；bugfix 有"旧代码会红"的证据。
- [ ] `git status --short` 里没有内部文档、`target/`、IDE 文件。
- [ ] 文档与 `CHANGELOG.md` 已同步；新增配置项在 `docs/05` / `docs/08` 的配置表里都补了。
- [ ] 若放行了新的 SpotBugs 规则族 —— 先按上面"人工 review 三条"自查。
