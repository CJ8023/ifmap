## 2. 模块地图

11 个 Maven 模块，`groupId=cn.cj`，版本 `0.1.0-SNAPSHOT`，**JDK 8 / JDK 17 双栈构建**。

```
                     ifmap-core            ← 零框架依赖的执行内核（本文档集的重点）
                    ╱    │     ╲
        ifmap-json-*   ifmap-testkit   （core 只依赖 JsonOps 抽象）
           ╱    │  ╲
 json-jackson  json-fastjson  json-tck
        ╲______│_______╱
               │
     ifmap-provider-jdbc / ifmap-provider-remote   ← ConfigRepository 的两个实现
               │
     ifmap-spring-boot-starter                    ← 自动装配 + 属性 + 生命周期
               │
 ifmap-admin-spring-boot-starter                  ← 管理端 REST + 内嵌 UI（唯一 Web 层）
               │
  ifmap-demo-pure-java / ifmap-demo-spring-boot3  ← 两个最小可运行样例
```

**依赖方向是单向的**（下依赖上，箭头只是示意）：`core` 不依赖 Spring / Jackson / JDBC，
所有外部能力都通过 `cn.cj.ifmap.core.spi` 下的接口或工厂倒置出去。这条约束是
`ifmap-json-tck`（JSON 能力一致性测试）和「纯 Java 接入」（`demo-pure-java`）能存在的前提。

| 模块 | 文件数 / 行数 | 职责（一句话） |
|---|---|---|
| `ifmap-core` | 119 / 14,986（main 92 / 10,698） | 引擎全部逻辑：模板渲染、规则、编排、判定、策略、SPI 抽象 |
| `ifmap-json-jackson` | 8 / 794 | `JsonOps` 的 Jackson 实现（默认绑定） |
| `ifmap-json-fastjson` | 11 / 1,246 | `JsonOps` 的 fastjson 实现（存量系统用得多） |
| `ifmap-json-tck` | 4 / 882 | 与实现无关的 JSON 能力一致性测试基类（Jackson / fastjson 都继承它） |
| `ifmap-testkit` | 3 / 1,153 | 测试替身：内存 `ConfigRepository`、`FakeGateway`、`RecordingLogSink` 等 |
| `ifmap-provider-jdbc` | 35 / 5,097 | JDBC 版配置仓储 + 写入器 + DDL + 真库集成测试 |
| `ifmap-provider-remote` | 6 / 1,557 | 从远端 HTTP 拉配置的 `ConfigRepository` 实现（含 JSON → 配置映射） |
| `ifmap-spring-boot-starter` | 13 / 3,055 | `ifmap.*` 属性、自动装配、启动期契约校验、健康指标 |
| `ifmap-admin-spring-boot-starter` | 43 / 7,357 | 管理端 REST（`/ifmap/admin/**`）+ 内嵌单页 UI（零 CDN / 零构建链） |

| `ifmap-demo-spring-boot3` | 9 / 484 | Spring Boot 3 接入样例（本项目本地启动管理端就是跑它） |

> 总规模约 **252 文件 / 3.67 万行**（含测试）。`ifmap-core` 的 92 个 main 文件是本系列
> 优先精读对象 —— 其余模块大多是「装配壳」或「IO 适配」，逻辑密度低一个数量级。

## 3. 主链路：一次 `execute` 到底发生了什么

入口是 `IfmapOrchestrator.execute(request, interfaceNo, busiNode)`（`orchestrator/IfmapOrchestrator.java:134`）。
下面按执行顺序列出每一段的责任人；**带 ⚠ 的是容易踩的点**，详情见后续篇章。

```
execute(req, interfaceNo, busiNode)
 │
 ├─1 租户解析    tenantResolver.resolve(req)                        :134 → 135
 │             ⚠ 缓存 key 必须含租户；单租户约定传 "-1"
 │
 ├─2 加载执行计划 loadPlan(tenantId, interfaceNo, busiNode)          :179
 │     repository.queryConfigsByBusiNode(...)                       :180 附近
 │     InterfaceOrdering.enabled(...) 过滤 + sort(...)              :180 附近
 │     ⚠ 顺序只有一个来源 interface_order；起点 interfaceNo 必须在计划里，否则 IfmapConfigException
 │
 ├─3 顺序执行    runPlan(...)                                        :202
 │     for each config:
 │       ├─3.1 executeOne(req, tenantId, config, mockResponse)       :247
 │       │    ├─ 主参数组包   fullParamStrategyRegistry.assemble     :260 附近
 │       │    │   来源 = params ← payload ← 跨步骤共享池(pool)        :435 initialPool / :453 flattenPool
 │       │    ├─ 方向分流     call_direction == INBOUND ?             :266
 │       │    │   INBOUND：不渲染请求模板、不跑前序策略、不出网（原文即回参）:268
 │       │    ├─ 请求渲染     render(config.requestTemplate, ...)     :273（走 TemplateEngine）
 │       │    ├─ 前序策略     applyPreStrategy(ctx, ...)             :314
 │       │    │   ⚠ 返回值合并进 params 后**重渲染请求**
 │       │    ├─ 出网         gateway.exchangeForOutcome(call)       :474 exchange(...)
 │       │    ├─ 响应渲染     renderResponse(...)                    :497
 │       │    ├─ 后序策略     applyPostStrategy(ctx, data)           :351
 │       │    │   ⚠ 只改产物 data / 入池；判定仍读**原始回参**
 │       │    ├─ 判定         pipeline.judge(config, response, out)  JudgementPipeline
 │       │    │   四段：传输 → 业务 → 抽取 → 分类
 │       │    ├─ 成功入池     pool.put(interfaceNo, data)            ⚠ 判定成功才入池
 │       │    ├─ 逻辑分支     applyBranch(...)                       :522 → executeBranch :558
 │       │    └─ 落执行日志   writeLog(..., judgement, elapsed)       :613
 │       └─ 失败且 stopOnFailure → 提前结束（默认 true）              :224 之后
 │
 └─4 汇总成 IfmapResult（步骤产物 + 失败归因）
```

### 3.1 判定管线的四段

判定是本项目最容易写错的地方，因为它有**四层**分工，且只有第一层能推翻后面全部结论：

| 段 | 责任人 | 输入 | 输出 | 规则 |
|---|---|---|---|---|
| ① 传输 | `JudgementPipeline.judge` | `PartnerOutcome` | 直接返回失败 | 超时 / 非 2xx → `TIMEOUT` / `HTTP_4XX` / `HTTP_5XX`，**不进规格求值** |
| ② 业务 | `ResultJudge.judge`（默认 `RuleSpecJudge`） | `result_judge` 规格 + 原始回参 | `Judgement` | fail-closed：规格非法 `SPEC_INVALID`、非 JSON `NOT_JSON`、取不到 `FIELD_MISSING`、没命中 `VALUE_MISMATCH` |
| ③ 抽取 | `ResponseExtractor` | 原始回参 | `message` / `trackId` | **只补信息，不改结论** |
| ④ 分类 | `JudgeFailType` 枚举 | — | `fail_type` 列 | 闭合枚举，仅用于排障，**不驱动重试/熔断** |

## 4. `ifmap-core` 的包结构

| 包 | 一句话 | 关键约束 |
|---|---|---|
| `cn.cj.ifmap.core` | `IfmapEngine`：对外唯一门面 | 只做「注册表 + 模板引擎」装配，不含编排 |
| `…core.template` | 模板 DSL 解析与渲染 | 存量逐字兼容的 `@array` / `@or@` / `@FUN(` 记号都在 `TemplateConstants` |
| `…core.rule` | 规则注册、方法解析、参数强制转换 | 同名方法默认**重载**，`override=true` 才整体替换 |
| `…core.rule.builtin` | 内置规则实现（字符串/数字/日期/字典/集合） | 纯函数、无状态、不抛未声明异常 |
| `…core.orchestrator` | 执行编排 + `Judgement` 值对象 | 顺序只有 `interface_order` 一个来源 |
| `…core.orchestrator.judgement` | 四段判定管线与规格 DSL | 判定器**不允许抛异常** |
| `…core.strategy` | 策略钩子 / 主参数组包 / 逻辑分支 / 动作 | 全部**按名注册**，注册 key 与配置列对齐 |
| `…core.config` | 配置与日志的模型 + 仓储接口 | 仓储接口的方法**排序契约写在 javadoc 里** |
| `…core.cache` | 配置缓存装饰器 | key **必须含租户维度** |
| `…core.model` | 请求 / 结果 / 出网入参值对象 | 三个 Map 都是不可变视图 |
| `…core.spi` | 15 个对外扩展点 | 默认实现都能让「纯 Java」跑起来 |
| `…core.json` | `JsonOps` 抽象 + 持有器 + 读上下文 | core 对 JSON 库**零依赖** |
| `…core.validate` | 启动期契约自检（模板/规则/判定） | 只报告，不阻塞启动（除非显式开启） |
| `…core.util` | 小工具：`Text` / `Values` / `Logs` / `Annotations` | 无状态、静态、无第三方依赖 |
| `…core.exception` | 异常族（7 个 + 1 个启动校验） | 全部 `RuntimeException`，`IfmapException` 为根 |

## 6. 三个「必须先知道」的隐性约定

1. **顺序只有一个来源**：`interface_order`。早期设计里的拓扑排序层（环检测、深度护栏、
   4 类校验）已整体删除，任何「按前置接口推导顺序」的想法都要先回到设计文档讨论。
2. **池只在判定成功时写入**：`payload.pool` 是预置池入口，正式池按「本步判定成功 → 入池」
   的规则累积，失败步骤不会污染后续步骤的入参。
3. **前后序策略都不改变成败判定**：判定永远读**对方原始回参**，后序策略只改本步产物。

## 7. 维护约定（本系列文档）

- **只写行号区间 + 一句话**，不复制代码：复制会立刻过期，行号区间过期时只需重排数字。
- **代码改动后**：改了某段逻辑的边界（新增/删除分支、方法搬家）时，同步更新对应表格；
  纯内部重写不影响行号区间语义的，可不动。
- **不做逐行注释**：3.6 万行逐行加注释的维护成本远高于收益，且注释与代码不一致时
  比没有注释更糟。这里的口径是「每个文件 → 职责 / 行号区间表 / 每个方法一行 /
  重要分支与坑逐条」。
- **发现文档与代码不一致**：以代码为准，并在表格里注明「代码现状」，不要顺手改代码。
