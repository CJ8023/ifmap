## 1. 建表：四种方式

### 1.0 Spring Boot 3：引 starter 自动建表（最省事）

```xml
<dependency>
  <groupId>cn.cj</groupId>
  <artifactId>ifmap-spring-boot-starter</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>
```

```yaml
ifmap:
  table-prefix: ifmap_     # 复用存量表时填 bankint_
  ddl:
    auto: true             # 默认即 true：启动时表不存在才建，已存在则跳过
```

starter 执行的就是 `db/changelog/v1.0.0/*.sql` **这份生产脚本本身**（按 `ifmap.table-prefix` 替换 `${tablePrefix}`），
因此与下面三种方式建出来的表结构完全一致。生产建议由 DBA 建好后置 `ifmap.ddl.auto: false`。
非 MySQL 库（如 H2）会自动剥掉表尾 MySQL 表选项、并把 `json` 列降级为 `text`（H2 的 `JSON` 类型不能用 JDBC 字符串写入）以适配方言，细节见 [`docs/05-SpringBoot集成.md`](05-SpringBoot集成.md) §5.1。

### 1.1 Liquibase 自动建表

把 `ifmap-provider-jdbc` 加入依赖后，指定主 changelog：

```yaml
# application.yml（Spring Boot 3）
spring:
  liquibase:
    change-log: classpath:db/changelog/db.changelog-master.yaml
    parameters:
      tablePrefix: ifmap_        # 默认值；复用存量表时填 bankint_
```

主 changelog 用一个 `tablePrefix` 参数驱动全部脚本，四个 changeset 顺序执行：

| changeset | 表 |
| --- | --- |
| `caijun:001-create-ifmap-config` | `ifmap_config`（接口配置主表） |
| `caijun:002-create-logic-branch` | `ifmap_logic_branch_config`（逻辑分支） |
| `caijun:003-create-execution-log` | `ifmap_execution_log`（执行日志） |
| `caijun:004-create-config-history` | `ifmap_config_history`（变更历史） |

### 1.2 手工执行 SQL（不用 Liquibase）

把 `db/changelog/v1.0.0/*.sql` 里的 `${tablePrefix}` 全局替换为实际前缀，去掉 `--liquibase` / `--changeset` 注释行后执行即可。
四个文件都是**纯 `CREATE TABLE`**，不依赖 Liquibase 运行时特性。

### 1.3 复用存量表（灰度共存）

存量系统已有 `bankint_config` 等同结构表时，**不要**改表名，直接把前缀指过去：

```java
ConfigRepository repo = new JdbcConfigRepository(dataSource, "bankint_");
```

前缀合法性在构造时校验：**只允许 `[A-Za-z0-9_]*`、长度 ≤ 32**，否则抛 `IfmapConfigException`
（前缀会直接拼进 SQL，必须挡住 `ifmap_config; DROP TABLE x;--` 这类输入）。

## 2. 仓储接入

### 2.1 Spring Boot 3 / Spring 5（手工声明 Bean）

> Spring Boot 3 项目**不需要**这一节：引 `ifmap-spring-boot-starter` 即自动装配（见 [`docs/05-SpringBoot集成.md`](05-SpringBoot集成.md)）。
> 下面适用于非 Spring Boot 3 的场景：Spring 5 / 手工装配 / 想在 Boot 3 里自己做精细控制。

```java
@Configuration
public class IfmapJdbcConfig {

    @Bean
    public ConfigRepository configRepository(DataSource dataSource) {
        return new JdbcConfigRepository(dataSource);      // 默认前缀 ifmap_
    }

    @Bean
    public JdbcConfigWriter configWriter(DataSource dataSource) {
        return new JdbcConfigWriter(dataSource);          // 仅管理端使用
    }
}
```

`ifmap-provider-jdbc` 默认依赖 `spring-jdbc 5.3.x`（JDK8 + Spring 5 兼容）。
Spring Boot 3 项目请覆盖版本（`spring-jdbc` 6 与 Spring 6 同族，无 `javax` 依赖冲突）：

```xml
<properties>
  <spring-jdbc.version>6.2.11</spring-jdbc.version>
</properties>
```

### 2.2 纯 Java（非 Spring）

```java
// 任何 DataSource 都行（HikariCP / Druid / 容器 JNDI）
HikariDataSource ds = new HikariDataSource();
ds.setJdbcUrl("jdbc:mysql://127.0.0.1:3306/ecc?useUnicode=true&characterEncoding=utf8");
ds.setUsername("app");
ds.setPassword("******");

ConfigRepository repo = new JdbcConfigRepository(ds);
```

`JdbcTemplate` 已是全局线程安全对象，无需池化仓储实例。

### 2.3 自行托管 JdbcTemplate（已有 Spring 配置）

```java
ConfigRepository repo = new JdbcConfigRepository(
        jdbcTemplate,                       // 宿主自己的 JdbcTemplate（可带自定义异常翻译器）
        TableNameResolver.defaults(),       // 或 new TableNameResolver("bankint_")
        SnowflakeIdGenerator.shared());     // 或 IdGenerator.AUTO_INCREMENT
```

## 3. `ConfigRepository` 契约

| 方法 | 返回 | 由实现保证的语义 |
| --- | --- | --- |
| `queryConfigs(tenantId, interfaceNo, busiNode)` | `List<IfmapConfig>` | 只含 `del_status=0 AND status=1`；按 `interface_order` 升序 |
| `findConfig(tenantId, interfaceNo, busiNode, order)` | `Optional<IfmapConfig>` | 精确命中某条顺序；不存在返回空 |
| `queryLogicBranches(tenantId, interfaceNo)` | `List<LogicBranchConfig>` | 只含 `del_status=0`；按 `logic_branch_order` 升序 |
| `saveExecutionLog(ExecutionLog)` | `void` | 写入执行日志；`keyId` 为空时由 `IdGenerator` 生成并**回写**到入参对象 |

两个容易被忽略的点：

1. **顺序由 SQL 保证**，不依赖数据库的返回顺序（明文写进接口契约，避免"换数据库就乱序"）。
2. **租户是字符串**：`null` / 空串按单租户默认值 `-1` 处理；**非数字字符串直接抛异常**，绝不静默查错租户。

## 4. 软删除与唯一键（`deleted_seq`）

### 4.1 问题

`uk_(tenant_id, interface_no, busi_node, interface_order, deleted_seq)` 是唯一键。如果软删除只是把
`del_status` 置 1，那么"删掉一条再建同顺序的新配置"会撞唯一键 —— 这是存量表最典型的运维事故。

### 4.2 方案

| 状态 | `del_status` | `deleted_seq` |
| --- | --- | --- |
| 未删除 | `0` | `0` |
| 已删除 | `1` | `key_id`（即本行主键） |

删除语句是**单条原子 UPDATE**，不存在"先查后改"的竞态：

```sql
UPDATE `ifmap_config`
   SET `del_status` = 1, `deleted_seq` = `key_id`, `version` = `version` + 1,
       `modify_user_id` = ?, `modify_time` = CURRENT_TIMESTAMP(3), `modify_request_id` = ?
 WHERE `key_id` = ? AND `del_status` = 0;
```

对应 API：

```java
boolean deleted = writer.softDelete(keyId, "zhangsan", "REQ-20260930-001");
```

| 返回值 | 含义 |
| --- | --- |
| `true` | 本次删除成功 |
| `false` | 目标不存在或已删除（**幂等**，重复调用不报错） |

因为 `deleted_seq` 取的是**各不相同的主键**，同一 `(租户, 接口, 节点, 顺序)` 可以被删除 → 重建 → 再删除 → 再重建**无限次**，
每次历史行都还在库里（可追溯）。

### 4.3 唯一键的作用域（实测结论）

唯一键维度是「**租户 + 接口编号 + 业务节点 + 顺序**」：

| 场景 | 结果 |
| --- | --- |
| 同租户 + 同接口 + 同节点 + 同顺序，再来一条 | ❌ 唯一键拦截（抛 `IfmapConfigException`） |
| 同租户 + 同接口 + **不同节点** + 同顺序 | ✅ 允许（每个业务节点各自一组接口链） |
| 软删除后再建同顺序 | ✅ 允许（`deleted_seq` 已变） |

## 5. 乐观锁（`version`）

管理端"打开编辑页 → 保存"之间可能已有人改过，直接覆盖会静默丢更新。写操作要求带上读到的版本号：

```java
IfmapConfig edit = writer.findByKeyId(keyId).orElseThrow();
edit.setRequestParamTemplate(newTemplate);

boolean ok = writer.update(edit, edit.getVersion(), "zhangsan", "REQ-001");
if (!ok) {
    throw new BizException("配置已被他人修改，请刷新后重试");
}
```

| 细节 | 说明 |
| --- | --- |
| 语句 | `UPDATE ... SET ..., version = version + 1, modify_time = CURRENT_TIMESTAMP(3) WHERE key_id = ? AND version = ? AND del_status = 0` |
| `false` | 版本不匹配（或行已删除），**数据保持原样**，提示用户刷新 |
| 不覆盖的字段 | `del_status` / `deleted_seq` / `add_*` 一律不动（软删除只走 `softDelete`） |
| 唯一键冲突 | 更新时改了 `(节点, 顺序)` 撞车 → 抛 `IfmapConfigException` 并提示维度 |
| 时间 | `modify_time` 由写入方显式赋值，DDL **不写 `ON UPDATE`**（避免"每次触碰都改时间"干扰审计） |

## 6. 执行日志

```java
ExecutionLog log = ExecutionLog.success("czb-apply-01", "BIZ-20260930-0001", 128L);
log.setTenantId(1001L);
repo.saveExecutionLog(log);
// log.getKeyId() 已回写，可直接用于回执/关联
```

| 成员 | 常量 | 说明 |
| --- | --- | --- |
| `executionResult` | `SUCCESS` / `FAIL` / `SKIP` / `TIMEOUT` | `ExecutionLog.success(...)` / `ExecutionLog.fail(...)` 工厂方法 |
| `executionTime` | — | 毫秒 |
| `errorMsg` | — | 失败原因（写入方负责截断到 1024） |
| `requestParam` / `responseParam` | — | **必须脱敏后**再落库 |

排障查询（非引擎链路，供运维用）：

```java
List<ExecutionLog> logs = ((JdbcConfigRepository) repo).recentLogs("1001", "BIZ-20260930-0001", 20);
```

### 6.1 日志清理策略

| 方案 | 说明 |
| --- | --- |
| **默认：分批 `DELETE`** | 按 `add_time` 保留 N 天，每天小批量删除（避免长事务与主从延迟） |
| 可选：按月分区 | `db/mysql8/partition-execution-log.sql`（**默认不启用**，需把主键改为 `(key_id, add_time)`，归档 = `DROP PARTITION`） |

## 7. 主键 ID 策略

| 策略 | 配置 | 说明 |
| --- | --- | --- |
| **雪花（默认）** | `IdGenerator` 默认 `SnowflakeIdGenerator.shared()` | 结构 `0 \| 41 位毫秒 \| 10 位 workerId \| 12 位序列号`，纪元 2020-01-01 |
| `AUTO_INCREMENT` | `IdGenerator.AUTO_INCREMENT`（`nextId()` 返回 `null`） | 建表时把 `key_id` 改成 `AUTO_INCREMENT`；此时**必须**由数据库生成主键，代码侧传 `null` 会抛 `IfmapConfigException`（避免写出空主键） |
| 自定义 | 实现 `IdGenerator` | 如接入宿主已有的发号器 |

### 7.1 workerId 部署要点

**同一时刻多实例的 workerId 必须互不相同，否则会生成重复 ID。** 取值优先级：

1. JVM 参数 `-Difmap.worker-id=12`
2. 环境变量 `IFMAP_WORKER_ID=12`
3. 都未配置 → `0`（**多实例部署必须显式配置**）

K8s 可用 StatefulSet 序号注入；非 StatefulSet 可用 `SnowflakeIdGenerator.workerIdFromHostname(hostname)`（按主机名取模）。

> 仓储默认用的是 `SnowflakeIdGenerator.shared()` **JVM 单例**。切勿自己反复 `new SnowflakeIdGenerator(0)`
> —— 每个实例的序列号独立，同一毫秒内会撞 ID。

### 7.2 时钟回拨

| 回拨幅度 | 行为 |
| --- | --- |
| ≤ 5ms（`MAX_BACKWARD_MS`） | 自旋等待时钟追上后继续生成 |
| > 5ms | 抛 `IfmapConfigException`（宁可失败，也不产生可能重复的 ID） |

## 8. 表结构速查

> **列数口径**：下表的"列数"是 **DDL 中声明的列数**（含审计列，不含索引），复现：
> ``for f in ifmap-provider-jdbc/src/main/resources/db/changelog/v1.0.0/*.sql; do echo "$(basename $f): $(grep -cE '^  `[a-z_]+` +[a-z]' $f) 列"; done``
> 实测：`001`=28、`002`=17、`003`=17、`004`=11。
> 实体类字段数少于列数是**有意**的：审计列（`add_*` / `modify_*`）不由引擎读取，
> 例如 `LogicBranchConfig` 只有 11 个字段（映射器也只取这 11 列的 SQL）。

### 8.1 `ifmap_config`（28 列）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `key_id` | `bigint` PK | 主键（默认雪花） |
| `tenant_id` | `bigint` NOT NULL DEFAULT -1 | 单租户固定 `-1` |
| `interface_no` | `varchar(64)` | 接口编号（业务唯一键之一） |
| `interface_code` | `varchar(64)` | 对接方接口编码 |
| `project_code` | `varchar(64)` | 项目编号 |
| `interface_name` | `varchar(128)` | 接口名称 |
| `busi_node` | `varchar(32)` | 业务节点（取值由宿主机注册） |
| `bank_code` / `bank_name` | `varchar(32)` / `varchar(128)` | 资方编码 / 名称 |
| `financing_mode` | `varchar(32)` | 融资模式 |
| `front_interface_no` | `varchar(64)` | 前置接口编号（空 = 无前置） |
| `interface_order` | `smallint` DEFAULT 0 | 执行顺序，升序 |
| `request_param_template` | `text` | 请求模板（DSL） |
| `response_param_template` | `longtext` | 响应模板（DSL） |
| `result_flag` | `varchar(512)` DEFAULT '' | 结果判定 JsonPath |
| `success_value` | `varchar(512)` DEFAULT '' | 成功值，多值以 `\|` 分隔 |
| `strategy_name` | `varchar(128)` DEFAULT '' | 特殊处理策略（= Spring bean 名） |
| `status` | `tinyint(1)` DEFAULT 1 | 1 启用 / 0 停用 |
| `version` | `int` DEFAULT 0 | 乐观锁 |
| `remark` | `varchar(512)` DEFAULT '' | 备注 |
| `del_status` | `tinyint(1)` DEFAULT 0 | 0 未删 / 1 已删 |
| `deleted_seq` | `bigint` DEFAULT 0 | 软删除唯一化 |
| `add_user_id` / `add_time` / `add_request_id` | `varchar(64)` / `datetime(3)` / `varchar(40)` | 创建审计 |
| `modify_user_id` / `modify_time` / `modify_request_id` | 同上 | 修改审计 |

索引：

| 名称 | 列 |
| --- | --- |
| `uk_ifmap_config_biz` | `(tenant_id, interface_no, busi_node, interface_order, deleted_seq)` |
| `idx_ifmap_config_list` | `(tenant_id, del_status, busi_node, bank_code)` |
| `idx_ifmap_config_front` | `(tenant_id, del_status, front_interface_no)` |
| `idx_ifmap_config_code` | `(tenant_id, del_status, interface_code)` |

### 8.2 `ifmap_logic_branch_config`（17 列）

关键列：`interface_no`、`method_flag`（动作标识，指向宿主机 `ActionRegistry`；空 = 默认兜底分支）、
`logic_branch_name`、`logic_branch_flag`（JsonPath）、`logic_branch_value`（多值以 `|` 分隔）、
`logic_branch_order`（升序，先命中先生效，兜底分支应设为最大）+ 审计/软删除列。

> 迁移口径：存量 `bankint_logic_branch_config`（15 列）**只有列名原样保留**（含 `method_flag`）；
> ifmap 版本新增 `logic_branch_order`（分支顺序，替代原先靠 `key_id` 顺序的隐式约定）与 `modify_request_id`，
> 故迁移是 `ALTER TABLE ... ADD COLUMN` 而不是纯改名。

### 8.3 `ifmap_execution_log`（17 列）

`key_id`、`tenant_id`、`interface_no`、`biz_id`、`request_param`(json)、`response_param`(mediumtext)、
`execution_time`、`execution_result`、`error_msg`、`remark` + 审计列。

### 8.4 `ifmap_config_history`（11 列）

`config_key_id`、`change_type`(`CREATE`/`UPDATE`/`DELETE`/`ENABLE`/`DISABLE`)、`change_reason`、
`snapshot`(json)、`diff`(json) + 审计列。**由管理端模块写入**（`ifmap-admin-spring-boot-starter`，见 [`docs/07-管理端REST.md`](07-管理端REST.md)），本模块只提供建表。

## 9. 排错与踩坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `Column 'xxx' cannot be null`（MySQL 严格模式）/ H2 `NULL not allowed for column` | 向 `NOT NULL DEFAULT ''` 列**显式**写入 `null`。SQL 默认值**只在省略该列时**生效 | 已由 `JdbcValues.orEmpty(...)` 在写入前统一归一化为 `''`；自定义 SQL 时注意同一坑 |
| 启动报 `表名前缀不合法` | 前缀含 `-`、空格、分号或超长 | 只用 `[A-Za-z0-9_]`；否则改用 `ifmap_` |
| 管理端保存"看起来成功但没变" | 乐观锁返回 `false` 被忽略 | 必须判断 `update(...)` 返回值并提示刷新 |
| 唯一键冲突 | 同 `(租户, 接口, 节点, 顺序)` 已有未删除配置 | 先停用（`status=0`）或删除旧配置；不要靠改顺序绕 |
| `datetime(3)` 写入变整秒 | 驱动/连接串未开启毫秒精度 | 无需特殊配置；若表由旧脚本建的 `datetime`（无精度），需 `ALTER` 到 `datetime(3)` |
| 时区导致时间少 8 小时 | 连接串未指定 `serverTimezone` | 连接串加 `serverTimezone=Asia/Shanghai`（或用 `useLegacyDatetimeCode=false` 等价的显式配置） |
| `JSON` 列建表报错 | 给 `json` 列写了**非 NULL 默认值** | JSON/BLOB/TEXT 列只允许 `DEFAULT NULL`（省略即可） |
| 5.7 上 `ALTER` 卡住/主从延迟 | 大表原生 DDL 全表重建 | 遵循发布侧《大表 ALTER 防主从延迟规范》：同表变更合并成**一条** ALTER、加 `ALGORITHM=INPLACE, LOCK=NONE`、上百万行改 gh-ost/pt-osc |
| 日志表越来越大 | 未开启清理 | 启用 `LogCleaner` 分批删除；或按 §6.1 启用分区 |

## 10. 自测方式

`ifmap-provider-jdbc` 的测试**直接执行生产建表脚本**（不是另写一份测试 DDL），在 H2 `MODE=MySQL` 下建表后跑仓储：

| 项 | 做法 |
| --- | --- |
| 建表脚本来源 | `db/changelog/v1.0.0/*.sql`（同一份文件，含索引与唯一键） |
| 唯一变换 | `TestSchema.toH2(...)` 仅剥离表尾 `ENGINE=InnoDB ... COLLATE=... ROW_FORMAT=... COMMENT='...'`（存储引擎选项）；**列定义、注释、主键、唯一键、普通索引原样执行** |
| 变换安全 | 若脚本不再匹配预期的表尾模式，测试**直接失败**（不会静默跳过校验） |
| MySQL 专属项 | `ENGINE`/`COLLATE`/`ROW_FORMAT`、`json` 在真库的行为由发布侧在 MySQL 5.7/8.0 上验证（CI 的 MySQL 集成 job 见 `.github/workflows/ci.yml`） |

本文档中出现的示例值，逐条由单元测试断言固定：

| 文档位置 | 示例值 | 断言测试 |
