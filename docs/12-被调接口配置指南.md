# 12 被调接口配置指南（对方调我方）

> 适用版本：`call_direction` 列落地之后。前置阅读：[`06-执行编排与策略扩展.md`](06-执行编排与策略扩展.md)（执行顺序、判定、分支动作）、
> [`02-模板DSL语法.md`](02-模板DSL语法.md)（模板取值与空值策略）。

## 0. 一句话

**被调接口不是"另一套引擎"**：它就是同一个业务节点里的普通一步，只是 `call_direction=INBOUND`
让这一步「不渲染请求模板、不出网」，把**对方推过来的报文原文**当作回参去判定、分流、组装应答。
所以配置、判定、分支、动作、执行日志、断点续跑全部复用，不需要宿主为每个接口写一个 handler。

## 1. 两个方向：同一引擎，两条执行路径

| 环节 | `OUTBOUND`（我方调对方） | `INBOUND`（对方调我方） |
| --- | --- | --- |
| 入参 `params` | `payload` + 主参数组包策略 + 共享池展平（`$.pool.*`） | 同左（**`payload` 非空优先**；为空时宽松解析原文当参数） |
| 请求报文 | 请求模板渲染 → 前序策略可再加工 | **跳过渲染、跳过前序策略**，直接用对方原文 |
| 出网 | `PartnerServiceGateway.exchange` | **不出网**（`PartnerOutcome.ofBody(原文)`） |
| dry-run（`mockResponse`） | 用它替代对方回参 | **同样优先**，用它替代对方原文 |
| 判定 `result_judge` | 读对方回参 | 读对方原文 |
| 产物 `response_param_template` | 渲染对方回参 | 渲染对方原文 ⇒ **就是要回给对方的应答** |
| 后序策略 / 逻辑分支 / 动作 / 执行日志 / 入池 | 一致 | 一致 |

> 方向由**配置**决定，不由方法决定：`executeInbound(...)` 只是「顺手把原文塞进 `IfmapRequest.rawBody`」的便捷入口，
> 若该配置是 `OUTBOUND`，它照样会出网。

## 2. 三个必须分清的概念

这三件事经常被混成一件，混了就会配出「判定永远成功但业务没跑」或「失败也回了 `0000`」：

| 概念 | 由什么表达 | 谁负责 | 判错的后果 |
| --- | --- | --- | --- |
| **报文可受理**（这笔推送我要不要接） | `result_judge` | 引擎（`ruleSpec`） | 太严 → 对方的正常推送被拒；太松 → 什么垃圾报文都进业务 |
| **业务结论**（接了之后算成功还是失败） | `logic_branch` + `method_flag` → `@IfmapAction` | 宿主动作 | 分支漏配 → 接了但什么也没做（`WARN` 提示，见 §8） |
| **应答报文**（回给对方什么） | `response_param_template` + 动作回填 | 宿主动作 + 模板 | 模板缺失 → 回给对方的 data 是空；动作不回填 → 业务字段缺失 |

**关键约束（引擎强制）**：`@IfmapAction` 是 `void execute(StrategyContext)`，**没有"软失败"通道**。
也就是说「受理了但业务上失败」这件事，只能靠
① 分支分流到不同的动作（`PAY_FAILED` → 记账/告警），
② 动作**原地改** `context.getResponseData()` 这个 Map（回填 `code` / `message` / `retryable`）。

## 3. 配置清单（一行一条）

| 列 | INBOUND 取值 | 说明 |
| --- | --- | --- |
| `call_direction` | `INBOUND` | 必须显式写；空值按 `OUTBOUND` 处理（存量兼容） |
| `interface_no` | 如 `RCV_LOAN_PAY` | 租户内全局唯一；也是**共享池的键**（见 §6） |
| `busi_node` | 如 `loanPayRcv` | 与出网步骤共用节点语义；同一节点内按 `interface_order` 升序执行 |
| `interface_order` | 如 `1` | 被调步骤一般排第一（见 §8 的 warning） |
| `partner_code` / `partner_name` | 如 `CMB` | 主参数组包策略按 `partner_code + busi_node` 命中，被调方向同样生效 |
| `request_param_template` | **留空** | INBOUND 不渲染它；留着会让人以为入参被加工过（保存被拦，见 §8） |
| `response_param_template` | **必填** | 回给对方的报文；渲染根 = **对方原文**，所以 `$.applyNo` 取的是对方字段 |
| `pre_strategy_name` | **留空** | 前序策略的语义是"改请求报文"，被调方向没有请求报文可改 |
| `post_strategy_name` | 可空（列 NOT NULL DEFAULT ''） | 后序策略加工**产物**（应答），不影响判定 |
| `result_judge` | 状态白名单，见 §4 | **必填**；判的是「报文可受理」，不是业务成败 |
| `judge_name` | 空（默认 `ruleSpec`） | 只有自定义 `ResultJudge` 才填 |
| `status` / `del_status` | `1` / `0` | 只有这两类会被加载 |
| `logic_branch` × N | 见 §4 | 首命中即执行；`logic_branch_order` 升序 |

## 4. 一份完整示例：放款结果通知

**配置行**（`ifmap_config`）：

```json
{
  "tenantId": 1,
  "interfaceNo": "RCV_LOAN_PAY",
  "interfaceCode": "CMB_RCV_LOAN_PAY",
  "interfaceName": "招行放款结果通知（被调）",
  "busiNode": "loanPayRcv",
  "partnerCode": "CMB",
  "partnerName": "招商银行",
  "interfaceOrder": 1,
  "callDirection": "INBOUND",
  "requestParamTemplate": "",
  "preStrategyName": "",
  "resultJudge": "{\"any\":[{\"path\":\"$.noticeStatus\",\"op\":\"eq\",\"value\":\"SUCCESS\"},{\"path\":\"$.noticeStatus\",\"op\":\"eq\",\"value\":\"FAILED\"}]}",
  "responseParamTemplate": "{\"code\":\"0000\",\"message\":\"success\",\"applyNo\":\"$.applyNo\",\"partnerSeqNo\":\"$.['seqNo']\",\"ourSeqNo\":\"$.seqNo\"}",
  "status": 1
}
```

**为什么判定要写 `any` 两条**：这次推送的 `noticeStatus` 只有 `SUCCESS` / `FAILED` 两种取值，
**两者都必须被受理**（业务失败也是有效推送，要去记账），所以白名单要写全。
只写 `SUCCESS` 的后果：对方的失败通知会被判成 `VALUE_MISMATCH` → 分支不执行 → 我们既不记账也不回 ACK。

**应答模板里两个 `seqNo` 的写法不是笔误**（实测口径，见 §9 第 12 条）：

| 想要 | 写法 | 取值 |
| --- | --- | --- |
| **对方**报文里的 `seqNo` | `$.['seqNo']` | `SEQ-9001`（源报文原值） |
| **我方**生成的流水号 | `$.seqNo` | `20261023133003465512`（20 位，与源报文无关） |

> 顶层只允许 `{"op":"always"}` 或 `{"all":[...]}` / `{"any":[...]}`；算子写 `equal` 是非法的（用 `eq`）。
> 支持的算子：`eq` / `ne` / `in` / `notIn` / `exists` / `notBlank` / `regex` / `always`。

**分支两行**（`ifmap_logic_branch`）：

| `logic_branch_order` | `logic_branch_name` | `branch_judge` | `method_flag` |
| --- | --- | --- | --- |
| 1 | 受理分支 | `{"any":[{"path":"$.noticeStatus","op":"eq","value":"SUCCESS"}]}` | `loanPaySuccess` |
| 2 | 失败分支 | `{"any":[{"path":"$.noticeStatus","op":"eq","value":"FAILED"}]}` | `loanPayFailed` |

`branch_judge` 与 `result_judge` **同一套语法**（顶层只能 `always` / `all` / `any`，`eq`/`ne`/`in`/
`notIn`/`exists`/`notBlank`/`regex`，单条件包一层 `any`），求值根是**对方原文**；额外两个分支专用算子：

| 算子 | 语义 | 例 |
| --- | --- | --- |
| `judged` | 与 `result_judge` 命中的那个值（`actualValue`）比较 | `{"any":[{"op":"judged","value":["SUCCESS"]}]}` |
| `strategy` | 交给 `@LogicBranch` 注册的策略判断 | `{"any":[{"op":"strategy","value":"PAY_SUCCESS"}]}` |

- **`branch_judge` 必填**：留空是「非法配置」（运行期 `SPEC_INVALID` 直接判失败），**不是**兜底。
  兜底分支要显式写 `{"op":"always"}`，每接口最多 1 条，且不参与常规匹配（排前面也不会抢命中）。
- 命中结论看 `logic_branch_name`：`IfmapResult.getMatchedBranch()` 与执行日志记的都是它。

**动作**（宿主实现，一个分支一个）：

```java
@IfmapAction("loanPaySuccess")
public class LoanPaySuccessAction implements IfmapActionHandler {

    @Override
    @SuppressWarnings("unchecked")
    public void execute(StrategyContext context) {
        String applyNo = (String) context.getParams().get("applyNo");
        // 业务逻辑：更新放款状态、记账……
        // 业务失败**不要抛异常**：动作在 writeLog 之前执行，抛出去连执行日志都不会落（见 §9 第 10 条）；
        // 正确做法是回填失败码 + retryable，让调用方自己决定要不要请对方重推。
        // 回填应答字段：产物是 Object，必须强转成可写的 Map，原地改才生效（见 §6）
        Map<String, Object> ack = (Map<String, Object>) context.getResponseData();
        ack.put("code", "0000");
        ack.put("message", "success");
    }
}
```

## 5. 宿主代码怎么调

```java
// 一次被调入口：request 的 rawBody = 对方推过来的报文原文（建议原样字符串，不要先自己反序列化）
IfmapRequest request = IfmapRequest.of(payload)          // payload 用于参数（可选）
        .withAttribute("noticeStatus", status)            // 供 RuleContext 读（可选）
        .withRawBody(rawBody);                            // 判定/应答模板取值的原文（必须）

// 便捷入口：等价于 executeInbound(...) = execute(request.withRawBody(rawBody), ...)
IfmapResult result = orchestrator.executeInbound(request, "RCV_LOAN_PAY", "loanPayRcv", rawBody);
```

> 可运行的完整样例：`ifmap-demo-spring-boot3` 的 `InboundNoticeDemo`（配置 + 2 条分支 + 两个动作 + 三个场景），
> `mvn -pl ifmap-demo-spring-boot3 -am test` 直接跑（H2 内存库，无需外部依赖）。

- `mockResponse` 非空 = dry-run：把 mock 当**对方原文**替换掉真实报文，用来在管理端用一份样例报文试跑整条链路
  （判定 + 分支 + 应答都真跑，只是不出网）。
- **`payload` 与 `rawBody` 各走各的**：判定与应答模板**只读原文**；`params`（动作里 `context.getParams()`）**优先 payload**，
  为空才宽松解析原文。两者不一致时不会互相顶掉 —— 这是刻意设计（原文是事实，payload 是我方补的上下文）。

## 6. 应答报文从哪来（这一段配错了最费时间）

编排器返回值：

```java
result.getData()   // = flattenPool(pool) + {"pool": pool}
result.getSuccess()
```

- `pool` 的键是**接口编号**，值是**这一步的产物**（= `response_param_template` 渲染结果，再经后序策略加工）。
- `flattenPool` 把每步产物**展平到顶层**，所以单步被调接口的 `result.getData()` 就是
  `{"code":"0000","message":"success","applyNo":"A123","partnerSeqNo":"...", "pool":{...}}`。
- **只有判定成功的步骤才入池**（池的键集合 = 已成功步骤集合 = 断点续跑的进度）。
  判定失败时这一步的产物**没有任何出口**（`result.getData()` 里不会有它）。
- **动作能改产物，靠的是"同一个对象"**：`pool.put(interfaceNo, data)` 在 `applyBranch` **之前**执行，
  且 `context.setResponseData(data)` 指向同一个 Map ⇒ 动作里 `ack.put(...)` 会同时改掉池里的值和返回值。
  反过来，`ack = new HashMap<>()` 这种**重新赋值**不会生效。

### 6.1 给应答补字段的三条通道，怎么选

| 通道 | 配置位 | 跑在 | 适合做什么 | 坑 |
|---|---|---|---|---|
| 应答模板 | `response_param_template` | 判定前 | 从对方原文映射出应答（**主渠道**） | 根是**对方原文**，不是产物；`$.seqNo` 是保留路径（§4、§9 坑 12） |
| 后序策略 | `post_strategy_name` | 判定**前** | 加与原文无关的字段（常量、我方业务号、时间戳），或整段重算产物 | 报文不可受理时它**也跑了**，但判定失败 ⇒ 应答不返回给三方（加工了白加工）；改不动判定 |
| 分支动作 | `method_flag` → `@IfmapAction` | 判定**后** | 依赖判定结果/分支的业务处理，包括把 `0000` 覆盖成 `2xxx` | 抛异常会带走执行日志（§9 坑 10）；只能原地改 Map |

`post_strategy_name` 在前两条里最容易被想到"用它兜拒收应答"—— **不行**，拒收时产物没有出口。
拒收应答由宿主按 `failType` 自己组装（§7）。可运行样例：`NoticeAckStamp`（后序补 `ackChannel`/`ackBizId`）
与 `NoticeAcceptedAction` / `NoticeFailedAction`（动作改 `approveNo` / 覆盖成 `2001`）。

## 7. 三个终态与建议码

| 终态 | 谁来判 | 建议 `code` | 建议 `retryable` | 语义 |
| --- | --- | --- | --- | --- |
| 受理并办妥 | 动作成功执行 | `0000` | 不出现 | 已处理，别再推 |
| 拒收（报文都不可受理） | 引擎（`result_judge` 失败） | `1xxx` | `false` | 报文有问题，重推也没用 |
| 处理失败（受理了但办不成） | 动作**回填**应答字段 | `2xxx` | `true` | 我这边的问题，请重推 |

**引擎里不出现任何业务码**：`0000` / `1xxx` / `2xxx` 只写在**你的应答模板与动作里**。
引擎只提供"结构"（判定失败类型 `fail_type`、`actualValue`），不替你编业务码 —— 否则换一家合作机构就得改引擎。

**注意**：判定失败时动作不执行 ⇒ **拒绝应答也是应答**，但这条路只能由宿主在拿到
`result.isSuccess() == false` 之后自己按 `result.getErrorMessage()` / `fail_type` 拼（引擎不会渲染应答模板）。
这条限制是刻意的：能拼"拒绝码"的地方一旦落在引擎里，就必然要引入业务码常量（见 §9 第 6 条）。

## 8. 保存前校验（`ConfigValidator`，管理端 `/validate` 与保存都会跑）

| 级别 | 触发条件 | 为什么拦 |
| --- | --- | --- |
| error | `response_param_template` 为空 | 回给对方的报文都没有 ⇒ 本步产物是空 Map，引擎白跑一趟 |
| error | `request_param_template` 非空 | INBOUND 不渲染模板 ⇒ 配了永不生效，会让人以为入参被加工过 |
| error | `pre_strategy_name` 非空 | 没有请求报文可改 ⇒ 配了永不执行 |
| warning | `result_judge` = `{"op":"always"}` | 任何报文都算受理，对方推错内容也不会有任何拦截 |
| warning | 该接口尚无任何 `logic_branch` | 受理之后没有分流 ⇒ 动作不会执行 |
| warning | 本步之前存在**出网**步骤 | 混合链路是允许的，但前面的出网调用**已经发生副作用**，而本条拿到的入参与它无关；顺序放错只能靠这条提醒发现 |

出网方向不加任何新规则（原行为不动）。

## 9. 十二条坑（都是实际踩过的）

1. **判定失败 ⇒ 分支动作不执行**：想在"失败时也做点什么"，就把失败状态写进 `result_judge` 白名单（§4），
   用分支去分流，而不是指望判定失败后还能跑动作。
2. **`actualValue` 只记"第一条命中"的值**：`any` 里多条同时命中时，分支比对用的是第一条。
3. **动作在 `pool.put` 之后** ⇒ 只能**原地改** `Map`，重新赋值无效（§6）。
4. **`applyPostStrategy` 在"没配后序策略"时会早返回，且不设置 `responseData`**：所以编排器在判定后**无条件**
   `context.setResponseData(data)` —— 这段顺序改不得，否则「动作回填应答字段」这条通道直接断掉（恒 `null`）。
5. **`{"op":"always"}` + 网关异常 = 静默成功**：`always` 根本不读报文，若 `exchange` 抛的是
   `IfmapRemoteException` 被内部吞掉，会得到一次"成功"的空产物。被调方向不出网，不受此影响；出网方向别用 `always` 兜底。
6. **不同分支不能回不同 ACK 模板**：应答模板是**配置级**的（一条配置一份），分支只能回填字段值。
   要"按状态回不同结构"，得拆成两条被调接口配置（不同 `interface_no`）或让动作清空/补齐字段。
7. **混合链路顺序**：`INBOUND` 通常应排在本节点第一步；排在出网步骤之后时，前面的副作用已经发生（§8 warning）。
8. **`$.pool.*` 只在请求模板里有效**：被调方向不渲染请求模板，所以这条对 INBOUND 无意义；
   应答模板里**不能**用 `$.pool.xxx`（它的根是对方原文）。
9. **日志里的"响应"是被调方向的我方应答**：`writeLog` 在 INBOUND 下记的是**动作回填后的产物**
   （因为 `response == requestJson`，两列同值没意义）。所以看日志发现"响应"里有 `code`/`message` 是正常的。
10. **动作抛异常 = 没有执行日志**：`applyBranch` 在 `writeLog` 之前，
    动作抛出去会一路穿过 `executeOne` / `runPlan` 直达调用方 —— 这次调用既没有日志行、也没有 ACK。
    「受理了但办不成」应当回填 `2xxx` + `retryable:true`，而不是抛异常。
11. **DDL 清单有两份**：`IfmapSchemaInitializer.ALTER_FILES`（`ifmap.ddl.auto` 建表用）与
    `TestDatabases.PRODUCTION_DDL`（真库测试用）。新增 changeset 必须**同时**加到两处，否则真库测试会一片
    `Column "XXX" not found`。
12. **应答模板里想把对方的 `seqNo` 原样回传，`$.seqNo` 拿不到**：`$.seqNo` 是模板 DSL 的**保留路径**
    （`docs/02` §1 第 7 条），命中后直接生成我方流水号，**不看源报文**。实测三种写法：
    `$.seqNo` → `20261023133003465512`（生成的）；`$.['seqNo']` → `SEQ-9001`（对的）；
    `$['seqNo']` → 原样输出字符串 `$['seqNo']`（少一个点 ⇒ 不以 `$.` 开头 ⇒ 被判成字面量，**静默出错**）。
    规避办法就一个：**别用 `$.seqNo` 去取源字段**，要么写 `$.['seqNo']`，要么让对接方把字段改名
    （如 `partnerSeqNo`）。这条在出网方向同样成立 —— 请求模板里写 `"seqNo":"$.seqNo"` 得到的是
    "我方流水号"，不是"上一步传来的 seqNo"。

## 10. 排障

| 现象 | 先查 |
| --- | --- |
| 对方说"你回的不是我在等的结构" | `response_param_template` 是否为空（§8 第一条 error）；动作里是否**重新赋值**了 Map 而不是原地改 |
| 回给对方的 `code` 永远是模板里的默认值 | 动作没执行（分支没命中 / `method_flag` 未注册 / 判定失败）；看执行日志的「命中分支」列 |
| 业务字段（`applyNo` 等）是空的 | 应答模板写成了 `$.data.applyNo` 而对方原文没有 `data` 这层；INBOUND 的模板根就是**原文根** |
| 判定总是 `VALUE_MISMATCH` | `actualValue` 是否带空格/大小写不同（`eq` 默认严格相等，要忽略大小写写 `"ignoreCase":true`） |
| 判定总是 `FIELD_MISSING` | 路径写错，或 `payload` 覆盖了同名字段（记住：判定读原文，不读 payload） |
| 这一步 "成功了但什么都没做" | 没有逻辑分支 / 分支 `branch_judge` 与原文不符 / `method_flag` 拼错（未注册会抛 `IfmapStrategyException`） |
| 保存被拦「不渲染 request_param_template」 | 从 OUTBOUND 改成 INBOUND 时残留的请求模板，清空即可 |
| 想先看链路通不通 | 管理端 dry-run：`executeInbound` 传 `mockResponse`（一份样例报文），判定/分支/应答都真跑，不出网 |

## 11. 与旧 `IfmapCallbackHandler` 的关系

旧设计里每个银行接口对应一个 `IfmapCallbackHandler` 实现（`@IfmapCallback("IF_X")`），由
`CallbackRegistry` 按接口号分发。该通道**已移除**（见 CHANGELOG `Removed`）：

- 它从没进过主链路（不经模板、不经判定、不落判定列），回调日志的"结论"永远缺失；
- 它把「接哪个接口、怎么判、怎么分流」写死在宿主代码里，等于把配置驱动的意义让回去了；
- 被调场景用「配置 + `call_direction=INBOUND` + 判定 + 分支」表达后，宿主**只需要写动作**（业务逻辑），
  接口清单、判定规则、分流规则全在配置里 —— 存量 17 个同构回调方法可以直接映射成 17 条配置 + 若干动作。
