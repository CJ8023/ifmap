# 存量系统迁移指南（M1 ~ M3）

> **适用对象**：已经有一套自研「资方接口配置表 + 定制执行代码」的系统（配置驱动地做接口
> 报文映射、结果判定、分支流转），希望换成 ifmap。
>
> 本文只写**方法论与执行顺序**：不绑定任何具体客户、资方、业务规则名与表前缀。
> 文中的表前缀 `bankint_` 只是"ifmap 前身工程"的示例前缀，换成你自己的前缀即可。

---

## 0. 迁移的成本到底花在哪

一个常见误判是「换表结构才是迁移」。实际上四个阶段的成本量级大致是：

| 阶段 | 干什么 | 成本 | 风险 |
|---|---|---|---|
| **M1** 数据迁移 | 加列 / 回填 / **改列名** / 改类型 / 加索引 / 改表名 | 低（脚本化，可演练） | 中（DDL 阻塞业务） |
| **M2** 规则与策略对齐 | 存量规则名、动作名、策略名逐个对上 ifmap 的注册点 | **中**（体力活） | **高（静默出错）** |
| **M3** 切换与回滚 | 停存量 → 改表名 → 起 ifmap | 极低（秒级） | 中（回滚窗口） |

**M2 才是真正的风险点**：存量配置里写的是"规则名 / 动作名 / 策略名"这些**字符串**，
ifmap 找不到注册就会走不同的分支 —— 有的报错（好事），有的**取到空值继续跑**（坏事：
业务回调静默不执行）。所以 M2 不能只看"程序起来了"：必须跑启动期契约自检（§4.3），
并在切换前用 `dry-run` 逐接口核对取值。

## 1. 迁移总览

```
M0 摸底 ──> M1 表结构迁移 ──> M2 规则/策略对齐 ──> M3 切换与回滚
           （kit 脚本）        （代码 + 自检）       （RENAME）
                 │                    │                    │
                 └──── 共存期：ifmap.table-prefix 指向存量表 ──────────┘
```

| 阶段 | 产出 | 完成标准 |
|---|---|---|
| M0 | 存量清单（列 / 规则名 / 动作名 / 策略名 / 模板 / 日志量） | 清单可核对，无"不知道是什么"的配置项 |
| M1 | 目标结构的存量表 | 迁移 kit 的 `05-verify.sql` 结构节全绿 |
| M2 | 宿主的规则 / 动作 / 策略注册代码 | `GET /ifmap/admin/audit` 返回 **0 违规** |
| M3 | 表名切换 + 应用切换 | 切换后执行日志正常，观察 1~2 个业务日无异常 |

## 2. M0 前置：摸清存量

在动 SQL 之前先把这五张清单拉出来（`M1` 的 `00-precheck.sql` 会给你前两项的数据）：

1. **列清单**：`information_schema.COLUMNS`，含类型 / 可空 / 默认值 / 注释；
2. **数据体检**：行数、重复键、超长值、NULL、零值时间、非法 JSON 模板；
3. **规则清单**：把所有模板里出现的 `@FUN(名字, ...)` 与"自定义函数调用"抽出来去重 ——
   这是 M2 的输入（**存量代码里搜规则注册点，别靠猜**）；
4. **动作与策略清单**：把所有配置行里 `method_flag` / `strategy_name`（迁移后要落到 `pre_strategy_name` 或 `post_strategy_name`）/ 分支标识的取值 `DISTINCT` 出来；
5. **日志量**：执行日志表的行数与 `DATA_LENGTH`（决定 M1 走低峰 `ALTER` 还是 gh-ost）。

> 模板里"裸字段名"（不带 `$.` 的路径）也要一并统计：ifmap 支持 `$.a.b` 与裸字段名两种写法，
> 但**存量自定义解析器**的语义可能与 ifmap 不一致（例如是否区分大小写、空值是否算命中）。

## 3. M1：表结构迁移

### 3.1 先选路径

> **还有第三条路：干脆不迁表。** 如果存量配置本来就是通过 HTTP 接口读的（ECC 就是这样），
> 可以直接用 [`docs/11-远端配置源.md`](11-远端配置源.md) 的 `ifmap-provider-remote` 把那个接口接成
> `ConfigRepository` —— 配置仍在老服务里，ifmap 只读；差异清单见该文 §6（例如判定已从
> `result_flag` + `success_value` 换成必填的 `result_judge` 单列，远端必须跟着发）。这条路**不影响**下面的表结构迁移：等有了独立部署的诉求再迁也不迟。

| 路径 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **A. 前缀指向**（共存期首选） | `ifmap.table-prefix=<存量前缀>`，ifmap 直接读写存量表 | 灰度期：新旧链路共用同一批配置 | 0 数据迁移；注意别让 ifmap 自动建表（表已存在） |
| **B. 改表名**（切换期首选） | 结构改完后 `RENAME TABLE` 成 `ifmap_*` | 存量模块已停用 | 毫秒级元数据操作，可秒级回滚 |
| **C. 新表 + 搬迁** | 建 ifmap 新表，`INSERT ... SELECT` 搬配置 | 两套要完全独立 | 需要字段映射与数据校验；回滚要回切数据源 |

> **不要用视图兜底**（`CREATE VIEW 旧表名 AS SELECT * FROM 新表`）：视图不可写，
> 存量代码一旦写库就报错，而且"迁移到底做完没有"变得不可判断。

### 3.2 迁移脚本

`ifmap-provider-jdbc` jar 里带了 Migrations-kit（**手动执行，不会被 Liquibase/Flyway 自动跑**）：

```
ifmap-provider-jdbc/src/main/resources/db/migration/ecc-to-ifmap/
├── README.md              # 完整执行手册（算法/锁、大表、排错、checklist）
├── 00-precheck.sql        # 只读体检（含唯一键冲突、NULL/长度体检、时区、基线快照）
├── 01-add-columns.sql     # 纯 ADD COLUMN（在线）
├── 02-backfill.sql        # 回填（软删唯一化、分支顺序）
├── 03-modify-and-index.sql# 改列名 + 改类型/可空 + 加唯一键与索引
├── 04-rename-tables.sql   # 切换时刻：RENAME TABLE
└── 05-verify.sql          # 迁移后核对
```

**MySQL 5.7 的三条铁律**（kit 严格遵守，自己写脚本时也要遵守）：

1. 同一张表的多次变更**合并成一条 `ALTER TABLE`**（5.7 没有 `ALGORITHM=INSTANT`，分开写会多次重建表）；
2. 每条 DDL **显式写 `ALGORITHM=` 与 `LOCK=`**（防静默降级成阻塞写入的 `COPY`）；
3. 会话先 `SET SESSION lock_wait_timeout = 10`（默认等锁上限 1 年）。

| 操作 | 5.7 的写法 |
|---|---|
| `ADD COLUMN` / `ADD KEY` | `ALGORITHM=INPLACE, LOCK=NONE`（允许并发读写） |
| **改列名**（`CHANGE COLUMN`、定义不变） | 官方标称 In Place / 不重建，但脚注限定「定义不变」；本 kit 顺带改了注释（`bank_name` 还收窄类型），故与类型变更合并进同一条 `ALTER`，实际走 `COPY` |
| **改变列数据类型** | **`ALGORITHM=COPY, LOCK=SHARED`**（只允许并发读；`LOCK=NONE` 会**直接报错**） |
| `RENAME TABLE` | 直接执行（元数据操作） |

**别 `KILL` 正在跑的 5.7 DDL**：DDL 非原子，中断会残留 `#sql-ib*.ibd` 孤儿表并让数据字典不一致。

### 3.3 结构差异的典型形态

| 变化 | 例子 | 为什么要改 |
|---|---|---|
| **改列名** | `bank_code` / `bank_name` → `partner_code` / `partner_name` | 标识符不再锁死在「银行」：同一列要承载银行 / 保理 / 信托 / 小贷 / 保险等各类合作机构。⚠️ **它会打断共存期（路径 A）** —— 存量模块 SQL 里的旧列名会报 1054，处置方式见迁移 kit 的 `README.md` §2 |
| 类型收窄 | 顺序号 `char(2) → smallint` | 字符串排序下 `'10' < '2'`，顺序会错 |
| 类型放宽/统一 | 操作人 `bigint → varchar(64)` | 存的是用户名/工号，不是数值 |
| 时间精度 | `timestamp → datetime(3)` | 固定值不受会话时区影响；毫秒精度 |
| 行格式 | `ROW_FORMAT=DYNAMIC` | 唯一键长度上限从 767 → 3072 字节（避免 1071） |
| 索引 | 按 ifmap 的查询形态建 3~4 个索引 | 存量表常常"除主键零索引" |

> 唯一键里带 `deleted_seq` 是 ifmap 的软删除方案：未删除行恒为 `0`，删除时写入主键值。
> 所以**回填必须在加唯一键之前**，否则历史软删行全是 `0` → 建唯一键直接撞 `1062`。

**存量结构不止一个版本**（实测两套真实存量：`yfl_bill` 的 `bankint_config` 22 列、`yfl_financing_scheme` 的 25 列，
都没有设计文档里假设的 `financing_mode`；`yfl_bill` 还没有 `interface_code`/`project_code`/`interface_name`，
`yfl_financing_scheme` 则多一个 `fig_bank_code`）。因此迁移 kit 不是「环境无关」的：
**执行前先把 `00-precheck.sql` 第 3 步（列定义全量清单）+ 3.1 步（列齐备性清单）的输出当输入，逐列核对一次** ——
缺的 `ADD COLUMN`、多的按「只增不映射」保留（都是 `DEFAULT NULL`，ifmap 的 INSERT 不写它们）。
清单只能给待办、不能当门禁（各环境形态本就不同），实测两个变体的完整跑批结论与逐列差异见
`ifmap-provider-jdbc/src/main/resources/db/migration/ecc-to-ifmap/README.md` §9.4。

### 3.4 分支判定列换血：`logic_branch_flag` + `logic_branch_value` → `branch_judge`

逻辑分支表的两列判定字段（`logic_branch_flag` 策略键 / `logic_branch_value` 判定值）**合并成一列**
`branch_judge`（分支判定规格，`text NOT NULL`，无默认值），语法与接口级的 `result_judge` **完全同源**
（同一校验器、同一套 `all`/`any`、同一深度上限 3、同一套 `ignoreCase`），额外放开两个无 `path` 的算子
`strategy`（= 旧 `logic_branch_flag`）与 `judged`（= 旧 `logic_branch_value`）。

**回填规则（机械 1:1，迁移 kit `02-backfill.sql` 第 4 步 / Liquibase `009-backfill-branch-judge.sql`）**：

| 旧数据 | 回填后的 `branch_judge` |
|---|---|
| `logic_branch_flag` 空 | `{"op":"always"}` ← 旧"兜底分支"的显式写法 |
| flag 有值、`logic_branch_value` 空 | `{"any":[{"op":"strategy","value":"<flag>"}]}` |
| 两者都有 | `{"any":[{"op":"strategy","value":"<flag>"},{"op":"judged","value":["a","b"],"ignoreCase":true}]}` |
| flag 空、value 非空（脏数据） | `{"op":"always"}`（旧代码里 flag 空即走兜底，value 从未生效 → 行为不变） |

要点：

- **多值分隔符 `[;,]`**（不是建表注释里的 `|`），元素逐个 `TRIM`、空段丢弃；单个单元格最多 16 个值
  （回填的数字派生表只到 16，超出会被静默丢弃 → `00-precheck` 第 10.3.1 条是阻塞项）。
- **不顺手清洗**：分支选错不会报错、只会"跑了另一个动作"，所以只做能证明等价的变换；
  等价性由 core 的 `BranchJudgeEquivalenceTest` 双跑对照守住。
- **旧代码比较忽略大小写**（`equalsIgnoreCase`）⇒ 回填时给 `judged` 显式带 `"ignoreCase":true`。
  这一条是**唯一**的"看起来更严格但实际等价"：以后新配的分支默认严格匹配，要靠 `ignoreCase` 声明。
- 回填**幂等**（只处理 `branch_judge` 为空的行）；`branch_judge` 收紧成 `NOT NULL` 之前必须先回填。
- 两个旧列在回填后**删除**（迁移 kit `03` 的 B-2 段；Liquibase `010-drop-logic-branch-legacy.sql`）。
  不删就会长期存在两套口径：老代码写 flag/value、ifmap 只读 `branch_judge`，不一致时**分支看着有配置却不生效**，
  且没有任何报错。删列不可回退（只能从备份恢复）。
- **只跑过自动 DDL 的库**（`ifmap.ddl.auto=true`，starter 的 `ALTER_FILES` 只含 008 加列、不含 009/010）：
  存量行 `branch_judge` 是空串、旧两列还在 ⇒ 运行期 **fail-closed**（`fail_type=SPEC_INVALID`，不执行任何分支），
  所以必须手工跑一遍回填（kit `02` 第 4 步）再删旧两列（kit `03` B-2）。

> 迁移后「兜底分支」的表达从"列空"变成**显式规格** `{"op":"always"}`，每个接口仍最多 1 条；
> 空规格（`""` / `{}` / `{"all":[]}`）是**非法配置**（运行期 fail-closed、管理端直接拒），**不等于兜底**。

## 4. M2：规则与策略对齐（最容易静默出错）

### 4.1 配置里的每个"字符串"都要有注册点

| 存量配置里出现 | ifmap 侧对应 | 找不到会怎样 |
|---|---|---|
| 模板里的 `@FUN(规则名, 参数...)` | 内置 18 个规则，或宿主用 `@IfmapRule` 注册的方法 | **报错**（`IfmapRuleNotFoundException`）—— 好事，启动期就能发现 |
| `method_flag`（分支命中后执行的动作） | 宿主用 `@IfmapAction` 注册的 bean（key = `method_flag`） | **报错**（`缺动作` 抛 `IfmapConfigException`） |
| 分支标识（需要复杂判断的分支） | 宿主用 `@LogicBranch` 注册的 bean | **报错** |
| `pre_strategy_name` / `post_strategy_name`（前 / 后序策略钩子） | Spring **bean 名**（实现 `IfmapStrategyHook`）；两列可写同一个 bean（按 `StrategyContext.getPhase()` 区分前 / 后序）；另兼容两种历史写法，见下方说明 | 默认**快速失败**（抛 `IfmapStrategyException`）；配 `ifmap.orchestrator.fail-on-missing-strategy=false` 才改成 WARN 跳过 |
| 规则名拼错 / 大小写不一致 | — | 取不到值 → **模板渲染成空值继续跑** → **静默差异** |

存量的**单列** `strategy_name` 在 ifmap 里拆成了**两列**（`pre_strategy_name` / `post_strategy_name`），
而**旧值不会自动搬迁**：旧语义只有"一个策略"，"它该在出网前跑还是回参之后跑"是业务决策，脚本猜不出来
（迁移 kit 的 `01-add-columns.sql` 1.0 段只加列、不搬值）。逐条决定后填进对应列即可；同一策略两处都要跑就两列都写。

> **`pre_strategy_name` / `post_strategy_name` 的两个宽松别名（存量"首字母小写"写法为什么不用改配置）**
>
> 注册表按**三个 key** 注册同一个策略：① Spring **bean 名**（权威 key，精确命中、无告警）；
> ② **类简单名**（`CmbApplyStrategy`）；③ **首字母小写变体**（`cmbApplyStrategy`，
> 只动第一个字符 —— 与 Spring `Introspector.decapitalize` 的宽松版一致）。后两者命中时会记一条
> WARN，提示把配置改成 bean 名。
>
> 这层宽容是**为存量 P0-7 准备的**：存量（单列 `strategy_name` 时代）多按"类名首字母小写"人工填写，而 Spring 的
> 真实 bean 名在**前两个字母皆大写时保持不变**（类 `CMBApplyStrategy` 的 bean 名仍是
> `CMBApplyStrategy`，不是 `cMBApplyStrategy`）—— 存量 38 个策略实现里有 **11 个**两种写法不一致。
> 若只认 bean 名，这 11 个接口迁到 ifmap 后会在运行期抛 `IfmapStrategyException`；三 key 注册让它们
> **一行配置都不用改**。

**这就是为什么 M2 不能只靠读代码**：第 5 行这种"错了一个字母"的问题，只有启动期契约自检 + 逐接口 `dry-run` 才能抓出来。

### 4.2 迁移期宿主代码示例

```java
// 1) 存量自定义规则 → 用 @IfmapRule 注册（方法名随意，key 必须是配置里写的那个名字）
//    模板里写成 @FUN(myCheckStatus,$.applyStatus)，参数按位传入；
//    需要环境信息时把 RuleContext 声明为第一个参数（模板里不用传）。
public class LegacyRuleAdapter {

    @IfmapRule(value = "myCheckStatus", desc = "存量状态判定",
            example = "@FUN(myCheckStatus,$.applyStatus)")
    public boolean checkStatus(String applyStatus) {
        return "OK".equalsIgnoreCase(applyStatus);
    }
}

// 2) 存量 method_flag → 用 @IfmapAction 注册（key = method_flag 的值）
@IfmapAction("discSuccess")
public class DiscSuccessAction implements IfmapActionHandler {
    @Override
    public void execute(StrategyContext context) {      // 可读写 context 里的参数
        // 原存量代码里的"成功后处理"
    }
}
```

注册方式：Spring Boot 下把这两个 bean 声明在容器里即可（starter 会自动收集）；
纯 Java 下用 `IfmapEngine.builder().register(rules).build()` 与
`IfmapOrchestrator` 的 `actions` / `strategyHooks` 参数显式注册。
自定义规则的完整约束（可见性、重载、`override`、可变参数等）见
[`docs/03-规则清单与扩展.md`](03-规则清单与扩展.md)。

### 4.3 启动期自检（M2 的验收动作）

开启管理端（`ifmap.admin.enabled=true`，**默认关闭**，打开后请自行加鉴权），然后：

```bash
# 全量巡检：模板能否解析、规则/动作/策略是否都注册了、分支配置是否自相矛盾
curl -s 'http://localhost:8080/ifmap/admin/audit?tenantId=-1&markdown=true' | head -50
# 期望：报告里 errors 为 0（warnings 允许存在，但要逐条确认"是不是已知差异"）

curl -s 'http://localhost:8080/ifmap/admin/rules'          # 内置 + 宿主注册的全部规则名
curl -s 'http://localhost:8080/ifmap/admin/actions'        # 已注册的 method_flag
curl -s 'http://localhost:8080/ifmap/admin/strategies'     # 已注册的 pre_/post_strategy_name / 分支策略

# 单条配置的校验与试跑（不落库、不出网）
curl -s -X POST 'http://localhost:8080/ifmap/admin/configs/validate' -H 'Content-Type: application/json' -d @config.json
curl -s -X POST 'http://localhost:8080/ifmap/admin/configs/dry-run'  -H 'Content-Type: application/json' -d @dryrun.json
```

### 4.4 两个必须说清的语义（迁移期最容易配错）

| 配置写法 | 语义 | 备注 |
|---|---|---|
| `branch_judge` = `{"op":"always"}` | **兜底分支**：不参与常规匹配，只在所有常规分支都未命中时生效 | 排在第一条也**不会抢命中**；每个接口最多 1 条。**空规格不是兜底，是非法配置**（fail-closed） |
| `method_flag` **为空** | **该分支不执行任何动作**（只做匹配、不改状态） | 与"兜底"是两件事，别混 |

> 存量系统常用"某个标志为空"来表达兜底分支。迁移时**不要**把 `method_flag` 为空也当成兜底 ——
> 否则会出现"分支命中了但回调不执行"的静默差异。
> 另外旧 `method_flag` 为空时会**退化为用 `logic_branch_flag` 当动作名**，这条隐藏行为已删除（那一列也不存在了）；
> 现在 `method_flag` 空就是"不执行动作"，动作名必须显式配。

### 4.5 JSON 取值实现（存量用 fastjson 时看这里）

存量里常有一个自己封的取值工具（如 `JsonParseUtils`），底层是 **fastjson 的 `JSONPath`**，
而 ifmap 默认用 **Jackson + jayway JsonPath**。两者在常见路径（`$.a.b`、`$.items[0].sku`、
`$.items[*].sku`、`$.items[?(@.qty > 1)].sku`）上结果相同，差别集中在少数写法上：

| 写法 | 建议 |
| --- | --- |
| 对象根通配 `$[*].x` | 一律改为具体字段或 `$.field[*]`（jayway 会展开、fastjson 不会） |
| 递归下降 `$..x` | 别依赖结果列表等长（`leafToNull` 下两边补 `null` 的规则不同） |
| 宽松 JSON（单引号 / 无引号键 / 尾逗号） | 存量脏数据先洗，否则换 Jackson 后直接解析失败 |

两条路径都可以走：

1. **借机换成 Jackson**（推荐）：切换前按 §4.6 的口径逐接口核对取值形态；
2. **完全保持存量语义**：引 `cn.cj:ifmap-json-fastjson` 并自己声明 `JsonOps` bean，
   差异清单与版本选择见 [`docs/05`](05-SpringBoot集成.md) §3.2。

> 两条路径在切换前都必须逐接口核对：JSON 实现的差异不会报错，只会“取到的值不一样”。

### 4.6 数字形态与小数保真（迁移前必读）

升级到本版后，**小数出来长什么样**不再取决于底层 JSON 库，而是固定契约（四个"不再"）：

| 场景 | 升级前（随库/版本漂） | 升级后 |
| --- | --- | --- |
| 源 `"10.00"` | Jackson `"10.0"` / fastjson `"10.00"` | **`"10.00"`**（保留源文字小数位） |
| 源 `"12345678.90"` | Jackson `"1.23456789E7"` | **`"12345678.90"`**（不丢位数） |
| 源 `0.000001` | Jackson `"1.0E-6"` | **`"0.000001"`**（永不科学计数法） |
| 源 `{"items":[1.50,2.25]}` | Jackson `[1.5,2.25]` | **`[1.50,2.25]`**（类型仍是 number，只去 `E`） |
| 模板 `"@sum@$.amounts"` | 无引号 number `3.5` | **字符串 `"3.5"`**（与 `numSum` 一致） |

**迁移动作：**

1. **先盘点再切 `fail`**：本版会因上面这些形态变化改变输出 —— 属**预期**，不是逻辑回归。
   上线前抽若干接口比对一次升级前后的报文，别把它当成"新引擎算错了"去逐条查。
2. **扫一遍 `@sum@` 模板**：目标侧若是"按 JSON number 收"（对方用 `getInteger`/`getBigDecimal`
   而不是 `getString`），B-4 之后会变成字符串而**对方可能直接抛类型异常**。核对方式是把该字段的
   目标侧类型取一次真实值；确实要 number 见 `CHANGELOG` 的开放问题 R4。
3. **保留两位小数不要指望自动**："保留源文字小数位"只在**源报文里就写了两位**时成立。
   源是 JSON number `10.0` 时尾随零的信息本来就不存在，引擎不猜 —— 要强制两位请用
   `@FUN(numRound,$.amount,2)` 或 `@FUN(numFormat,...)`。
4. **不要用视图/工具"抹平"差异**：这是**输出侧**契约，改模板取值只会把问题挪个位置。

## 5. M3：切换与回滚

### 5.1 切换 checklist

- [ ] M1 的 `05-verify.sql` 结构节全绿（表名可能还是存量前缀，路径 A）；
- [ ] **列改名已生效**（`partner_code` / `partner_name`，`SHOW FULL COLUMNS` 复核）**且存量模块的列名已处置**（同步改 / 兼容视图 / 停写窗口改，见迁移 kit `README.md` §2）；
- [ ] M2 自检 0 违规；
- [ ] **停存量模块**（定时任务、MQ 消费者、入口开关全停）—— 这一步不做完不要改名；
- [ ] `RENAME TABLE 存量前缀_* TO ifmap_*`（毫秒级）；
- [ ] 确认 ifmap 侧 `table-prefix` 为默认 `ifmap_`；
- [ ] 启动 ifmap 应用 → `05-verify.sql` 全量节通过 → 执行日志开始有正常记录；
- [ ] 观察 1~2 个业务日（成功率、耗时、失败原因分布）。

### 5.2 回滚（随时可用，秒级）

```
停 ifmap → RENAME TABLE ifmap_* TO 存量前缀_* → 重新启用存量模块
```

**不要做双写**：两边同时写同一批配置表，等于把"谁覆盖谁"变成运行时随机行为；
共存期要"两边都能看到最新配置"，用路径 A（同一张表）而不是双写。

## 6. 行为对齐清单（逐条确认，别跳）

| # | 语义点 | 存量常见行为 | ifmap 行为 | 迁移动作 |
|---|---|---|---|---|
| 1 | 接口执行顺序 | 顺序列**没被使用**，实际顺序不确定 | 显式按顺序列升序（同值按主键）；且**只在同一个业务节点内**成序，调用方传的 `interfaceNo` 是「起点」不是「前置链」 | ① 整理顺序值（建议 10/20/30 留白）；② 同一 `busi_node` 内的步骤才互相看得到产物 |
| 2 | 逻辑分支顺序 | 靠 DB 返回顺序 | 按分支顺序升序取首个命中；**兜底分支最后**（两趟匹配，排第一也不抢命中） | 回填 + 人工复核 |
| 3 | 兜底 / 动作 | 常混在一个字段上判断 | `branch_judge = {"op":"always"}` = 兜底（显式）；`method_flag` 空 = 不执行动作 | 按 §3.4 回填（旧"空 flag" → `always`，行为不变），宿主必须注册动作 bean |
| 4 | 规则名 | 自定义规则库 | 内置 18 个 + 宿主 `@IfmapRule` | 逐个对齐，自检要求 0 违规 |
| 5 | 模板非法 JSON | 存进去也能跑（取不到值→空） | 契约校验判定违规（保存被拒） | 先扫存量脏数据 |
| 6 | 时间语义 | `timestamp` 随会话时区 | `datetime(3)` 固定值 | 迁移前后抽样逐行比对 |
| 7 | 日志保留 | 没有自动清理 | 默认开启「保留期 + 分批清理」 | 不想动历史数据就先关掉 |
| 8 | 日志失败原因 | 可能没有该列 | 新增失败原因列 | 无需动作 |
| 9 | 软删除 | 只有删除标记，历史行与在用行冲突 | 软删除唯一化（`deleted_seq`） | 回填历史行 + 建唯一键 |
| 10 | 多租户 | 单租户或按业务线隔离 | 所有查询强制带 `tenant_id`（空 → `-1`） | 确认配置行的租户值与调用方传的一致 |
| 11 | JSON 取值 / JsonPath | 常用 fastjson 的 `JSONPath` | 默认 Jackson + jayway json-path | 少数写法行为不同（对象根通配、`$..` 补 null）；见 §4.5 |
| 12 | 结果判定写法 | 两列：`result_flag`（JsonPath，**空 = 成功**）+ `success_value`（单值 / `,` 多值 / **`!a` 取反**，比较时忽略大小写） | 一列 `result_judge`（JSON 规格，**必填**）：多值 `{"op":"in","value":["a","b"]}`、取反 `{"op":"ne","value":"a"}`、不判定 `{"op":"always"}`；**`ignoreCase` 默认 false（严格比较）** | 逐条把旧两列翻译成规格（对照表见 [`docs/06`](06-执行编排与策略扩展.md) §7.3）；`!` 取反写 `ne`；要保留旧的大小写不敏感必须显式加 `"ignoreCase":true` |
| 13 | 小数形态 | 随底层 JSON 库与版本漂（`1.23456789E7` / `1.0E-6`） | 固定契约：保源文字小数位、不丢位数、**永不科学计数法** | 逐接口核对升级前后报文（§4.6） |
| 14 | `@sum@` 的返回类型 | 无引号 number | **字符串**（与 `numSum` 一致） | 目标侧按 number 收的字段要改（§4.6 第 2 条） |
| 15 | 表达式错语法（`@sum@$.a,$.b` / `@FUN(` 未闭合） | 存进去也能跑（静默 0 / 回写原文） | 启动期与保存前**一律拒绝** | **必须先跑一次存量配置巡检**再上线（§4.3） |
| 16 | 前后序加工 | 常只有一个"特殊处理"钩子，出网前调一次 | 两个钩子：`pre_strategy_name`（出网前）/ `post_strategy_name`（回参产物之后、判定之前） | 存量的单列 `strategy_name` **不自动搬**：逐条决定该策略属于前序还是后序（都要跑就两列都写） |
| 17 | 步骤间传参 | 前置接口的产物靠代码里手工拼 / 全局变量 / 再查一次库 | 引擎内建**跨步骤共享池**：`$.pool.<前面步骤的接口号>.<字段>`；**只有判定成功的步骤入池**；宿主可用 `payload.pool` 预置数据 | 把原来手工拼的字段路径改成 `$.pool.*`；预置数据走 `payload.pool`（别在 `payload` 顶层伪装成某个接口的产物） |

## 7. 排错速查

| 现象 | 首查 |
|---|---|
| 启动报缺规则 / 缺动作 | M2 未完成：`GET /ifmap/admin/audit`，逐条补 `@IfmapRule` / `@IfmapAction` |
| 业务跑通但回调没执行 | 分支是兜底分支吗？`method_flag` 是否为空？命中分支与预期是否一致（看执行日志的**命中分支**字段） |
| 配置查不到 / 巡检恒为 0 条 | `tenant_id` 不一致（空值 → `-1`） |
| 取到的字段全是空 | 模板路径写错、规则名拼错（大小写）；用 `dry-run` 接口逐步看中间结果 |
| 迁移 SQL 报 `1062` | 唯一键冲突：`00-precheck.sql` 第 6 节没通过就往下跑了 |
| 迁移 SQL 报 `1071` | 老表 `ROW_FORMAT=COMPACT`（索引前缀 767 字节上限）→ 先转 `DYNAMIC` |
| 迁移 SQL 报 `1048/1138` | 目标为 `NOT NULL` 但存量该列有 NULL（**别指望列的 `DEFAULT` 兜底**：显式写 NULL 不生效） |
| DDL 卡住 | 长事务占表：查 `information_schema.INNODB_TRX`；**不要 `KILL`** 5.7 的 DDL |
| 从库延迟飙升 | 大表 `ALTER` 走了 `COPY`：改低峰执行，或用 gh-ost 限流 |
| 模板取到的值与存量不同 | JSON 实现差异（对象根通配 `$[*].x`、`$..x` 补 null、宽松 JSON）：见 §4.5 |
